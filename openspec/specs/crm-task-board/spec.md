## Requirements

### Requirement: สร้างงานบนกระดานได้ด้วยหัวข้อ + ชื่องาน โดยวันครบกำหนดเป็นตัวเลือก
`/crm/alerts` SHALL มี "กระดานงานที่ต้องทำ" ที่ admin สร้างงานเองได้ โดยข้อมูล
**ที่บังคับ** มีเพียง 2 อย่าง: `topicId` (ต้องเป็นหัวข้อที่มีอยู่จริงและยัง
`isActive`) และ `title` (ต้องไม่ว่างหลังผ่าน `sanitizePlainText`) ส่วน `detail`,
`dueDate` และลิงก์ข้ามเอนทิตี้ SHALL เป็น **ตัวเลือกทั้งหมด** — งานที่ไม่มี
วันครบกำหนดคือโพสต์อิตที่ถูกต้องสมบูรณ์ (D5) ห้ามบังคับให้ใส่วันที่

เมื่อบันทึกสำเร็จ ระบบ SHALL เขียน `crm_tasks` 1 แถว (`id` =
`crypto.randomUUID()`, `status` = `"pending"`, `completedAt` = null,
`createdAt` เป็น ISO string) พร้อมแถวใน `task_links` ทุกลิงก์ **ใน
`withTransaction` เดียวกัน** — สำเร็จทั้งชุดหรือไม่มีอะไรถูกเขียนเลย และเพราะ
`withTransaction` retry callback ได้ถึง 3 ครั้ง callback SHALL idempotent คือ
mint UUID ไว้ **ภายใน** callback งานที่บันทึกแล้ว SHALL ปรากฏบนกระดานทันที
โดยไม่ต้อง reload หน้า และ SHALL ค้างอยู่จนกว่าจะถูกกด "สำเร็จ" เท่านั้น
ไม่มีการหมดอายุหรือลบตัวเองตามเวลาใดๆ

ค่าที่รับเข้ามาทุกช่อง SHALL ผ่าน `sanitizePlainText` ก่อนบันทึก, `dueDate`
SHALL เป็นสตริง `YYYY-MM-DD` เท่านั้น และทุก route SHALL เป็น
`withRoute("<ข้อความ fallback ภาษาไทย>", handler)` + `await requireAuth()`

#### Scenario: สร้างงานแบบสั้นที่สุด
- **WHEN** admin เลือกหัวข้อ "📞 โทรหาลูกค้า" พิมพ์ชื่องาน แล้วกดบันทึก
  โดยไม่กรอกรายละเอียด ไม่ใส่วันครบกำหนด และไม่ผูกลิงก์ใดเลย
- **THEN** งานถูกบันทึกสำเร็จ (`dueDate` เป็น null, `status` = `"pending"`)
  และการ์ดของงานนั้นปรากฏบนกระดานทันทีโดยไม่ต้อง reload

#### Scenario: ไม่ได้พิมพ์ชื่องาน
- **WHEN** admin กดบันทึกโดยที่ช่องชื่องานว่าง หรือมีแต่ช่องว่าง/แท็ก HTML
  ที่เหลือค่าว่างหลัง `sanitizePlainText`
- **THEN** API ตอบ 400 พร้อมข้อความภาษาไทยว่าต้องระบุชื่องาน และไม่มีแถวใน
  `crm_tasks` หรือ `task_links` ถูกเขียนเลย

#### Scenario: หัวข้อที่ส่งมาไม่มีอยู่จริงหรือถูกซ่อนไปแล้ว
- **WHEN** payload มี `topicId` ที่ไม่มีในตาราง `task_topics` หรือมีอยู่แต่
  `isActive` = false (เช่นแท็บเปิดค้างไว้ก่อนที่ admin จะซ่อนหัวข้อนั้น)
- **THEN** API ตอบ 400 พร้อมบอกว่าหัวข้อนี้ใช้ไม่ได้แล้ว ไม่มีการเขียนข้อมูล
  และ **ไม่** สร้างหัวข้อขึ้นมาเองอัตโนมัติ

#### Scenario: รูปแบบวันครบกำหนดไม่ถูกต้อง
- **WHEN** `dueDate` ที่ส่งมาไม่ใช่ `YYYY-MM-DD` (เช่น `"31/12/2569"` หรือ
  ISO timestamp เต็ม)
- **THEN** API ตอบ 400 และไม่มีการเขียนข้อมูล — ห้ามบันทึกค่าที่เทียบกับ
  คอลัมน์ VARCHAR วันที่แบบ lexical ไม่ได้

#### Scenario: เขียนลิงก์ล้มเหลวกลางทาง
- **WHEN** งานถูกสร้างพร้อมลิงก์ 3 รายการ แล้วการ insert ลิงก์รายการที่ 3
  ล้มเหลว (DB error)
- **THEN** ไม่มีแถวใน `crm_tasks` และ `task_links` ถูกเขียนเลย และกระดานยังคง
  แสดงรายการเดิมตามปกติ

#### Scenario: transaction ถูก retry
- **WHEN** `withTransaction` retry callback เพราะ connection หลุดชั่วคราว
- **THEN** ผลลัพธ์สุดท้ายคืองานเพียง 1 แถว (id ถูกสร้างใหม่ภายใน callback
  ทุกรอบ) ไม่เกิดงานซ้ำจากรอบที่ถูกยกเลิกไป

#### Scenario: Guest เรียก route ของกระดานงาน
- **WHEN** ผู้ที่ไม่ได้ login เรียก route สร้าง/อ่าน/แก้ไขงานหรือหัวข้อ
- **THEN** ได้ 401 Unauthorized และไม่มีข้อมูลลูกค้า/งานรั่วออกไป

### Requirement: หัวข้องานเป็นข้อมูลในตาราง ไม่ใช่ enum — เพิ่ม แก้ชื่อ เปลี่ยนสี และจัดลำดับได้
หัวข้อของงาน SHALL เก็บในตาราง `task_topics` (`id` INT PK, `name`, `icon`,
`color`, `sortOrder`, `isActive`, `createdAt`) — **ห้ามฝังเป็น enum หรือค่าคงที่
ในโค้ด** เพราะเจ้าของระบบต้องเพิ่มหัวข้อเองได้ในอนาคต (D3) ตอน bootstrap ระบบ
SHALL seed หัวข้อเริ่มต้น 5 รายการ: 📞 โทรหาลูกค้า, 🚗 นัดเข้าไปหาลูกค้า,
📄 รอทำใบเสนอราคา, 🔧 นัดเข้า Service, 📌 อื่นๆ — การ seed SHALL ทำ **ครั้ง
เดียวเมื่อตารางยังว่าง** เท่านั้น เพื่อไม่ให้หัวข้อที่ admin เปลี่ยนชื่อ ซ่อน
หรือลบไปแล้ว ถูกใส่กลับคืนมาเงียบๆ ในการ deploy ครั้งถัดไป

admin SHALL เพิ่มหัวข้อใหม่, แก้ชื่อ, เปลี่ยน icon (emoji), เปลี่ยนสี และ
จัดลำดับ (`sortOrder`) ได้ทุกเมื่อ โดย:
- `color` SHALL เก็บเป็น **token จากชุดสีที่กำหนดไว้** (เช่น `"blue"`,
  `"amber"`) ไม่ใช่ CSS/hex ดิบจากผู้ใช้ และ token ที่ไม่รู้จัก SHALL ถูก
  render ด้วยสีกลาง — ห้ามนำค่าจาก DB ไปต่อเป็น class/style โดยตรง
- การ **แก้ชื่อ/สี/icon SHALL ไม่แตะแถวใน `crm_tasks` เลย** เพราะงานอ้างถึง
  `topicId` ไม่ใช่ชื่อ — งานเดิมทุกใบ (รวมงานที่ปิดไปแล้ว) แสดงชื่อใหม่ทันที
- การจัดลำดับหลายแถว SHALL เขียนใน `withTransaction` เดียว (all-or-nothing)
- `id` SHALL ถูกจองแบบ `MAX(id)+1` แล้ว insert พร้อม **retry เมื่อชน
  duplicate key** ตามแบบ `addCategory` ใน `app/lib/productStore.ts`
- ชื่อหัวข้อ SHALL ผ่าน `sanitizePlainText` และห้ามว่าง

#### Scenario: ระบบใหม่ยังไม่มีหัวข้อเลย
- **WHEN** DB ถูก bootstrap ครั้งแรกหลังการเปลี่ยนแปลงนี้
- **THEN** `task_topics` มี 5 แถวตามค่าเริ่มต้น เรียงตาม `sortOrder` และ
  `isActive` = true ทุกแถว

#### Scenario: deploy ซ้ำหลังจาก admin แก้หัวข้อไปแล้ว
- **WHEN** admin เปลี่ยนชื่อ "📌 อื่นๆ" เป็น "📌 งานจิปาถะ" และซ่อนหัวข้อ
  "🚗 นัดเข้าไปหาลูกค้า" ไปแล้ว จากนั้นระบบถูก deploy/bootstrap อีกครั้ง
- **THEN** ชื่อที่แก้ไว้ยังเป็น "📌 งานจิปาถะ", หัวข้อที่ซ่อนยังซ่อนอยู่ และ
  **ไม่มี** หัวข้อเริ่มต้นถูก insert ซ้ำเข้ามา

#### Scenario: สองแท็บเพิ่มหัวข้อพร้อมกัน (id ชนกัน)
- **WHEN** admin เปิด 2 แท็บแล้วกดเพิ่มหัวข้อพร้อมกัน ทั้งคู่อ่าน
  `MAX(id)` ได้ค่าเดียวกันจึงคำนวณ id ถัดไปตรงกัน
- **THEN** ฝ่ายที่แพ้ได้ duplicate-key แล้ว **retry ด้วย `MAX(id)` ที่อ่านใหม่**
  จนสำเร็จ — สุดท้ายมีหัวข้อใหม่ครบ **2 แถว** คนละ id ไม่มีแถวใดถูกเขียนทับ
  และไม่มี request ใดล้มเหลว

#### Scenario: retry จนครบจำนวนครั้งแล้วยังไม่สำเร็จ
- **WHEN** การจอง id ชนซ้ำจนครบจำนวนครั้งที่กำหนด
- **THEN** API ตอบ error พร้อมข้อความภาษาไทย และไม่มีหัวข้อครึ่งๆ กลางๆ
  ถูกสร้างขึ้น

#### Scenario: เปลี่ยนชื่อหัวข้อที่มีงานผูกอยู่
- **WHEN** หัวข้อ "📄 รอทำใบเสนอราคา" มีงานค้าง 4 ใบและงานที่ปิดแล้ว 10 ใบ
  แล้ว admin เปลี่ยนชื่อเป็น "📄 ค้างทำใบเสนอราคา" และเปลี่ยนสี
- **THEN** งานทั้ง 14 ใบยังผูกกับ `topicId` เดิม และแสดงชื่อ/สีใหม่ทันที
  โดยไม่มีการ UPDATE แถวใดใน `crm_tasks`

#### Scenario: ส่งค่าสีที่ไม่รู้จักมา
- **WHEN** `color` ที่ส่งมาไม่อยู่ในชุด token ที่กำหนด (เช่น CSS ดิบ)
- **THEN** ระบบปฏิเสธค่านั้น หรือเก็บ/แสดงเป็นสีกลาง — และไม่มีสตริงจากผู้ใช้
  ถูกนำไปใส่ใน style/class ที่ render ออกหน้าเว็บ

### Requirement: ซ่อนหัวข้อได้โดยงานใต้หัวข้อนั้นต้องไม่หายไป และหัวข้อที่มีงานอยู่ห้ามลบ
การเลิกใช้หัวข้อ SHALL ทำด้วยการ **ซ่อน** (`isActive` = false) ไม่ใช่การลบ
หัวข้อที่ถูกซ่อน SHALL หายไปจาก dropdown ตอนสร้าง/แก้งานเท่านั้น ส่วน
**งานทุกใบที่อยู่ใต้หัวข้อนั้น SHALL ยังคงอยู่ครบและยังเห็นบนกระดานเหมือนเดิม**
(ทั้งในมุมมอง "ทั้งหมด" และยังถูกนับในกระดิ่งตามกฎเดิม) หัวข้อที่ถูกซ่อนแต่
**ยังมีงานค้างอยู่** SHALL ยังปรากฏในตัวกรองพร้อมป้าย "(ซ่อนแล้ว)" เพื่อไม่ให้
มีงานที่กรองเข้าไปดูไม่ได้ และ admin SHALL เปิดหัวข้อกลับมาใช้ (unhide) ได้

การ **ลบ** หัวข้อ SHALL ถูกปฏิเสธเมื่อยังมีแถวใน `crm_tasks` อ้างถึงหัวข้อนั้น
ไม่ว่าจะ `pending` หรือ `done` โดยตอบ 400 พร้อมแนะนำให้ "ซ่อน" แทน — เหตุผลคือ
`topicId` เป็น soft reference ที่ไม่มี FK การลบจะทำให้งานเก่ากลายเป็นกำพร้าและ
ประวัติหายไปเงียบๆ ซึ่งขัดกับกฎของโปรเจกต์ที่ห้ามลบข้อมูลอัตโนมัติ และเป็น
guard แบบเดียวกับการห้ามลบลูกค้าที่ยังมีอุปกรณ์ผูกอยู่ (`crm-data-integrity`)
หัวข้อที่ **ไม่มีงานอ้างถึงเลย** SHALL ลบได้จริง เพราะไม่มีข้อมูลใดสูญหาย
ทั้งนี้ระบบ SHALL ทนต่อกรณีที่ `topicId` หาแถวหัวข้อไม่เจอ (เช่นถูกแก้ DB
ตรงๆ) ด้วยการแสดงงานนั้นภายใต้ "ไม่ระบุหัวข้อ" — ห้าม crash และห้ามซ่อนงานทิ้ง

#### Scenario: ซ่อนหัวข้อที่ยังมีงานค้าง
- **WHEN** หัวข้อ "🔧 นัดเข้า Service" มีงานค้าง 3 ใบ แล้ว admin กดซ่อน
- **THEN** งานทั้ง 3 ใบยังอยู่บนกระดานภายใต้มุมมอง "ทั้งหมด" ครบถ้วน,
  ตัวกรองยังมีหัวข้อนี้พร้อมป้าย "(ซ่อนแล้ว)" แต่ dropdown ตอนสร้างงานใหม่
  ไม่มีหัวข้อนี้ให้เลือกแล้ว

#### Scenario: ซ่อนหัวข้อที่ไม่มีงานค้างเหลืออยู่
- **WHEN** หัวข้อที่ถูกซ่อนมีแต่งานที่ปิดไปแล้ว (ไม่มีงาน `pending`)
- **THEN** หัวข้อนั้นไม่รกอยู่ในตัวกรองของกระดานงานค้าง แต่ยังใช้แสดงชื่อ
  หัวข้อของงานที่ปิดแล้วในรายการงานสำเร็จได้ตามปกติ

#### Scenario: พยายามลบหัวข้อที่มีงานอ้างถึง
- **WHEN** admin กดลบหัวข้อที่มีงาน (pending หรือ done ก็ตาม) อ้างถึงอยู่
- **THEN** API ตอบ 400 พร้อมข้อความทำนอง "หัวข้อนี้มีงานอยู่ ไม่สามารถลบได้
  กรุณาซ่อนแทน" และไม่มีแถวใดถูกลบทั้งใน `task_topics` และ `crm_tasks`

#### Scenario: ลบหัวข้อที่ยังไม่เคยถูกใช้
- **WHEN** admin เพิ่มหัวข้อผิด แล้วกดลบทันทีก่อนสร้างงานใดๆ ใต้หัวข้อนั้น
- **THEN** หัวข้อถูกลบจริง และไม่มีงานใดได้รับผลกระทบ

#### Scenario: เปิดหัวข้อที่ซ่อนไว้กลับมาใช้
- **WHEN** admin กดเลิกซ่อนหัวข้อ
- **THEN** หัวข้อกลับมาอยู่ใน dropdown สร้างงานตามลำดับ `sortOrder` เดิม และ
  ป้าย "(ซ่อนแล้ว)" ในตัวกรองหายไป

#### Scenario: งานที่ชี้ไปยังหัวข้อที่ไม่มีอยู่แล้ว
- **WHEN** แถวใน `crm_tasks` มี `topicId` ที่ไม่มีแถวใน `task_topics` (ข้อมูล
  ถูกแก้จากนอกระบบ)
- **THEN** กระดานยังโหลดได้ปกติ งานนั้นแสดงภายใต้ "ไม่ระบุหัวข้อ" และ admin
  ยังกดปิดงานหรือย้ายไปหัวข้ออื่นได้ — ไม่มี error หน้าจอขาว

### Requirement: กรองกระดานตามหัวข้อได้ รวมตัวเลือก "ทั้งหมด" และการกรองเป็นเรื่องของการมองเท่านั้น
กระดานงาน SHALL มีตัวกรองตามหัวข้อ โดยมีตัวเลือก **"ทั้งหมด" เป็นค่าเริ่มต้น**
และมีหัวข้อที่ `isActive` ทุกหัวข้อ บวกหัวข้อที่ซ่อนแล้วแต่ยังมีงานค้าง
ตัวกรอง SHALL เป็น **มุมมองล้วนๆ**: SHALL ไม่เขียน ไม่แก้ ไม่ลบข้อมูลใดๆ,
SHALL ไม่เปลี่ยนตัวเลขบนกระดิ่ง, และ SHALL ไม่ทำให้งานหายถาวร — เปลี่ยนกลับไป
"ทั้งหมด" ต้องเห็นงานครบเท่าเดิมเสมอ ตัวเลือกที่กรองอยู่ SHALL แสดงจำนวนงาน
ค้างของแต่ละหัวข้อ และเมื่อกรองแล้วไม่พบงานเลย SHALL แสดงข้อความว่าง
ที่บอกชัดว่ากำลังกรองหัวข้อไหนอยู่ พร้อมทางกลับไป "ทั้งหมด"

ถ้า admin สร้างงานในหัวข้อที่ **ไม่ตรง** กับตัวกรองที่เปิดอยู่ ระบบ SHALL ไม่
ปล่อยให้งานที่เพิ่งสร้างหายไปเงียบๆ — SHALL แจ้งให้เห็นว่าไปอยู่หัวข้อใด
(หรือสลับมุมมองไปยังหัวข้อนั้น/"ทั้งหมด" ให้)

#### Scenario: กรองไปยังหัวข้อเดียว
- **WHEN** กระดานมีงานค้าง 8 ใบจาก 3 หัวข้อ แล้ว admin เลือกกรอง
  "📞 โทรหาลูกค้า" ซึ่งมี 3 ใบ
- **THEN** เห็นเฉพาะ 3 ใบนั้น, ตัวเลขบนกระดิ่งไม่เปลี่ยน และเมื่อกลับไป
  "ทั้งหมด" เห็นครบ 8 ใบเหมือนเดิม

#### Scenario: กรองแล้วไม่มีงานในหัวข้อนั้น
- **WHEN** admin กรองหัวข้อที่ไม่มีงานค้างเลย
- **THEN** เห็นข้อความทำนอง "ไม่มีงานค้างในหัวข้อ «<ชื่อหัวข้อ>»" พร้อมปุ่มกลับ
  ไป "ทั้งหมด" — ไม่ใช่หน้าว่างเปล่าที่ทำให้เข้าใจผิดว่าไม่มีงานเลยทั้งกระดาน

#### Scenario: สร้างงานคนละหัวข้อกับที่กรองอยู่
- **WHEN** admin กรองอยู่ที่ "🔧 นัดเข้า Service" แล้วสร้างงานใหม่ในหัวข้อ
  "📄 รอทำใบเสนอราคา"
- **THEN** งานถูกบันทึกเรียบร้อย และระบบแจ้ง/สลับมุมมองให้เห็นงานที่เพิ่งสร้าง
  — ห้ามบันทึกแล้วจอเงียบจนดูเหมือนกดบันทึกไม่ติด

#### Scenario: การกรองไม่ใช่การลบ
- **WHEN** admin กรองหัวข้อหนึ่งไว้ ปิดเบราว์เซอร์ แล้วเปิด `/crm/alerts`
  ใหม่ในวันถัดไป
- **THEN** งานทุกหัวข้อยังอยู่ครบในฐานข้อมูล และกระดานกลับมาเริ่มที่มุมมอง
  "ทั้งหมด" ตามค่าเริ่มต้น

### Requirement: ผูกงานเข้ากับลูกค้า เครื่องจักร ใบเสนอราคา และเอกสารได้ไม่จำกัดจำนวน พร้อมเก็บ label snapshot
งาน 1 ใบ SHALL ผูกลิงก์ได้ **กี่รายการก็ได้** ข้าม 4 ประเภท: `customer`,
`equipment`, `quotation`, `document` (D4) โดยเก็บใน `task_links` ที่มี
PRIMARY KEY `(taskId, targetType, targetId)` + INDEX `(targetType, targetId)`
ตามแบบ polymorphic key ของ `alert_snoozes` ลิงก์ SHALL เป็น **soft link**
(คอลัมน์ `targetId` VARCHAR(255) มี index แต่ **ไม่มี FOREIGN KEY**) ตามแบบ
`sales_records.quotationId` และ `customer_equipments.salesRecordId` เพราะ
ปลายทางบางชนิดถูกลบ/purge ได้อิสระ

ทุกลิงก์ SHALL เก็บ `label` เป็น **snapshot ณ เวลาที่ผูก** (ชื่อลูกค้า,
ชื่อสินค้า+serial ของเครื่อง, `docNo` ของใบเสนอราคา, ชื่อเอกสาร) เพื่อให้ชิป
ยังอ่านรู้เรื่องแม้ปลายทางจะหายไปแล้ว การแสดงผล SHALL ใช้ **ค่าปัจจุบันของ
ปลายทางเมื่อยังหาเจอ** (ชื่อที่ถูกแก้ภายหลังจึงสะท้อนทันที) และ **ตกกลับไปใช้
snapshot เมื่อหาปลายทางไม่เจอ** เท่านั้น

`targetId` ของใบเสนอราคา SHALL ใช้ `quotations.id` (id ที่เสถียร) **ห้ามใช้
`docNo`** เพราะ `docNo` แก้ได้เองและเปลี่ยนเมื่อ clone จึงไม่ปลอดภัยที่จะเป็น
เป้าลิงก์ ลิงก์ SHALL เพิ่ม/ลบออกจากงานที่มีอยู่แล้วได้ภายหลัง และการลบลิงก์
SHALL ลบเฉพาะแถวใน `task_links` — **ห้ามแตะข้อมูลปลายทางเด็ดขาด**

#### Scenario: งานเดียวผูกหลายปลายทางหลายประเภท
- **WHEN** admin สร้างงาน "ตามใบเสนอราคาโรงพยาบาล A" แล้วผูกลูกค้า 2 คน,
  เครื่อง 1 เครื่อง, ใบเสนอราคา 1 ใบ และเอกสาร 1 ใบ
- **THEN** `task_links` มี 5 แถวของ `taskId` เดียวกัน และการ์ดของงานแสดงชิป
  ครบทั้ง 5 อัน แยกให้เห็นว่าเป็นคนละประเภทกัน

#### Scenario: ผูกปลายทางเดิมซ้ำ
- **WHEN** admin เผลอเลือกลูกค้าคนเดิมผูกเข้างานเดิมอีกครั้ง
- **THEN** ยังมีลิงก์เพียงแถวเดียว (PRIMARY KEY กันซ้ำอยู่แล้ว) โดย API ไม่ตอบ
  error ให้ผู้ใช้เห็น และไม่มีชิปซ้ำบนการ์ด

#### Scenario: ปลายทางถูกเปลี่ยนชื่อภายหลัง
- **WHEN** ลูกค้าที่ผูกไว้ถูกแก้ชื่อในหน้า `/customers` หลังจากผูกลิงก์แล้ว
- **THEN** ชิปแสดงชื่อ **ปัจจุบัน** ของลูกค้ารายนั้น (ไม่ใช่ snapshot เก่า)
  ส่วนคอลัมน์ `label` ใน DB ยังเก็บค่า snapshot เดิมไว้เป็น fallback

#### Scenario: ผูกใบเสนอราคาด้วย id ไม่ใช่เลขที่เอกสาร
- **WHEN** admin ผูกใบเสนอราคา แล้วภายหลังมีคนแก้ `docNo` ของใบนั้น
- **THEN** ลิงก์ยังชี้ไปยังใบเดิมได้ถูกต้อง (เพราะเก็บ `quotations.id`) และชิป
  แสดงเลขที่เอกสารใหม่

#### Scenario: ลบลิงก์ออกจากงาน
- **WHEN** admin กดลบชิปเครื่องจักรออกจากงาน
- **THEN** แถวใน `task_links` แถวนั้นหายไปแถวเดียว ส่วนแถวใน
  `customer_equipments` ของเครื่องนั้นยังอยู่ครบ ไม่ถูกแตะต้อง

### Requirement: ชิปลิงก์ต้องพาไปยังปลายทางได้จริง และปลายทางที่ถูกลบต้องขึ้น "ถูกลบแล้ว" โดยไม่พังและไม่ 404
ชิปแต่ละอันบนการ์ดงาน SHALL พาไปยังปลายทางของมันได้ในคลิกเดียว:
- `quotation` → นำทางไป `/quotation?id=<quotations.id>&view=1` (เปิดแบบอ่าน
  อย่างเดียว)
- `document` → นำทางไป `/document/<documents.id>`
- `customer` → SHALL เปิด `CustomerDetailsModal` **ในหน้าเดิม** (ไม่นำทางออก
  จาก `/crm/alerts`, ไม่เปลี่ยน URL) — component และกลไกดึงข้อมูลเดียวกันกับ
  ที่ปุ่ม "แก้ไข" บนการ์ดนัดโทรลูกค้าใช้อยู่แล้ว (`open-customer-profile-
  in-place`)
- `equipment` → SHALL เปิด `EquipmentDetailsModal` **ในหน้าเดิม** เช่นกัน —
  component เดียวกับที่การ์ด "กำหนดการ" ที่ผูกเครื่องใช้อยู่แล้ว

`customer`/`equipment` SHALL ใช้ฟังก์ชันโหลด-แล้ว-เปิด modal ตัวเดียวกันกับที่
ปุ่ม "แก้ไข" ของการ์ดแจ้งเตือนใช้ — SHALL ไม่มีโค้ด fetch+เปิด modal ชุดที่สอง
สำหรับชิปโดยเฉพาะ เมื่อโฮสต์ที่ render ชิป (`TaskBoardSection`) ไม่ได้รับ
ฟังก์ชันเปิด modal มา (ไม่มี caller ส่งมาให้) ชิปทั้งสองประเภท SHALL ตกกลับไป
นำทางด้วย `<Link href>` แบบเดิม แทนที่จะเป็นปุ่มที่กดแล้วไม่มีอะไรเกิดขึ้น

เนื่องจากปัจจุบัน `app/customers/page.tsx` **ไม่รับ URL parameter ใดเลย** —
ทั้งแท็บที่เปิดอยู่ (`activeTab`) และลูกค้า/เครื่องที่กำลังดูรายละเอียด เป็น
state ภายในคอมโพเนนต์ล้วนๆ — หน้านั้น SHALL ยังคงรับพารามิเตอร์เพื่อ
deep-link ไปยังแท็บและลูกค้า/เครื่องที่ระบุได้เหมือนเดิม (สำหรับผู้ที่เข้าหน้า
`/customers` ตรงๆ) และพารามิเตอร์ที่ชี้ไปยังของที่ไม่มีอยู่แล้ว SHALL ไม่ทำให้
หน้าพัง — การเปลี่ยนแปลงนี้ไม่แตะกลไก deep-link ของหน้านั้นเลย เพียงแค่กระดาน
งานเลือกเปิด modal ในที่เดิมแทนการนำทางไปที่นั่น

ก่อนแสดงผล ระบบ SHALL ตรวจว่าปลายทางแต่ละอัน **ยังมีอยู่จริงหรือไม่** (คิวรี่
เป็นชุดเดียวต่อประเภท ไม่ยิงทีละชิป) ชิปที่หาปลายทางไม่เจอ SHALL แสดง label
snapshot พร้อมป้าย **"ถูกลบแล้ว"** ในสไตล์ที่ดูไม่กดได้ (disabled) และ
**SHALL ไม่นำทางหรือเปิด modal ใดๆ เลย** — งานนั้น SHALL ยังใช้งานได้ครบ
(กดสำเร็จ/แก้ไข/ลบลิงก์ที่ตายแล้วออกได้) และระบบ SHALL **ไม่ลบแถว
`task_links` ที่ตายแล้วให้อัตโนมัติ** เพราะ label ที่ค้างไว้คือหลักฐานเดียวที่
บอกว่างานนี้เคยอ้างถึงอะไร

#### Scenario: กดชิปใบเสนอราคาที่ยังอยู่
- **WHEN** admin กดชิปใบเสนอราคาบนการ์ดงาน
- **THEN** เปิด `/quotation?id=<id>&view=1` และเห็นใบนั้นแบบอ่านอย่างเดียว

#### Scenario: กดชิปเอกสารที่ยังอยู่
- **WHEN** admin กดชิปเอกสาร
- **THEN** เปิด `/document/<id>` ของเอกสารนั้น

#### Scenario: ใบเสนอราคาถูก purge ไปแล้วตาม retention 2 ปี
- **WHEN** งานถูกสร้างไว้เมื่อ 2 ปีก่อนพร้อมลิงก์ใบเสนอราคา แล้ว cron ลบใบ
  เสนอราคานั้นทิ้งตาม retention
- **THEN** งานยังอยู่บนกระดานครบ ชิปนั้นแสดง label เดิม (เช่น
  "QT-2568-001") ต่อท้ายด้วย "ถูกลบแล้ว" กดไม่ได้ ไม่นำทางไปไหน และไม่มี
  request ไปยัง `/quotation?id=...` ที่จะได้หน้าเปล่า

#### Scenario: deep-link ไปยังลูกค้าที่ยังอยู่
- **WHEN** admin กดชิปลูกค้าบนการ์ดงาน ขณะอยู่ที่ `/crm/alerts`
- **THEN** `CustomerDetailsModal` ของลูกค้ารายนั้นเปิดขึ้นทับหน้าเดิม — URL
  ยังเป็น `/crm/alerts` ไม่เปลี่ยนไปเป็น `/customers` ปิด modal แล้วต้องเห็น
  กระดานงานเดิมทันที

#### Scenario: กดชิปเครื่องจักรที่ยังอยู่ — เปิดในหน้าเดิม ไม่นำทางออก
- **WHEN** admin กดชิปเครื่องจักรบนการ์ดงาน
- **THEN** `EquipmentDetailsModal` ของเครื่องนั้นเปิดขึ้นทับหน้าเดิมเช่นกัน
  ไม่นำทางออกจาก `/crm/alerts`

#### Scenario: ลูกค้าหรือเครื่องจักรถูกลบไปแล้ว
- **WHEN** ปลายทางประเภท `customer` หรือ `equipment` ไม่มีแถวอยู่แล้ว
- **THEN** ชิปแสดง snapshot + "ถูกลบแล้ว" แบบกดไม่ได้เช่นเดียวกัน (ไม่เปิด
  modal เปล่า ไม่มี request ไปหาข้อมูลที่ไม่มีอยู่) และงานยังกดปิดเป็นสำเร็จ
  ได้ตามปกติ

#### Scenario: งานที่ทุกลิงก์ตายหมดแล้ว
- **WHEN** ปลายทางทั้งหมดของงานหนึ่งถูกลบไปหมด
- **THEN** การ์ดงานยังแสดงหัวข้อ ชื่องาน รายละเอียด และวันครบกำหนดตามปกติ
  โดยมีชิป "ถูกลบแล้ว" เรียงอยู่ — ไม่มี error และไม่มีการซ่อนงานทิ้ง

### Requirement: ปิดงานเป็น "สำเร็จ" แล้วงานต้องออกจากกระดานแต่ไม่ถูกลบ และเปิดกลับมาได้
การกด "สำเร็จ" SHALL ตั้ง `status` = `"done"` และ `completedAt` เป็นเวลาปัจจุบัน
เท่านั้น — **SHALL ไม่ DELETE แถวใดๆ** ทั้งใน `crm_tasks` และ `task_links`
งานที่ปิดแล้ว SHALL หายจากกระดานงานค้าง (และจากการนับของกระดิ่ง) แต่ SHALL ยัง
ดูย้อนหลังได้เสมอในมุมมอง "งานที่ทำแล้ว" บน `/crm/alerts` พร้อมวันที่ปิดงาน
โดยลิงก์ทุกอันของงานนั้นยังอยู่ครบ admin SHALL กด "เปิดงานใหม่" ได้ ซึ่ง
SHALL ตั้ง `status` กลับเป็น `"pending"` และล้าง `completedAt` แล้วงานกลับมา
อยู่บนกระดานตามหัวข้อและวันครบกำหนดเดิม ระบบ SHALL **ไม่ลบงานที่ปิดแล้วโดย
อัตโนมัติ** ไม่ว่าจะผ่านไปนานเท่าใด (กฎของโปรเจกต์: ห้ามลบข้อมูลอัตโนมัติ)
การลบงานถาวร SHALL ทำได้เฉพาะเมื่อ admin สั่งเอง และ SHALL ถามยืนยันก่อนเสมอ

#### Scenario: กดสำเร็จ
- **WHEN** admin กด "สำเร็จ" บนงานที่ค้างอยู่
- **THEN** งานหายจากกระดานงานค้างทันที, แถวยังอยู่ใน DB โดย `status` = `"done"`
  และมี `completedAt` และตัวเลขบนกระดิ่งลดลงถ้างานนั้นเคยถูกนับอยู่

#### Scenario: ดูงานที่ทำไปแล้ว
- **WHEN** admin เปิดมุมมอง "งานที่ทำแล้ว"
- **THEN** เห็นงานที่ปิดไปเรียงตามวันที่ปิดล่าสุดก่อน พร้อมหัวข้อ ชื่องาน
  และชิปลิงก์ครบเหมือนตอนที่ยังค้างอยู่

#### Scenario: กดสำเร็จผิดใบแล้วเปิดกลับ
- **WHEN** admin กดสำเร็จผิดใบ แล้วกด "เปิดงานใหม่"
- **THEN** งานกลับมาอยู่บนกระดานพร้อมหัวข้อ รายละเอียด วันครบกำหนดและลิงก์เดิม
  ครบทุกอย่าง (`completedAt` ถูกล้าง) ไม่มีข้อมูลใดสูญหาย

#### Scenario: กดสำเร็จซ้ำจากแท็บที่เปิดค้าง
- **WHEN** งานถูกปิดไปแล้ว แล้วอีกแท็บหนึ่งกด "สำเร็จ" ของงานเดิมอีกครั้ง
- **THEN** ผลลัพธ์คงเดิม (ยังเป็น `done` ใบเดียว) ไม่มี error หน้าจอ และ
  `completedAt` ไม่ถูกเขียนซ้ำจนประวัติเพี้ยน

#### Scenario: ลบงานถาวร
- **WHEN** admin กดลบงานทิ้ง
- **THEN** ระบบถาม dialog ยืนยันก่อนเสมอ และเมื่อยืนยันจึงลบแถวใน `crm_tasks`
  พร้อมแถวใน `task_links` ของงานนั้น โดยไม่แตะข้อมูลลูกค้า/เครื่อง/ใบเสนอราคา/
  เอกสารที่เคยผูกไว้เลย

### Requirement: กระดิ่งนับเฉพาะงานที่ยังค้างและถึงกำหนดแล้วเท่านั้น
งานบนกระดาน SHALL ถูกนับรวมในตัวเลขของ `GlobalAdminBell` **ก็ต่อเมื่อเข้า
เงื่อนไขครบทั้งสองข้อ** เท่านั้น (D6):
1. `status` = `"pending"` และ
2. `dueDate` ไม่ว่าง **และ** `dueDate <= วันนี้`

"วันนี้" SHALL คำนวณเป็น **วันตามปฏิทิน Asia/Bangkok** ด้วย
`bangkokDateString(new Date())` จาก `app/lib/dateFormat.ts` — **ห้ามใช้วันที่
UTC ของเซิร์ฟเวอร์** (Vercel รันที่ UTC ซึ่งช่วง 00:00–06:59 เวลาไทยจะยังเป็น
"เมื่อวาน" ทำให้งานถึงกำหนดไม่ถูกนับนานถึง 7 ชั่วโมงทุกวัน) การเทียบ SHALL
เป็นการเทียบสตริง `YYYY-MM-DD` แบบ lexical เช่นเดียวกับ `getAlerts()`

งานที่ **ไม่มี `dueDate`** SHALL ไม่ถูกนับเลยไม่ว่าจะสร้างไว้นานแค่ไหน และงาน
ที่ครบกำหนดในอนาคต SHALL ยังไม่ถูกนับ — เจตนาคือกระดิ่งมีไว้บอกว่า "ต้องทำ
ตอนนี้" ไม่ใช่ให้ to-do list มาทำให้ตัวเลขเฟ้อ จำนวนนี้ SHALL ถูกส่งออกมาจาก
`/api/admin/alerts` เป็น **ฟิลด์ของตัวเอง** ชื่อ `dueTaskCount`
แล้วบวกเข้ากับผลรวมเดิมของกระดิ่ง
และ SHALL เป็นตัวเลขเดียวกันกับที่ป้ายจำนวนของกระดานงานบน `/crm/alerts` แสดง

### Requirement: กระดานงานต้องแยกให้เห็นชัดจากการแจ้งเตือนอัตโนมัติบนหน้าเดียวกัน

อัตโนมัติของ `getAlerts()` บน `/crm/alerts` โดยสิ้นเชิง เพราะมันคือโน้ตที่
admin เขียนเตือนตัวเอง ไม่ใช่สิ่งที่ระบบตรวจพบ (D2) โดยเฉพาะ:

  บล็อกแยกท้ายหน้าแบบเดิม — `/crm/alerts` SHALL มีเพียงปุ่ม/การ์ดลิงก์ไปยัง
  `/crm/tasks` แทน (ดู requirement ใหม่ใน `crm-alert-surface`)
- `/crm/alerts` SHALL **ไม่ยิง request** ไปยัง `/api/admin/tasks` หรือ
  `/api/admin/task-topics` อีกต่อไป — ข้อมูลกระดานงานถูกโหลดที่ `/crm/tasks`
  เท่านั้น
- ในหน้า `/crm/tasks` การ์ดงานที่บันทึกเอง SHALL แสดงเป็นเนื้อหาหลักของหน้า
  ไม่ต้องแยกจากอะไรอีก (ไม่มีการ์ดแจ้งเตือนอัตโนมัติบนหน้านี้ให้ปนกัน)
- การ์ดงานทุกใบ SHALL มีป้ายกำกับที่อ่านออกทันทีว่า **"บันทึกเอง"** (คงไว้
  แม้ย้ายหน้า เพื่อไม่ให้สับสนกับแจ้งเตือนอัตโนมัติที่เคยอยู่ข้างๆ กัน)
- ข้อความบนการ์ดงาน SHALL ไม่ใช้ถ้อยคำที่ทำให้เข้าใจว่าระบบตรวจพบเอง (เช่น
  "ประกันใกล้หมด" / "ข้อมูลไม่ครบ") — ข้อความบนการ์ดคือสิ่งที่ admin พิมพ์เอง
- กระดานงาน SHALL ไม่มีปุ่ม "เลื่อนการแจ้งเตือน" (snooze) ของระบบเตือนอัตโนมัติ
  และ SHALL ไม่เขียนแถวใดลง `alert_snoozes`
- ชิปลิงก์ลูกค้า/เครื่องบนการ์ดงาน (`open-task-chip-targets-in-place`) SHALL
  ยังคงเปิด `CustomerDetailsModal`/`EquipmentDetailsModal` **ในหน้า
  `/crm/tasks` เอง** (ไม่นำทางออกจาก `/crm/tasks`, ไม่เปลี่ยนไป `/crm/alerts`
  หรือ `/customers`) — ใช้ฟังก์ชันโหลด-แล้ว-เปิด modal ตัวเดียวกันกับที่
  `/crm/alerts` ใช้สำหรับปุ่ม "แก้ไข" ของมันเอง (hook กลาง
  `useCustomerEquipmentDetails`) ไม่ใช่โค้ด fetch+เปิด modal ชุดที่สอง

### Requirement: ตารางของกระดานงานต้องเป็น soft link และต้อง bump SCHEMA_VERSION
การเปลี่ยนแปลงนี้ SHALL เพิ่มตาราง `task_topics`, `crm_tasks` และ `task_links`
ใน `app/lib/db.ts` และ SHALL **bump `SCHEMA_VERSION` จาก 34 เป็น 35** —
ตัวเลขนี้ SHALL เพิ่มขึ้นอย่างเดียวเท่านั้น เพราะการตรวจข้ามใช้เงื่อนไข
`stored >= SCHEMA_VERSION` การนำเลขที่เคยใช้แล้วกลับมาใช้ซ้ำจะทำให้ migration
ทั้งก้อนถูกข้ามไปเงียบๆ (เคยเกิดมาแล้วกับ v33)

ทุกคอลัมน์อ้างอิงของสามตารางนี้ (`crm_tasks.topicId`, `task_links.taskId`,
`task_links.targetId`) SHALL เป็น soft link: มี index/PK แต่ **ไม่มี FOREIGN
KEY และไม่มี ON DELETE CASCADE เลยแม้แต่ตัวเดียว** เพื่อให้ปลายทางถูกลบ/purge
ได้โดยที่งานไม่หายตามไปด้วย และเพื่อให้มีกติกาเดียวทั้งชุดตาราง ผลที่ตามมาคือ
การลบงาน SHALL ลบแถวใน `task_links` ของงานนั้น **ด้วยคำสั่งของตัวเองใน
`withTransaction` เดียวกัน** ไม่ใช่ปล่อยให้ FK cascade จัดการ การ bootstrap
SHALL idempotent (รันซ้ำแล้วไม่พัง ไม่สร้างซ้ำ) และ SHALL ไม่แก้หรือลบข้อมูลเดิม
ใดๆ ในตารางอื่น

### Requirement: หน้ารายละเอียดลูกค้า SHALL สร้างงานที่ผูกกับลูกค้าคนนั้นได้โดยตรง โดยไม่ต้องค้นหาซ้ำ

SHALL ไม่ต้องค้นหาลูกค้าคนเดิมซ้ำในตัวเลือกผูกลิงก์ของฟอร์มอีก

label ของลิงก์ที่ผูกให้อัตโนมัติ SHALL คำนวณด้วยฟังก์ชันเดียวกับที่ตัวเลือก

อุปกรณ์

เมื่อบันทึกงานสำเร็จ ระบบ SHALL ปิดฟอร์ม แสดง toast ยืนยัน และ**คงอยู่หน้า
รายละเอียดลูกค้าเดิม** — SHALL ไม่นำทางออกไปยัง `/crm/alerts` โดยอัตโนมัติ

งานที่สร้างจากปุ่มนี้ SHALL ปรากฏบนกระดาน "สิ่งที่ต้องทำ" ที่ `/crm/alerts`
เหมือนงานที่สร้างจากกระดานโดยตรงทุกประการ (แถวเดียวกันใน `crm_tasks` /
`task_links`) — SHALL ไม่มีตารางหรือเส้นทางข้อมูลแยกต่างหาก

#### Scenario: กดปุ่มจากหน้าลูกค้าคนหนึ่ง แล้วบันทึกงาน
- **WHEN** แอดมินเปิดรายละเอียดลูกค้า "คุณสมชาย (บริษัท ก)" แล้วกด
  "สร้างสิ่งที่ต้องทำ" กรอกหัวข้อ+ชื่องาน แล้วกดบันทึก
- **THEN** งานที่ถูกสร้างมีลิงก์ `{ targetType: "customer", targetId:
  <id ของคุณสมชาย> }` โดยไม่ต้องเลือกลูกค้าเองในฟอร์มเลย และงานนั้นปรากฏบน
  กระดานงานที่ `/crm/alerts` พร้อมชิปลิงก์ไปยังคุณสมชาย

#### Scenario: เปิดลูกค้าคนละคนกัน ต้องได้ลิงก์คนละอัน
- **WHEN** แอดมินเปิดฟอร์มจากลูกค้า A ปิดไปโดยไม่บันทึก แล้วเปิดลูกค้า B
  แล้วกด "สร้างสิ่งที่ต้องทำ" อีกครั้ง
- **THEN** ฟอร์มที่เปิดจากลูกค้า B มีลิงก์ผูกกับ B เท่านั้น ไม่มีลิงก์ของ A
  ค้างอยู่

#### Scenario: ถอดลิงก์ที่ผูกมาอัตโนมัติออกก่อนบันทึก
- **WHEN** แอดมินกดปุ่มจากหน้าลูกค้า แล้วกดลบชิปลิงก์ลูกค้าที่ผูกมาให้ก่อน
  กดบันทึก
- **THEN** งานที่ถูกสร้างไม่มีลิงก์ใดเลย (บันทึกได้ตามปกติ — ลิงก์เป็นเรื่อง
  optional ของงานอยู่แล้ว)

#### Scenario: แก้ไขงานเดิมที่มีลิงก์อื่นอยู่แล้ว ไม่ถูกลิงก์ลูกค้าแทรก
- **WHEN** แอดมินเปิดแก้ไขงานเดิมที่ผูกกับเครื่องจักรอยู่แล้ว (ไม่ใช่การสร้าง
  ใหม่จากปุ่มนี้)
- **THEN** ฟอร์มยังแสดงลิงก์เครื่องจักรเดิมเท่านั้น ไม่มีลิงก์ลูกค้าใดถูกเพิ่ม
  เข้ามาโดยไม่ได้ตั้งใจ

#### Scenario: หัวข้อโหลดไม่สำเร็จตอนกดปุ่มครั้งแรก
- **WHEN** `GET /api/admin/task-topics` ล้มเหลวตอนแอดมินกดปุ่มนี้เป็นครั้งแรก
  (ไม่ว่าจะกดจากฝั่งลูกค้าหรือฝั่งอุปกรณ์ก่อน)
- **THEN** ระบบแจ้งเตือนเป็นภาษาไทยและไม่เปิดฟอร์ม — ไม่เปิดฟอร์มที่ไม่มี
  หัวข้อให้เลือกเลย และครั้งถัดไปที่กดปุ่ม (ฝั่งไหนก็ได้) ระบบลองโหลดใหม่อีก
  ครั้ง ไม่ค้างอยู่ในสถานะล้มเหลวถาวร

#### Scenario: โหลดหัวข้อจากฝั่งหนึ่งแล้ว อีกฝั่งไม่ต้องโหลดซ้ำ
- **WHEN** แอดมินกดปุ่มนี้จากหน้า `/customers` จนหัวข้อโหลดสำเร็จแล้ว จากนั้น
  ไปที่ `/crm/alerts` แล้วกดปุ่ม "สร้างสิ่งที่ต้องทำ" บน `EquipmentDetailsModal`
- **THEN** ฟอร์มเปิดทันทีพร้อมรายชื่อหัวข้อที่มีอยู่แล้ว โดยไม่มีการยิง
  `GET /api/admin/task-topics` ซ้ำอีกครั้ง

### Requirement: หน้ารายละเอียดอุปกรณ์ SHALL สร้างงานที่ผูกกับเครื่องนั้นได้โดยตรง โดยไม่ต้องค้นหาซ้ำ

`EquipmentDetailsModal` SHALL มีปุ่ม "สร้างสิ่งที่ต้องทำ" (แถวเดียวกับปุ่ม
"แก้ไข" ที่มีอยู่แล้วในหัวข้อของ modal) ที่เปิด `TaskFormModal` ในโหมดสร้าง
งานใหม่ พร้อมลิงก์ประเภท `"equipment"` ไปยังเครื่องที่ modal กำลังแสดงอยู่
**ถูกผูกไว้ให้แล้วตั้งแต่เปิดฟอร์ม** — แอดมิน SHALL ไม่ต้องค้นหาเครื่องเดิมซ้ำ
ในตัวเลือกผูกลิงก์ของฟอร์มอีก

เนื่องจาก `EquipmentDetailsModal` เป็น component เดียวที่ใช้ร่วมกันทั้งจากแท็บ
"อุปกรณ์ที่ขาย" ในหน้า `/customers` และจากการ์ดแจ้งเตือนที่ผูกเครื่องบน
`/crm/alerts` (ปุ่ม "แก้ไข" ของการ์ดกำหนดการ / ประกันใกล้หมด / สอบเทียบ /
ข้อมูลไม่ครบ) ปุ่มนี้ SHALL ปรากฏเหมือนกันทุกประการไม่ว่าจะเปิด modal จากทาง
ไหน

label ของลิงก์ที่ผูกให้อัตโนมัติ SHALL คำนวณด้วย `buildTaskLinkLabel("equipment",
{ productName, serialNumber })` ตัวเดียวกับที่ตัวเลือกผูกลิงก์ในฟอร์มใช้เมื่อ
แอดมินเลือกเครื่องเอง — SHALL ไม่มีสูตรคำนวณ label ชุดที่สอง

ลิงก์ที่ผูกมาให้อัตโนมัตินี้ SHALL ยังคงลบออกได้ตามปกติก่อนกดบันทึก และหัวข้อ
งาน (topic) SHALL ยังคงเป็นช่องที่แอดมินต้องเลือกเองเสมอ — กติกาเดียวกับปุ่ม
ฝั่งลูกค้าทุกข้อ (ดู requirement ของฝั่งลูกค้าด้านล่าง)

ข้อความแจ้งผล (สำเร็จ/ล้มเหลว) ของปุ่มนี้ SHALL ใช้กลไกเดียวกับที่
`EquipmentDetailsModal` ใช้อยู่แล้วทุกจุด (`alert()`) — SHALL ไม่นำระบบ toast
เข้ามาใช้เฉพาะจุดนี้จุดเดียวภายใน modal เดียวกัน ซึ่งจะทำให้การแจ้งผลของ modal
นี้มีสองรูปแบบปนกัน

เมื่อบันทึกงานสำเร็จ ระบบ SHALL ปิดฟอร์มสร้างงานเท่านั้น และ**คงอยู่ที่
`EquipmentDetailsModal` เดิม** — SHALL ไม่ปิด modal รายละเอียดอุปกรณ์ และ
SHALL ไม่นำทางออกจากหน้าที่เปิด modal นั้นอยู่โดยอัตโนมัติ

#### Scenario: กดปุ่มจากหน้าอุปกรณ์ที่ขาย แล้วบันทึกงาน
- **WHEN** แอดมินเปิดรายละเอียดเครื่อง "เครื่องชั่ง A (S/N: SN-1)" จากแท็บ
  "อุปกรณ์ที่ขาย" แล้วกด "สร้างสิ่งที่ต้องทำ" กรอกหัวข้อ+ชื่องาน แล้วกดบันทึก
- **THEN** งานที่ถูกสร้างมีลิงก์ `{ targetType: "equipment", targetId:
  <id ของเครื่องนั้น> }` โดยไม่ต้องเลือกเครื่องเองในฟอร์มเลย และงานนั้นปรากฏ
  บนกระดานงานที่ `/crm/alerts` พร้อมชิปลิงก์ไปยังเครื่องนั้น

#### Scenario: ปุ่มขึ้นเหมือนกันไม่ว่าจะเปิด modal จากทางไหน
- **WHEN** แอดมินเปิด `EquipmentDetailsModal` ของเครื่องเดียวกัน สองทาง —
  ครั้งแรกจากแท็บ "อุปกรณ์ที่ขาย" ครั้งที่สองจากการ์ด "ประกันใกล้หมด" บน
  `/crm/alerts`
- **THEN** ปุ่ม "สร้างสิ่งที่ต้องทำ" ปรากฏและทำงานเหมือนกันทั้งสองครั้ง

#### Scenario: ถอดลิงก์ที่ผูกมาอัตโนมัติออกก่อนบันทึก
- **WHEN** แอดมินกดปุ่มจากหน้าอุปกรณ์ แล้วกดลบชิปลิงก์เครื่องที่ผูกมาให้ก่อน
  กดบันทึก
- **THEN** งานที่ถูกสร้างไม่มีลิงก์ใดเลย (บันทึกได้ตามปกติ)

#### Scenario: ไม่มีหัวข้องานเลยสักอันในระบบ
- **WHEN** แอดมินกดปุ่มนี้ขณะที่ยังไม่มีหัวข้องานที่เปิดใช้งานอยู่เลยสักอัน
- **THEN** ระบบแจ้งเตือนเป็นภาษาไทยผ่าน `alert()` และไม่เปิดฟอร์ม
