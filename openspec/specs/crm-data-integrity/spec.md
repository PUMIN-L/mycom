## Requirements

### Requirement: การ sync อุปกรณ์กับใบขายต้องจับคู่ด้วย serial number ไม่ใช่ตำแหน่ง และห้ามลบข้อมูลอัตโนมัติเด็ดขาด
`syncEquipmentsForSalesRecord` SHALL จับคู่ serial number ที่ส่งมากับแถวอุปกรณ์เดิม
โดยใช้ **serial number เป็น key** ไม่ใช่ลำดับ index (serial ว่างใช้การจับคู่ตาม
ตำแหน่งเป็น fallback เพื่อไม่ให้อุปกรณ์ที่ยังไม่กรอก serial ถูกสร้างซ้ำทุกครั้งที่
บันทึก) ฟังก์ชันนี้ SHALL **ไม่ลบแถวอุปกรณ์ใดๆ โดยอัตโนมัติเด็ดขาด** — เมื่อ
จำนวนอุปกรณ์ในใบขายลดลง แถวส่วนเกิน SHALL ถูก "ปลดออกจากใบขาย"
(`salesRecordId` ว่าง) เท่านั้น ไม่ใช่ลบทิ้ง เพื่อคงข้อมูลอุปกรณ์และประวัติ
ซ่อม/ประกันทั้งหมดไว้ในฐานข้อมูลเสมอ (ยังคงดูได้ภายใต้ลูกค้ารายเดิม) การ sync
ทั้งหมด SHALL ทำใน transaction เดียว (all-or-nothing)

#### Scenario: แก้ไขจำนวนอุปกรณ์ในใบขายโดยลำดับ serial เปลี่ยน
- **WHEN** ใบขายมีเครื่อง A (serial "A1", มีประวัติซ่อม) และเครื่อง B (serial "B1")
  แล้วแอดมินแก้ลำดับใน form เป็น "B1" มาก่อน "A1"
- **THEN** ประวัติซ่อมของเครื่อง A ยังคงผูกกับ serial "A1" เดิม ไม่ถูกย้ายไปอยู่กับ "B1"

#### Scenario: ลดจำนวนอุปกรณ์ในใบขาย
- **WHEN** แอดมินลดจำนวนจาก 2 เหลือ 1
- **THEN** อุปกรณ์ที่ถูกตัดออกจากใบขาย SHALL ถูกปลดออกจากใบขาย (unlink) เท่านั้น
  — แถวข้อมูล พร้อม schedule/log ทั้งหมดยังอยู่ในฐานข้อมูลครบ และยังเห็นได้ใน
  รายการอุปกรณ์ของลูกค้ารายนั้น

#### Scenario: sync ล้มเหลวกลางทาง
- **WHEN** การ sync แถวใดแถวหนึ่งล้มเหลว (เช่น DB error)
- **THEN** ไม่มีการเปลี่ยนแปลงใดๆ เกิดขึ้นกับอุปกรณ์ที่เกี่ยวข้องเลย (all-or-nothing)

### Requirement: การเปลี่ยนประเภทใบขายหรือลบใบขายต้องไม่ลบอุปกรณ์ที่ผูกอยู่
`cleanupEquipmentsForSalesRecord` (เรียกเมื่อเปลี่ยนใบขายจากประเภท "อุปกรณ์"
เป็น "บริการ" หรือเมื่อลบใบขาย) SHALL ปลดอุปกรณ์ที่ผูกอยู่ทั้งหมดออกจากใบขาย
(`salesRecordId` ว่าง) เท่านั้น **ห้ามลบแถวอุปกรณ์ทิ้ง**

#### Scenario: ลบใบขายที่มีอุปกรณ์ผูกอยู่
- **WHEN** ลบใบขายที่มีอุปกรณ์ 2 ชิ้นผูกอยู่
- **THEN** อุปกรณ์ทั้ง 2 ชิ้นยังอยู่ในฐานข้อมูลครบ (แค่ไม่ผูกกับใบขายที่ถูกลบแล้ว)

### Requirement: Schedule จะเป็นสถานะ completed ได้ก็ต่อเมื่อผ่านการบันทึกผลงาน (log) เท่านั้น
`PUT /api/admin/schedules/[id]` SHALL ปฏิเสธการเปลี่ยน status เป็น `completed`
โดยตรง — การเปลี่ยนเป็น completed ทำได้ผ่าน `completeScheduleWithLog`
(บันทึกผลงานพร้อมกัน) เท่านั้น

#### Scenario: พยายามแก้ status เป็น completed ผ่านฟอร์มแก้ไขทั่วไป
- **WHEN** PUT request ส่ง `status: "completed"` มาที่ schedule ที่ยังเป็น `pending`
- **THEN** API ตอบ 400 พร้อมข้อความให้ไปบันทึกผลงานผ่านหน้าจบงานแทน และไม่มีการ
  เปลี่ยนแปลงสถานะ

### Requirement: ลบลูกค้าต้องเช็คก่อนว่ามีอุปกรณ์/ใบขายผูกอยู่หรือไม่
`DELETE /api/customers/[id]` SHALL ปฏิเสธการลบเมื่อลูกค้ายังมี
`customer_equipments` หรือ `sales_records` ผูกอยู่ (เทียบเท่า guard ที่ใช้กับ
การลบ company)

#### Scenario: ลบลูกค้าที่มีอุปกรณ์อยู่
- **WHEN** ลูกค้ามี `customer_equipments` อย่างน้อย 1 แถว แล้วแอดมินกดลบลูกค้า
- **THEN** API ตอบ 400 "ไม่สามารถลบลูกค้าที่มีอุปกรณ์หรือประวัติการขายอยู่" และไม่ลบ

### Requirement: วันที่ประกันในใบขายต้องไม่หายเมื่อแก้ไขข้อมูลอื่น
`updateSalesRecord` (partial update) SHALL คงค่า `warrantyStartDate`/
`warrantyEndDate` เดิมไว้เมื่อ request ไม่ได้ส่งค่าใหม่มา — วันที่ที่อ่านจาก DB
SHALL อยู่ในรูปแบบ string `YYYY-MM-DD` เสมอ (ไม่ใช่ raw Date object)

#### Scenario: แก้ไขข้อมูลอื่นในใบขายที่มีวันประกันอยู่แล้ว
- **WHEN** ใบขายมี warrantyStartDate/EndDate ตั้งไว้แล้ว แล้วแอดมินแก้ไขแค่ note
- **THEN** วันประกันยังคงอยู่เหมือนเดิมหลังบันทึก

### Requirement: ค่า sentinel ของ UI ต้องไม่ถูกบันทึกลง DB
ค่า placeholder ที่ UI ใช้แทนสถานะ "ยังไม่เลือก" (เช่น `"_custom"`) SHALL ถูก
แปลงเป็นค่าว่างจริงก่อนส่งไปยัง API เสมอ ทั้งฝั่ง client และมี defense-in-depth
ฝั่ง server

#### Scenario: บันทึกอุปกรณ์โดยไม่ได้เลือกสินค้าจากลิสต์
- **WHEN** แอดมินเปิดฟอร์มแก้ไขอุปกรณ์ที่ไม่มี productId แล้วกดบันทึกโดยไม่เลือกอะไร
- **THEN** ค่าที่บันทึกลง DB คือ `""` ไม่ใช่ `"_custom"`

### Requirement: ปุ่มลบอุปกรณ์ต้องมี dialog ยืนยันก่อนลบเสมอ
การลบอุปกรณ์จากหน้ารายละเอียดลูกค้า SHALL แสดง dialog ยืนยันก่อนเรียก API ลบจริง
เหมือนกับการลบ company/customer/salesperson ในหน้าเดียวกัน

#### Scenario: กดปุ่มลบอุปกรณ์
- **WHEN** แอดมินกดไอคอนถังขยะบนแถวอุปกรณ์
- **THEN** เห็น dialog ถามยืนยัน พร้อมปุ่มยกเลิก/ยืนยัน — การลบจริงเกิดขึ้นก็ต่อเมื่อ
  กดยืนยันเท่านั้น
