# Proposal: แสดง "อัปเดตล่าสุด" ของบันทึกลูกค้า และเรียงคนที่อัปเดตล่าสุดขึ้นก่อน

## Why

หน้ารายชื่อลูกค้า (`app/customers/page.tsx`) เรียงตาม **วันที่สร้างลูกค้า**
คนที่เพิ่งเพิ่มเข้าระบบอยู่บนสุด แต่สิ่งที่ใช้งานจริงทุกวันคือ `บันทึกลูกค้า`
(สมุดบันทึกการโทร) — คนที่เพิ่งโทรคุยเมื่อวานควรอยู่บน ไม่ใช่คนที่เพิ่งสร้าง

และวันนี้ **ไม่มีทางรู้เลยว่าบันทึกของใครถูกแก้ล่าสุดเมื่อไหร่** ตาราง
`customers` มีแค่ `note` กับ `createdAt` ไม่มีคอลัมน์เวลาแก้ไข

## What Changes

1. **คอลัมน์ใหม่ `customers.noteUpdatedAt`** (`VARCHAR(255) NULL`, ISO-8601 UTC
   รูปแบบเดียวกับ `createdAt`) = เวลาที่ **บันทึกลูกค้า** เปลี่ยนครั้งล่าสุด
   - แก้ชื่อ / เบอร์ / แผนก / บริษัท / อีเมล **ไม่นับ**
   - กดบันทึกโดยที่บันทึกไม่ได้เปลี่ยน **ไม่นับ**
2. **ประทับเวลาทุกเส้นทางที่เขียนบันทึก** (มี 4 ทาง)
   - สร้างลูกค้าใหม่พร้อมบันทึก — `POST /api/customers`
   - แก้ลูกค้า (ฟอร์มแก้ไข และช่องแก้บันทึกใน modal ดูข้อมูล) — `PUT /api/customers/[id]`
   - ค้นหาและแทนที่คำในบันทึก — `customerNoteSearchStore.replaceInNotes`
   - กู้คืนบันทึกจากประวัติ — `POST /api/revisions/[id]/restore`
3. **เติมค่าให้ลูกค้าเดิม (backfill) ตอน migrate**
   - ใช้เวลาจาก `revisions` — ระบบเก็บ snapshot ไว้ทุกครั้งที่บันทึกเปลี่ยน
     จึงได้เวลาจริงของคนที่เคยแก้
   - คนที่ไม่เคยแก้เลย ใช้ `createdAt` แทน
   - คนที่บันทึกว่าง ไม่เติม (คงเป็น NULL)
4. **หน้ารายชื่อลูกค้า**
   - คอลัมน์ใหม่ "อัปเดตล่าสุด" แสดง `24 Sep 2026 14:30` (เวลากรุงเทพฯ)
     คนที่บันทึกว่างแสดง `-`
   - วันที่ตรงกันทุกแถว: เติม 0 หน้าวันที่หลักเดียว (`05 Sep`), ตัวเลขกว้างเท่ากัน
     (`tabular-nums`), ชื่อเดือนอยู่ในกล่องกว้างคงที่ (`Jul` กับ `Sep` กว้างไม่เท่ากัน)
   - แถวที่บันทึกถูกแก้ภายใน 12 ชม. → พื้นหลังเขียวพาสเทล (`bg-green-100`)
     หมดเวลาแล้วกลับเป็นสีปกติเอง (นาฬิกาในหน้าเดินทุกนาที)
   - เรียง: มีบันทึกก่อน → อัปเดตล่าสุดก่อน; คนที่บันทึกว่างอยู่ล่างสุด
     (เรียงกันเองตามวันที่สร้าง ใหม่ก่อน)

## Decisions

- **เรียงฝั่ง client เฉพาะหน้า `/customers` ไม่แตะ `ORDER BY` ของ
  `GET /api/customers`** — API นี้ถูกใช้เป็นรายการ dropdown อีกหลายจุด
  (`EquipmentEditModal`, `SalesRecordEditModal`, `EquipmentTab`,
  `TaskLinkChips`, `QuotationPickerSection`) เปลี่ยนลำดับที่ API จะไปสลับลำดับ
  dropdown เหล่านั้นด้วยโดยไม่มีใครขอ และการเรียงฝั่ง client ยังทำให้ลำดับขยับ
  ทันทีเมื่อ modal ดูข้อมูลแก้บันทึกแล้วอัปเดตรายการในหน่วยความจำ (ไม่ได้โหลดใหม่)
- **Backfill ไม่ได้ใช้ revision ล่าสุดตรงๆ** — ก่อนหน้านี้ `PUT` เคยเก็บ snapshot
  ทุกครั้งที่กดบันทึก แม้แก้แค่เบอร์โทร revision ล่าสุดจึงอาจไม่ใช่การแก้บันทึก
  เลือกเฉพาะ revision ที่ snapshot ของบันทึก **ต่างจากบันทึกปัจจุบัน** — อันล่าสุด
  ในกลุ่มนี้คือจังหวะที่บันทึกกลายเป็นค่าปัจจุบันพอดี
- **`PUT` ส่ง `noteUpdatedAt` กลับมาใน response** ให้ modal ใช้ค่าจริงจาก server
  แทนการเดาเวลาเอง
- **เรียงใน `useMemo` ด้วย `sortCustomersByNoteActivity`** — หน้านี้ render ใหม่
  ทุกครั้งที่พิมพ์ (ฟอร์มแก้ลูกค้า, ช่องค้นหาบริษัทในอีกแท็บ) การใช้
  `.sort(comparator)` ธรรมดากับลูกค้า ~6,000 คนใช้เวลา ~40–70 ms ต่อครั้ง
  ตัวช่วยนี้ parse เวลาแต่ละแถวครั้งเดียว (~5 ms) และ `useMemo` ทำให้เรียงใหม่
  เฉพาะตอนรายชื่อหรือคำค้นเปลี่ยน

## Known limits

- ประวัติเก็บไว้ 10 ชิ้นล่าสุดต่อคน (`REVISION_KEEP.customer`) ถ้าทั้ง 10 ชิ้น
  เป็นการกดบันทึกที่ไม่ได้แก้บันทึก (ยุคก่อนมีการเช็ก) จังหวะแก้จริงถูกตัดทิ้งไปแล้ว
  จะ fallback เป็น `createdAt` ซึ่งเก่ากว่าความจริง — ดีที่สุดเท่าที่ข้อมูลเหลืออยู่
