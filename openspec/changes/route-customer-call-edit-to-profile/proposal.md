# Proposal: กดแก้ไขนัดโทรลูกค้า ให้เปิดหน้ารายละเอียดลูกค้าแทนฟอร์มแก้นัด

## Why

ตอนนี้ปุ่ม "แก้ไข" บนการ์ด "นัดโทรลูกค้า" (และปุ่ม "ไปแก้ไขข้อมูล" ในแผง
รายละเอียดของการ์ดเดียวกัน บนหน้า `/crm/alerts`) เปิด **ฟอร์มเล็กแก้แค่นัดหมาย**
— วันที่นัด / ผู้รับผิดชอบ / หมายเหตุของนัดนั้นเพียงอย่างเดียว
(`resolveAlertEditRoute` → `schedule_form`) นี่คือพฤติกรรมที่ตั้งใจทำไว้ตอนแก้บั๊ก
"กดแก้ไขนัดโทรลูกค้าแล้วพัง" ใน `add-crm-task-board` (นัดโทรลูกค้าไม่มี
`equipmentId` เกาะอยู่ กติกาเดิมเลยเลือกฟอร์มแก้นัดเป็นทางออกเดียวที่ไม่พัง)

เจ้าของระบบแจ้งว่าที่อยากได้จริงๆ ไม่ใช่ฟอร์มแก้นัด แต่คือ **หน้ารายละเอียดของ
ลูกค้าคนนั้น** — แผนก / อีเมล / เบอร์โทรศัพท์ / บันทึกลูกค้า (เหมือนที่เห็นตอน
เปิดลูกค้าจากหน้า `/customers`) เหตุผล: เป้าหมายจริงของปุ่ม "แก้ไข" ตรงนี้คือ
"ก่อนจะโทร ขอดู/แก้ข้อมูลลูกค้าคนนี้" ไม่ใช่ขยับวันนัด

ข่าวดีคือ **ไม่ต้องสร้างของใหม่เลย** — หน้า `/customers` มีกลไก deep-link อยู่แล้ว:
`/customers?customerId=<id>` จะสลับไปแท็บ "รายชื่อลูกค้า" แล้วเปิด "Viewing
Customer Modal" ของคนนั้นให้อัตโนมัติ พร้อมด่านกันไว้ครบ (ลูกค้าไม่พบเพราะถูกลบ
/ โหลดไม่สำเร็จ มีข้อความไทยแยกกันสองแบบ, `app/customers/page.tsx:226-238`)
งานนี้จึงเป็นแค่ **เปลี่ยนปลายทางของปุ่ม** ไม่ใช่สร้างหน้าใหม่หรือ modal ใหม่

## What Changes

- `resolveAlertEditRoute` (`app/lib/alertEditRoute.ts`): เพิ่ม route kind ใหม่
  `customer_profile` — เมื่อ `target.type === "customer_call"` **และ** มี
  `customerId` ที่ใช้ได้ (ผ่าน `usableId` ตัวเดิม) ให้เลือกเส้นทางนี้แทน
  `schedule_form` เดิม
  - ถ้า `customerId` ใช้ไม่ได้ (ข้อมูลเก่า/พังจริงๆ ซึ่งไม่ควรเกิดในทางปฏิบัติ
    เพราะแถวนัดโทรลูกค้าผูกกับ `customerId` เสมอตามคำนิยาม) **ตกกลับไปที่
    `schedule_form` เหมือนเดิม** — เพื่อไม่ให้ปุ่มกลายเป็น "กดแล้วไม่มีอะไร
    เกิดขึ้นเลย" เมื่อข้อมูลไม่สมบูรณ์
  - กำหนดการที่ผูกเครื่อง (`target.type === "schedule"`) **ไม่เปลี่ยนพฤติกรรม
    เลย** — ยังไปหน้ารายละเอียดอุปกรณ์เหมือนเดิมทุกประการ (แถวประเภทนี้ผูก
    equipmentId เสมอ ไม่ใช่กรณีที่ขอเปลี่ยน)
- `app/crm/alerts/page.tsx` (`handleEditClick`): เพิ่มการจัดการ route kind
  `customer_profile` → `router.push(\`/customers?customerId=${encodeURIComponent(id)}\`)`
  แล้วปิดการ์ด/แผงรายละเอียดที่เปิดอยู่ — รูปแบบเดียวกับที่ "ลูกหนี้ค้างชำระ"
  ทำกับ `/billing?id=...&view=1` อยู่แล้วในไฟล์เดียวกัน (นำทางออกจากหน้า ไม่ใช่
  modal ซ้อน modal)
- ปุ่ม "เสร็จแล้ว" และ "เลื่อนแจ้งเตือน" บนการ์ดนัดโทรลูกค้า **ไม่แตะ** — ยัง
  ทำงานเหมือนเดิมทุกประการ (ปิดงานผ่าน `service_logs`, เลื่อนแจ้งเตือนผ่าน
  `alert_snoozes` ตามเดิม)
- ป้ายปุ่ม "แก้ไข" บนการ์ด และ "ไปแก้ไขข้อมูล" ในแผงรายละเอียด **ไม่เปลี่ยนคำ**
  — ยังใช้คำเดิมกับทุกประเภทการ์ด (เหมือนที่ทำกับ "ลูกหนี้ค้างชำระ" ซึ่งก็นำทาง
  ออกจากหน้าเหมือนกันแต่ไม่ได้เปลี่ยนคำปุ่ม)

### ผลข้างเคียงที่ต้องบอกไว้ตรงๆ (trade-off)

ฟอร์มแก้นัด (ขยับวันที่ / มอบหมายคนรับผิดชอบ / แก้หมายเหตุของ "นัดนี้" เอง) จะ
**ไม่มีทางเข้าถึงจากปุ่ม "แก้ไข" บนการ์ดนี้อีกต่อไป** ถ้าอยากขยับวันนัดโทร ยังทำ
ได้ผ่านเครื่องมือ "ค้นหาตามวันที่ + เลื่อนหลายอัน" (`add-alert-date-search`,
`/crm/alerts` เช่นกัน) ที่มีอยู่แล้ว แต่เป็นคนละหน้าจอ/ขั้นตอน ไม่ใช่คลิกเดียว
จากตัวการ์ด — ถ้าต้องการให้ยังแก้วันนัดได้จากตรงนี้ด้วย (เช่น เพิ่มปุ่มแยกอีก
ปุ่มสำหรับแก้นัดหมายโดยเฉพาะ) แจ้งเพิ่มได้ งานนี้ยังไม่ได้ทำส่วนนั้น

## Impact

- Affected specs:
  - `crm-alert-surface` (แก้ 1 requirement ที่ตั้งไว้ใน `add-crm-task-board`
    ซึ่งยังไม่ถูก archive)
- Affected code:
  - `app/lib/alertEditRoute.ts` — route kind ใหม่ `customer_profile`
  - `app/crm/alerts/page.tsx` — `handleEditClick` จัดการ kind ใหม่
  - `__tests__/lib/alertEditRoute.test.ts` — แก้ 1 เคสที่ปักหมุดพฤติกรรมเดิม
    (task 10.5 เดิม) ให้ตรงกับพฤติกรรมใหม่ + เพิ่มเคส fallback
  - เทสต์หน้า `/crm/alerts` (ใหม่หรือขยายของเดิม ถ้ามีไฟล์อยู่แล้ว) — ยืนยันว่า
    กด "แก้ไข" นำทางไป `/customers?customerId=...` จริง ไม่ใช่เปิด
    `editingSchedule`
- ไม่กระทบ:
  - `app/customers/page.tsx` — ใช้กลไก deep-link (`?customerId=`) ที่มีอยู่แล้ว
    ทั้งหมด ไม่แก้ไฟล์นี้แม้แต่บรรทัดเดียว
  - การ์ด "กำหนดการ" (equipment-scoped schedule, `type: "schedule"`) — ปุ่ม
    แก้ไขยังไปหน้าอุปกรณ์เหมือนเดิม
  - ปุ่ม "เสร็จแล้ว" / "เลื่อนแจ้งเตือน" ของนัดโทรลูกค้า และทุกประเภทการ์ดอื่น
  - `app/lib/db.ts` และ `SCHEMA_VERSION` — ไม่มีคอลัมน์หรือ migration ใหม่
  - `GET /api/admin/alerts`, `getAlerts()` — ฟีดเดิมไม่เปลี่ยน ตัวเลขบนกระดิ่ง
    ไม่เปลี่ยน
