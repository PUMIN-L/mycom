# Proposal: กระดานงานที่ต้องทำใน CRM และการแยกที่มาของเครื่องจักร

## Why
หน้า `/crm/alerts` ทุกวันนี้แสดงได้แค่ "สิ่งที่ระบบคำนวณเอง" — ประกันใกล้หมด,
ใกล้ถึงกำหนดสอบเทียบ, ข้อมูลไม่ครบ, เอกสารค้าง — ไม่มีที่ว่างสำหรับสิ่งที่
เจ้าของกิจการเองเป็นคนรู้ว่าต้องทำ และมีปัญหาที่เจอจริง 3 เรื่อง

**1. นัดโทรที่จองไว้จากหน้าลูกค้า หายไปเฉยๆ จนกว่าจะเหลืออีก 7 วัน**
สร้างนัดโทรจากหน้ารายชื่อลูกค้าแล้วกลับไปดูที่หน้าแจ้งเตือน — ไม่มีอะไรเลย
เพราะ `getAlerts()` (`app/lib/crmStore.ts:798-876`) ดึงกำหนดการด้วยคิวรี่เดียว
ที่กรอง `WHERE s.status = 'pending' AND s.scheduledDate <= ?` โดย `?` คือ
วันนี้ + `scheduleDays` (ค่าเริ่มต้น 7 วัน จาก
`app/api/admin/alerts/route.ts`) นัดโทรของเดือนหน้าจึงยังไม่เข้าเงื่อนไข
ผลคือ **การกดสร้างนัดรู้สึกเหมือนไม่ได้เกิดอะไรขึ้น** ทั้งที่ข้อมูลถูกบันทึกแล้ว
และเจ้าของก็ไม่มีทางรู้ว่าเดือนนี้มีนัดโทรค้างอยู่กี่ราย

**2. ไม่มีที่จดว่า "ต้องโทรหาเจ้านี้" / "ต้องทำใบเสนอราคาให้เจ้านั้น"**
งานพวกนี้ไม่ใช่สิ่งที่ระบบคำนวณได้ — มันคือสิ่งที่เจ้าของนึกขึ้นได้เองระหว่างวัน
ทุกวันนี้จึงไปอยู่บนกระดาษหรืออยู่ในหัว หายง่าย และไม่เชื่อมกับข้อมูลลูกค้า/
เครื่อง/ใบเสนอราคา/เอกสารที่อยู่ในระบบอยู่แล้ว ทั้งที่เวลาจะทำงานนั้นจริงๆ
ต้องเปิดของพวกนี้ทุกครั้ง สิ่งที่ต้องการคือ **โพสต์อิทแปะไว้** ที่เปิดหน้าเดียว
แล้วเห็นครบ กรองตามหัวข้อได้ และเพิ่มหัวข้อใหม่เองได้ในอนาคต

**3. รายการเครื่องจักรแยกไม่ออกว่าเราขายเองหรือลูกค้าซื้อมาเอง**
`customer_equipments` วันนี้ไม่มีฟิลด์ใดบอกที่มาของเครื่องเลย เครื่องที่เราขายเอง
กับเครื่องที่ลูกค้าซื้อจากที่อื่นแล้วจ้างเราดูแล ถูกเก็บเหมือนกันทุกประการ
ซึ่งเปลี่ยนความหมายของช่องประกันไปทั้งหมด — ใบรับประกัน/วันเริ่ม-หมดประกันของ
เครื่องที่เราไม่ได้ขาย อาจไม่ใช่ประกันของเรา และการเตือน "ประกันใกล้หมด" ของ
เครื่องกลุ่มนี้อาจไม่ใช่เรื่องที่เราต้องทำอะไร กลายเป็นเสียงรบกวนในหน้าแจ้งเตือน

## What Changes

### Database
- ตารางใหม่ `task_topics` — หัวข้องานที่ผู้ใช้เพิ่มเองได้: `id` (INT PK
  จัดสรรแบบ `MAX(id)+1` พร้อม retry เมื่อชนกัน ตามแบบ `product_categories`
  ใน `app/lib/productStore.ts:27-72`), `name`, `icon` (emoji), `color`
  (เก็บเป็น token ไม่ใช่ CSS ดิบ), `sortOrder`, `isActive`, `createdAt`
  พร้อม seed 5 หัวข้อเริ่มต้น: 📞 โทรหาลูกค้า, 🚗 นัดเข้าไปหาลูกค้า,
  📄 รอทำใบเสนอราคา, 🔧 นัดเข้า Service, 📌 อื่นๆ
- ตารางใหม่ `crm_tasks` — งานที่ต้องทำ 1 แถวต่อ 1 งาน: `id` VARCHAR(36) PK,
  `topicId`, `title`, `detail` TEXT, `dueDate` (nullable, `YYYY-MM-DD`
  แบบเดียวกับ `service_schedules.scheduledDate`), `status`
  (`"pending" | "done"`), `completedAt`, `createdAt`
- ตารางใหม่ `task_links` — ลิงก์จากงานไปยังของในระบบ: `taskId`,
  `targetType` (`"customer" | "equipment" | "quotation" | "document"`),
  `targetId` VARCHAR(255), `label` (snapshot ชื่อ ณ ตอนผูกลิงก์),
  `createdAt`, `PRIMARY KEY (taskId, targetType, targetId)` +
  `INDEX (targetType, targetId)` — ใช้รูปคีย์ polymorphic แบบเดียวกับ
  `alert_snoozes` (`app/lib/db.ts:880-890`)
- เพิ่ม 2 คอลัมน์บน `customer_equipments` แบบ additive: `ownershipSource`
  (`"sold_by_us" | "customer_owned"`, default `"sold_by_us"`) และ
  `warrantyAlertEnabled` (default เปิด) — แถวเดิมทั้งหมดจึงคงพฤติกรรมเดิม
  ทุกประการ ไม่มีเครื่องไหนถูกจัดประเภทใหม่หรือถูกปิดการเตือนเงียบๆ
- Bump `SCHEMA_VERSION` ใน `app/lib/db.ts` **34 → 35** (ต้องเป็นเลขใหม่ที่
  ยังไม่เคยใช้เท่านั้น เพราะการข้าม migration เช็คด้วย
  `stored >= SCHEMA_VERSION` — เคยเกิดปัญหานี้มาแล้วกับ v33)
- ลิงก์ทั้งหมดเป็น **soft link ไม่มี FK** ตามธรรมเนียมเดิมของโปรเจกต์
  (`sales_records.quotationId`, `customer_equipments.salesRecordId`)
  เพราะใบเสนอราคาถูกลบอัตโนมัติตาม retention 2 ปี

### Store
- `app/lib/crmStore.ts` — แยกคิวรี่กำหนดการใน `getAlerts()` จาก **1 คิวรี่**
  เป็น **2 หมวด**:
  1. **กำหนดการเข้า Service (ผูกกับเครื่อง)** — `equipmentId` ไม่ว่าง คง
     หน้าต่าง `scheduleDays` (7 วัน) และคงแท็บเดิมไว้ทุกอย่าง
  2. **นัดโทรลูกค้า (ผูกกับลูกค้า)** — `equipmentId` ว่าง / `customerId`
     ไม่ว่าง (ซึ่งบังคับเป็น `scheduleType = "phone_call"` อยู่แล้ว) แสดง
     **ทันทีที่สร้าง ไม่จำกัดช่วงวัน** และอยู่จนกว่าจะถูกปิดงาน โดยคืนใต้คีย์
     `customerCallFollowUps` (ตัดที่ 100 แถวเพื่อแสดงผล) พร้อมยอดจริง
     `customerCallFollowUpsTotal` ตามแบบ `incompleteEquipmentsTotal`
- `app/lib/crmStore.ts` — ตัวนับ "ประกันใกล้หมด" ต้องเคารพ
  `warrantyAlertEnabled` ของเครื่องแต่ละตัว
- `app/lib/taskStore.ts` (ใหม่) — CRUD ของ `crm_tasks` + `task_links`
  (สร้างงานพร้อมลิงก์ในทรานแซกชันเดียว, ปิดงาน/เปิดงานใหม่, ลิสต์ตามหัวข้อ/
  สถานะ, นับงานที่ **ถึงกำหนดแล้ว** สำหรับกระดิ่ง) และ CRUD ของ `task_topics`

## Constraints (จาก requirement)
- **กระดานงานที่ต้องทำ "ไม่ใช่การแจ้งเตือน"** (D2) — เจ้าของบอกชัดว่า
  "แยกมาอีก 1 function ใน crm/alerts แต่ไม่ใช่การเตือน ... เหมือนแปะโพสอิดไว้"
  ดังนั้นบนหน้าจอมันต้องอ่านออกทันทีว่าเป็นคนละเรื่องกับการ์ดแจ้งเตือน
  ที่ระบบคำนวณให้ ห้ามยัดเป็นแท็บหนึ่งในชุดแท็บแจ้งเตือน
- **นัดโทรลูกค้าขึ้นทันทีที่สร้าง** (D1) — ไม่จำกัดว่าอีกกี่วัน และอยู่จนกว่า
  จะกดว่าสำเร็จ ส่วนกำหนดการที่ผูกกับเครื่อง (Service) คงหน้าต่าง 7 วันและแท็บ
  เดิมไว้ทุกประการ — การเปลี่ยนแปลงนี้ห้ามทำให้พฤติกรรมเดิมของงาน Service ขยับ
- **หัวข้อเป็นข้อมูลที่ขยายได้ ห้ามเป็น enum ตายตัวในโค้ด** (D3) — 5 หัวข้อ
  แรกคือ seed data ไม่ใช่ค่าคงที่ และการเพิ่ม/เปลี่ยนชื่อ/เปลี่ยนสี/ซ่อนหัวข้อ
  ต้องทำได้จากหน้าจอโดยไม่ต้องแก้โค้ดหรือ deploy ใหม่
- **ลิงก์เป็น soft link และต้องรอดเมื่อปลายทางถูกลบ** (D4) — งาน 1 ชิ้นผูกได้
  หลายลิงก์ข้าม 4 ชนิด ไม่มี FK และทุกลิงก์เก็บ **label snapshot** ณ ตอนผูก
  เพราะใบเสนอราคาถูกลบตาม retention 2 ปี เมื่อปลายทางหายไป chip ยังต้องอ่าน
  รู้เรื่องและแสดงว่า "ถูกลบแล้ว" — ห้าม error และห้ามพาไปหน้าที่พัง
- **`dueDate` เป็น optional** (D5) — งานที่ไม่มีกำหนดวันคือโพสต์อิทที่ถูกต้อง
  สมบูรณ์ ห้ามบังคับกรอกวัน
- **กระดิ่งนับเฉพาะงานที่ถึงกำหนดแล้ว** (D6) — `dueDate <= วันนี้` และยัง
  `pending` เท่านั้น งานที่ไม่มีกำหนดวัน หรือกำหนดวันในอนาคต **ห้าม** ทำให้
  ตัวเลขบนกระดิ่งเพิ่ม เพราะกระดิ่งมีไว้บอกว่า "ต้องทำเดี๋ยวนี้" ไม่ใช่ให้
  to-do list ไปเป่าตัวเลขให้พอง
- **ที่มาของเครื่องเป็นข้อมูล ไม่ใช่กฎ** (D7) — `ownershipSource` บอกแค่ว่า
  เราขายเองหรือลูกค้าซื้อมาเอง มันไม่ได้ตัดสินใจแทนเรื่องการเตือนประกัน
- **สวิตช์เตือนประกันเป็นรายเครื่อง แยกอิสระจากที่มาของเครื่อง** (D8) —
  เจ้าของเลือก "ให้เลือกได้เองรายเครื่อง" แทนกฎเหมารวม ดังนั้นห้ามผูก
  `warrantyAlertEnabled` ให้เปลี่ยนตาม `ownershipSource` โดยอัตโนมัติ
  เครื่องเดิมทั้งหมด default = เตือนเหมือนเดิม + `"sold_by_us"`
  ซึ่งคือสมมติฐานเดิมของระบบ ไม่มีการจัดประเภทใหม่แบบเงียบๆ
- **คู่มือต้องอยู่ในหน้า และเข้าถึงได้ตลอด** (D9) — ครอบคลุมทั้งการแจ้งเตือน
  อัตโนมัติเดิมและกระดานงานใหม่ ไม่ใช่ tooltip ที่โผล่ครั้งเดียวแล้วหายไป
- **ห้ามลบข้อมูลอัตโนมัติ** — งานที่ปิดแล้วยังเก็บไว้พร้อม `completedAt`
  และการ "ซ่อน" หัวข้อคือ `isActive = false` ไม่ใช่การลบแถวหรือลบงานที่ผูกอยู่
- การเขียนหลาย statement ที่ต้อง atomic (งาน + ลิงก์) ใช้ `withTransaction`
  และเพราะมัน retry callback ได้ถึง 3 ครั้ง callback SHALL idempotent
  (mint UUID ภายใน callback)
