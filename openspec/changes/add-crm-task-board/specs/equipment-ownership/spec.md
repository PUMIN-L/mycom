# Spec Delta: equipment-ownership

## ADDED Requirements

### Requirement: ทุกแถวอุปกรณ์ต้องระบุที่มาของเครื่องว่าเราขายเองหรือลูกค้าซื้อมาเอง
`customer_equipments` SHALL มีคอลัมน์ `ownershipSource` ที่รับได้เพียง 2 ค่า คือ
`"sold_by_us"` (แสดงผลว่า "เราขายเอง") และ `"customer_owned"` (แสดงผลว่า
"ลูกค้าซื้อมาเอง เราดูแลให้") โดยมีค่า default เป็น `"sold_by_us"` และ
`SCHEMA_VERSION` ใน `app/lib/db.ts` SHALL ถูก bump จาก 34 เป็น 35 (เลขเวอร์ชัน
เพิ่มขึ้นได้อย่างเดียว เพราะ bootstrap ข้ามการ migrate เมื่อ
`stored >= SCHEMA_VERSION`)

เหตุผลที่ต้องมีฟิลด์นี้ ไม่ใช่แค่เพื่อ "รู้ไว้เฉยๆ" แต่เพราะ **คอลัมน์เดิม
ชุดเดียวกันมีความหมายต่างกันตามที่มาของเครื่อง**: สำหรับเครื่องที่เราไม่ได้ขาย
`quotationNumber` และ `warrantyCertNumber` คือเลขเอกสารของ **ดีลของคนอื่น**
(ผู้ขายรายอื่นเป็นคนออก) ไม่ใช่เอกสารที่เราออกเองและค้นกลับได้ในระบบ
เช่นเดียวกับ `salesRecordId` ที่จะว่างตลอดไปโดยไม่ใช่ความผิดพลาดของข้อมูล
ถ้าไม่มีฟิลด์นี้ คนอ่านตารางจะแยกไม่ออกระหว่าง "เครื่องที่เราขายแต่ยังกรอก
เอกสารไม่ครบ" กับ "เครื่องที่เราไม่เคยขาย จึงไม่มีเอกสารของเราให้กรอกตั้งแต่ต้น"

ค่าอื่นนอกเหนือจาก 2 ค่านี้ SHALL ถูกปฏิเสธที่ระดับ API (400 พร้อมข้อความ
ภาษาไทย) — ห้ามบันทึกค่าที่ไม่รู้จักลง DB และห้ามเงียบๆ แปลงเป็นค่า default
route ที่เขียนฟิลด์นี้ SHALL ยังใช้ `withRoute(fallback, handler)` +
`await requireAuth()` ตามเดิม

#### Scenario: บันทึกขายผ่านระบบตามปกติ
- **WHEN** admin บันทึกใบขายแล้วระบบสร้างแถว `customer_equipments` ให้
- **THEN** แถวนั้นได้ `ownershipSource` = `"sold_by_us"` โดยไม่ต้องเลือกเอง

#### Scenario: เพิ่มเครื่องที่ลูกค้าซื้อมาจากที่อื่น
- **WHEN** admin เพิ่มอุปกรณ์ด้วยมือให้ลูกค้ารายหนึ่ง แล้วเลือกที่มาเป็น
  "ลูกค้าซื้อมาเอง เราดูแลให้"
- **THEN** แถวนั้นเก็บ `ownershipSource` = `"customer_owned"`, `salesRecordId`
  ยังว่างได้โดยไม่ถือเป็นข้อมูลผิด และช่อง `quotationNumber` /
  `warrantyCertNumber` ยังกรอกได้ (เป็นเลขเอกสารของผู้ขายรายอื่น) โดยหน้าจอ
  ระบุให้ชัดว่าเป็นเอกสารจากผู้ขายรายอื่น ไม่ใช่เอกสารในระบบเรา

#### Scenario: ส่งค่าที่มาที่ไม่รู้จักเข้ามา
- **WHEN** request ส่ง `ownershipSource` เป็นค่าอื่น เช่น `"unknown"` หรือ
  ข้อความว่าง
- **THEN** API ตอบ 400 พร้อมข้อความภาษาไทย และไม่มีการเขียนแถวหรือแก้แถวใดๆ

### Requirement: ข้อมูลเดิมทุกแถวต้องถูกตั้งเป็น "เราขายเอง" และห้ามเดาที่มาจาก salesRecordId
ตอน bootstrap แถวเดิมทุกแถวใน `customer_equipments` SHALL ได้
`ownershipSource` = `"sold_by_us"` และ `warrantyAlertEnabled` = เปิด ซึ่งเป็น
พฤติกรรมเดิมของระบบก่อนการเปลี่ยนแปลงนี้พอดี (ทุกเครื่องเตือนประกันอยู่แล้ว)
การ migrate SHALL เป็น additive อย่างเดียวและ idempotent — ไม่แก้ ไม่ทับ
ไม่ลบค่าใดในคอลัมน์อื่น

ระบบ SHALL **ไม่** จัดประเภทแถวเดิมโดยอัตโนมัติจาก `salesRecordId`,
`quotationNumber` หรือ heuristic ใดๆ ทั้งสิ้น เพราะเครื่องจำนวนมากที่เราขายเอง
ถูกกรอกด้วยมือก่อนมีฟีเจอร์บันทึกขาย จึงมี `salesRecordId` ว่างอยู่แล้ว —
การเดาจะติดป้าย "ลูกค้าซื้อมาเอง" ให้เครื่องที่เราขายเองอย่างเงียบๆ เป็นจำนวนมาก
และไม่มีใครรู้ว่าแถวไหนถูกเดา แถวไหนถูกยืนยันจริง การแก้ให้ถูก SHALL เป็นงานที่
admin ทำเองรายเครื่อง (หรือแก้เป็นชุดจากรายการที่กรองแล้ว)

#### Scenario: อัปเกรดฐานข้อมูลที่มีข้อมูลเดิมอยู่
- **WHEN** bootstrap รันบน DB ที่มีอุปกรณ์เดิม 500 แถว โดยบางแถวมี
  `salesRecordId` และบางแถวว่าง
- **THEN** ทั้ง 500 แถวได้ `ownershipSource` = `"sold_by_us"` และเปิดเตือน
  ประกันไว้ทั้งหมด ไม่มีแถวใดถูกจัดเป็น `"customer_owned"` จากการเดา และค่า
  ในคอลัมน์อื่น (serial / วันประกัน / calibrationDate / note) ไม่ถูกแตะต้อง

#### Scenario: รัน bootstrap ซ้ำ
- **WHEN** bootstrap ถูกเรียกอีกครั้งหลัง migrate ผ่านไปแล้ว และ admin ได้แก้
  บางเครื่องเป็น `"customer_owned"` ไปแล้ว
- **THEN** ค่าที่ admin แก้ไว้ยังอยู่เหมือนเดิม ไม่ถูกรีเซ็ตกลับเป็น
  `"sold_by_us"`

#### Scenario: admin แก้เครื่องที่จัดประเภทผิดให้ถูก
- **WHEN** admin เปิดรายการอุปกรณ์ กรองเฉพาะ "เราขายเอง" แล้วเปลี่ยนเครื่องที่
  รู้ว่าลูกค้าซื้อมาเองเป็น "ลูกค้าซื้อมาเอง เราดูแลให้"
- **THEN** เฉพาะแถวที่แก้เท่านั้นที่เปลี่ยน และไม่มีการเปลี่ยนสถานะเตือนประกัน
  ของแถวนั้นตามไปด้วยโดยอัตโนมัติ

### Requirement: การเตือน "ประกันใกล้หมด" ต้องเป็นสวิตช์รายเครื่องที่เป็นอิสระจากที่มาของเครื่อง
`customer_equipments` SHALL มีคอลัมน์ `warrantyAlertEnabled` (default =
เปิด) ที่กำหนดว่าเครื่องนั้นจะขึ้นการแจ้งเตือน "ประกันใกล้หมด" หรือไม่
คิวรี่ warranty ใน `getAlerts()` (`app/lib/crmStore.ts`) SHALL กรองเครื่องที่
ปิดสวิตช์นี้ออก เช่นเดียวกับที่กรองด้วย `status != 'Expired'` และ
`alert_snoozes` อยู่แล้ว และจำนวนที่ `GlobalAdminBell` นับ SHALL ลดลงตามด้วย
(ต้องมาจากชุดข้อมูลเดียวกัน ห้ามให้กระดิ่งนับเครื่องที่หน้า `/crm/alerts`
ไม่แสดง)

สวิตช์นี้ SHALL เป็นอิสระจาก `ownershipSource` โดยสมบูรณ์ — ระบบ SHALL **ไม่**
ปิดเตือนให้อัตโนมัติเมื่อเลือกที่มาเป็น `"customer_owned"` และ SHALL ไม่เปิด
ให้อัตโนมัติเมื่อเปลี่ยนกลับเป็น `"sold_by_us"` เจ้าของงานเลือก
"ให้เลือกได้เองรายเครื่อง" แทนกฎเหมาเข่งที่ผูกกับที่มา เพราะทั้งสองทิศทางมี
เคสจริง: เครื่องที่ลูกค้าซื้อมาเองแต่เราขายสัญญาดูแลต่อ ก็ยังต้องเตือนก่อน
ประกันหมด ส่วนเครื่องที่เราขายเองแต่ลูกค้าแจ้งเลิกใช้/ไม่ต่อประกัน ก็ควรเงียบได้
เมื่อทั้งสองค่าขัดกันในสายตาคนอ่าน **สวิตช์ชนะเสมอ**

#### Scenario: เครื่องลูกค้าซื้อมาเอง แต่เปิดเตือนไว้
- **WHEN** เครื่องหนึ่งมี `ownershipSource` = `"customer_owned"`,
  `warrantyAlertEnabled` = เปิด และ `warrantyEndDate` เหลืออีก 20 วัน
- **THEN** เครื่องนั้นขึ้นในแท็บ "ประกันใกล้หมด" ตามปกติ และถูกนับในกระดิ่ง

#### Scenario: เครื่องลูกค้าซื้อมาเอง และปิดเตือนไว้
- **WHEN** เครื่องเดียวกันถูกปิด `warrantyAlertEnabled`
- **THEN** เครื่องนั้นหายจากแท็บ "ประกันใกล้หมด" ทันที จำนวนในกระดิ่งลดลง 1
  และค่า `warrantyStartDate` / `warrantyEndDate` ยังอยู่ครบใน DB

#### Scenario: เครื่องที่เราขายเอง แต่ปิดเตือนไว้
- **WHEN** เครื่องที่มี `ownershipSource` = `"sold_by_us"` ถูกปิด
  `warrantyAlertEnabled` แล้วประกันกำลังจะหมดใน 10 วัน
- **THEN** เครื่องนั้น **ไม่** ขึ้นเตือน — สวิตช์รายเครื่องมีน้ำหนักเหนือที่มา
  ของเครื่อง (ไม่มีกฎ "เราขายเองต้องเตือนเสมอ")

#### Scenario: เปลี่ยนที่มาของเครื่องที่เปิดเตือนอยู่
- **WHEN** admin เปลี่ยนเครื่องที่เปิดเตือนอยู่จาก "เราขายเอง" เป็น
  "ลูกค้าซื้อมาเอง เราดูแลให้" แล้วบันทึก
- **THEN** `warrantyAlertEnabled` ยังเป็น "เปิด" เหมือนเดิม และเครื่องนั้นยัง
  ขึ้นเตือนประกันอยู่ — ระบบไม่ปิดให้เอง

#### Scenario: เปิดเตือนกลับ
- **WHEN** admin เปิด `warrantyAlertEnabled` ของเครื่องที่เคยปิดไว้ และ
  `warrantyEndDate` ยังอยู่ในหน้าต่าง `warrantyDays` (default 30)
- **THEN** เครื่องนั้นกลับมาขึ้นในแท็บ "ประกันใกล้หมด" ทันทีในการโหลดครั้งถัดไป
  โดยไม่ต้องกรอกวันประกันใหม่

### Requirement: สวิตช์เตือนประกันต้องไม่มีผลต่อการเตือนสอบเทียบและการเตือนข้อมูลไม่ครบ
`warrantyAlertEnabled` SHALL มีผลกับการเตือน "ประกันใกล้หมด" **เท่านั้น**
คิวรี่ calibration และคิวรี่ "ข้อมูลไม่ครบ" ใน `getAlerts()` SHALL ไม่อ้างอิง
คอลัมน์นี้เลย

เขียนข้อนี้ไว้ชัดเจนเพราะเป็นคำถามแรกที่คนอ่านจะถาม เหตุผลคือสองการเตือนนี้ตอบ
คนละคำถามกัน: การเตือนประกันเป็นเรื่อง **ภาระผูกพันทางการค้า** ("ใครรับผิดชอบ
ค่าซ่อม และประกันของใครกำลังจะหมด") ซึ่งขึ้นกับดีล จึงสมเหตุสมผลที่จะปิดได้
ส่วนการเตือนสอบเทียบเป็นเรื่อง **เครื่องมือยังวัดได้แม่นหรือไม่** ซึ่งไม่ขึ้น
กับว่าใครขายเครื่องนั้น — เครื่องชั่งที่เลยกำหนดสอบเทียบก็ให้ค่าที่เชื่อไม่ได้
เท่ากันไม่ว่าเราจะเป็นคนขายหรือไม่ และงานสอบเทียบเองก็เป็นบริการที่เราขายได้
กับเครื่องของลูกค้าที่ซื้อมาจากที่อื่น การปิดเตือนสอบเทียบตามสวิตช์ประกันจึงจะ
ทำให้เราพลาดทั้งความปลอดภัยของผลวัดและโอกาสขายบริการไปพร้อมกัน

ด้วยเหตุผลเดียวกัน การเตือน "ข้อมูลไม่ครบ" (serial ว่าง หรือไม่มี
`warrantyStartDate`) SHALL ไม่ถูกปิดตามสวิตช์นี้ เพราะมันเป็นการเตือนเรื่อง
**คุณภาพข้อมูลในระบบเราเอง** ไม่ใช่เรื่องประกันของลูกค้า ถ้าเครื่องไหนรก
รายการนี้จริงๆ ให้ใช้ `alert_snoozes` ที่มีอยู่แล้วเป็นทางออก — ห้ามผูกกับ
`warrantyAlertEnabled`

#### Scenario: ปิดเตือนประกันบนเครื่องที่ถึงกำหนดสอบเทียบ
- **WHEN** เครื่องที่ `warrantyAlertEnabled` ปิดอยู่ และ `ownershipSource` =
  `"customer_owned"` มี `calibrationDate` ที่ผ่านมาแล้วเกิน 10 เดือน
- **THEN** เครื่องนั้นยังขึ้นในแท็บ "ใกล้ถึงกำหนดสอบเทียบ" ตามปกติ และยังถูก
  นับในกระดิ่ง

#### Scenario: ปิดเตือนประกันบนเครื่องที่ข้อมูลไม่ครบ
- **WHEN** เครื่องที่ปิดเตือนประกันไว้ ยังไม่มี serial number
- **THEN** เครื่องนั้นยังขึ้นในแท็บ "ข้อมูลไม่ครบ" เหมือนเดิม

#### Scenario: เครื่องที่ปิดเตือนประกันและไม่มีวันสอบเทียบ
- **WHEN** เครื่องที่ปิดเตือนประกันไว้ ไม่มี `calibrationDate` เลย
- **THEN** เครื่องนั้นไม่ขึ้นเตือนสอบเทียบ (ตามกฎเดิมที่ต้องมี
  `calibrationDate` ก่อน) — พฤติกรรมนี้ไม่ได้เกิดจากสวิตช์ประกัน

### Requirement: ที่มาของเครื่องต้องเห็นเป็นป้ายในรายการอุปกรณ์และกรองได้
รายการอุปกรณ์ (`app/customers/EquipmentTab.tsx`) SHALL แสดง `ownershipSource`
เป็น **badge** ในแต่ละแถว โดยใช้ข้อความไทยเต็ม ("เราขายเอง" /
"ลูกค้าซื้อมาเอง เราดูแลให้") ไม่ใช่ค่าดิบในฐานข้อมูล และ SHALL มีตัวกรอง
"ที่มาของเครื่อง" ให้เลือกได้ 3 ค่า: ทั้งหมด / เราขายเอง / ลูกค้าซื้อมาเอง
ตัวกรองนี้ SHALL เป็น `app/components/SearchableDropdown.tsx` (ห้ามใช้
`<select>` ปกติ) และ SHALL ทำงานร่วมกับช่องค้นหาและตัวกรองประกันที่มีอยู่เดิม
แบบ AND ไม่ใช่แทนที่กัน

คำถามทางธุรกิจที่ฟิลด์นี้เกิดมาเพื่อตอบคือ "เครื่องที่เราดูแลอยู่ แต่เราไม่ได้
เป็นคนขาย มีกี่เครื่อง เครื่องไหนบ้าง" ดังนั้นเมื่อกรองแล้ว หน้าจอ SHALL แสดง
**จำนวนรายการที่ตรงตัวกรอง** ให้เห็น และไฟล์ export ของรายการนี้ SHALL มี
คอลัมน์ "ที่มาของเครื่อง" ด้วย เพื่อให้เอาไปนับ/ทำรายการต่อได้

เครื่องที่ปิดเตือนประกันไว้ SHALL มีเครื่องหมายให้เห็นในรายการเช่นกัน (เช่น
ไอคอนกระดิ่งปิด) เพื่อไม่ให้ใครสงสัยว่าทำไมเครื่องที่ประกันใกล้หมดถึงไม่เคย
ขึ้นเตือน — สถานะที่ทำให้ระบบ "เงียบ" ต้องมองเห็นได้จากรายการ ไม่ใช่ต้องเปิด
เข้าไปในฟอร์มถึงจะรู้

#### Scenario: กรองดูเฉพาะเครื่องที่เราไม่ได้ขาย
- **WHEN** admin เลือกตัวกรองที่มาเป็น "ลูกค้าซื้อมาเอง เราดูแลให้"
- **THEN** ตารางแสดงเฉพาะแถวที่ `ownershipSource` = `"customer_owned"` พร้อม
  จำนวนรายการที่ตรงตัวกรอง และเลข pagination คำนวณจากผลลัพธ์ที่กรองแล้ว

#### Scenario: ใช้ตัวกรองที่มาร่วมกับคำค้นและตัวกรองประกัน
- **WHEN** admin พิมพ์คำค้น serial บางส่วน + เลือกตัวกรองประกัน
  "ใกล้หมดใน 30 วัน" + เลือกที่มา "เราขายเอง"
- **THEN** ผลลัพธ์คือแถวที่ตรงเงื่อนไข **ทั้งสามข้อพร้อมกัน**

#### Scenario: ป้ายบนแถวและเครื่องหมายปิดเตือน
- **WHEN** ในรายการมีเครื่องที่เราขายเอง 1 เครื่อง และเครื่องที่ลูกค้าซื้อมาเอง
  ซึ่งปิดเตือนประกันไว้อีก 1 เครื่อง
- **THEN** แต่ละแถวแสดง badge ที่มาของตัวเอง และแถวที่ปิดเตือนมีเครื่องหมาย
  บอกว่า "ปิดเตือนประกัน" ให้เห็นโดยไม่ต้องเปิดฟอร์ม

#### Scenario: export รายการอุปกรณ์
- **WHEN** admin กด export รายการอุปกรณ์
- **THEN** ไฟล์ที่ได้มีคอลัมน์ "ที่มาของเครื่อง" เป็นข้อความไทย และมีเฉพาะแถว
  ที่ตรงกับตัวกรองที่เปิดอยู่บนหน้าจอ

### Requirement: ฟอร์มอุปกรณ์ต้องแก้ทั้งสองฟิลด์ได้ และบอกให้ชัดว่าปิดเตือนไม่ได้ลบวันประกัน
`app/components/modals/EquipmentEditModal.tsx` SHALL มีช่อง "ที่มาของเครื่อง"
(`SearchableDropdown` 2 ตัวเลือก) และสวิตช์ "เตือนเมื่อประกันใกล้หมด"
ตำแหน่งของทั้งสองช่อง SHALL อยู่ในลำดับฟอร์มเดิมอย่างมีเหตุผล: "ที่มาของเครื่อง"
วางก่อนกลุ่มเอกสาร (ใบเสนอราคา / ใบรับประกัน) เพราะเป็นตัวกำหนดความหมายของช่อง
เหล่านั้น และสวิตช์เตือนวางติดกับกลุ่มวันเริ่ม/หมดประกันที่มันควบคุม

ข้างสวิตช์ SHALL มีข้อความกำกับที่บอกชัดว่า **การปิดเตือนไม่ได้ลบหรือล้างวัน
เริ่ม/หมดประกัน** — ข้อมูลประกันยังอยู่ครบและยังดูได้จากรายละเอียดเครื่อง
เพียงแต่จะไม่ขึ้นในหน้าแจ้งเตือนเท่านั้น (สอดคล้องกับหลักการของโปรเจกต์ที่
ห้ามลบข้อมูลอัตโนมัติ) เมื่อ `ownershipSource` = `"customer_owned"` ฟอร์ม SHALL
กำกับช่อง `quotationNumber` / `warrantyCertNumber` ว่าเป็นเอกสารของผู้ขายราย
อื่น แต่ SHALL ยังให้กรอกได้และ SHALL ไม่ล้างค่าที่เคยกรอกไว้เมื่อสลับที่มา
ค่าที่เป็นข้อความทั้งหมด SHALL ผ่าน `sanitizePlainText` ก่อนบันทึกตามเดิม

#### Scenario: ปิดเตือนแล้ววันประกันยังอยู่
- **WHEN** admin เปิดเครื่องที่มีวันเริ่ม/หมดประกันครบ แล้วปิดสวิตช์
  "เตือนเมื่อประกันใกล้หมด" และกดบันทึก
- **THEN** `warrantyStartDate` / `warrantyEndDate` ใน DB ไม่เปลี่ยนแปลง
  หน้ารายละเอียดเครื่องยังแสดงวันประกันเหมือนเดิม และมีเพียงการแจ้งเตือน
  เท่านั้นที่เงียบไป

#### Scenario: เห็นคำอธิบายก่อนตัดสินใจปิด
- **WHEN** admin เลื่อนมาถึงสวิตช์เตือนประกันในฟอร์ม
- **THEN** มีข้อความกำกับทำนอง "ปิดแล้วเครื่องนี้จะไม่ขึ้นในแจ้งเตือน
  ประกันใกล้หมด — วันเริ่ม/หมดประกันยังถูกเก็บไว้ครบ ไม่ถูกลบ" แสดงอยู่ข้าง
  สวิตช์นั้นตลอด (ไม่ใช่แสดงเฉพาะตอนกดปิด)

#### Scenario: สลับที่มาแล้วเลขเอกสารเดิมไม่หาย
- **WHEN** เครื่องที่มี `quotationNumber` และ `warrantyCertNumber` กรอกไว้แล้ว
  ถูกเปลี่ยนที่มาเป็น "ลูกค้าซื้อมาเอง เราดูแลให้"
- **THEN** เลขเอกสารทั้งสองยังอยู่ครบ ไม่ถูกล้าง เพียงแต่ป้ายกำกับช่องเปลี่ยน
  เป็นสื่อว่าเป็นเอกสารจากผู้ขายรายอื่น

#### Scenario: แก้ไขเครื่องเดิมโดยไม่แตะสองฟิลด์ใหม่
- **WHEN** admin เปิดฟอร์มแก้เครื่องเดิมเพื่อแก้แค่ `note` แล้วบันทึก
- **THEN** `ownershipSource` และ `warrantyAlertEnabled` ยังเป็นค่าเดิม
  (partial update ไม่รีเซ็ตเป็นค่า default)
