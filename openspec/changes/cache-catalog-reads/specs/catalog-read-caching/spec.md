# Spec Delta: catalog-read-caching

## ADDED Requirements

### Requirement: การอ่านแคตตาล็อกทั้งตารางต้องแคชข้าม request
`getAllProducts()` และ `getAllCategories()` SHALL แคชผลลัพธ์ข้าม request ด้วย
`unstable_cache` ของ Next.js — การเปิดหน้าสาธารณะซ้ำๆ โดยที่ข้อมูลไม่เปลี่ยน
SHALL ไม่ยิงคิวรีอ่านทั้งตารางซ้ำทุกครั้ง

แต่ละฟังก์ชัน SHALL ใช้ cache key ของตัวเอง และ key เหล่านั้น SHALL ไม่ชนกับ
`["products_data"]` ที่ `getProductsData` ใช้อยู่ (คนละ shape ข้อมูล)

#### Scenario: เปิดหน้า showcase หลายครั้งโดยข้อมูลไม่เปลี่ยน
- **WHEN** มีการเปิดหน้า `/showcase/[id]` หลายครั้งติดกัน โดยไม่มีการแก้ไข
  สินค้าหรือหมวดหมู่คั่นกลาง
- **THEN** คิวรี `SELECT * FROM products` และ `SELECT * FROM product_categories`
  ถูกยิงจริงเพียงครั้งเดียว ครั้งถัดๆ ไปเสิร์ฟจากแคช

#### Scenario: หน้ายังคงเป็น dynamic ตามเดิม
- **WHEN** แคชถูกเปิดใช้งาน
- **THEN** `/showcase/[id]` ยังคงเรนเดอร์แบบ dynamic ต่อ request (ยังอ่าน session
  ได้) — การแคช SHALL อยู่ที่ชั้นการอ่านข้อมูล ไม่ใช่ชั้นการเรนเดอร์หน้า

### Requirement: แคทตาล็อกที่แคชไว้ต้องล้างทันทีเมื่อข้อมูลถูกแก้
แคชของ `getAllProducts()` / `getAllCategories()` SHALL ผูกกับ cache tag
`"products"` ซึ่งเป็น tag เดียวกับที่ทุก route ที่แก้ไขสินค้า/หมวดหมู่เรียก
`revalidateTag("products", { expire: 0 })` อยู่แล้ว — แอดมินที่บันทึกการแก้ไข
SHALL เห็นผลทันทีในทุกหน้าที่อ่านข้อมูลชุดนี้ โดยไม่ต้องรอแคชหมดอายุ

#### Scenario: แอดมินแก้ชื่อสินค้าแล้วเปิดหน้าสาธารณะ
- **WHEN** แอดมินบันทึกการแก้ไขสินค้าผ่าน API แล้วเปิดหน้าที่แสดงสินค้านั้น
- **THEN** เห็นชื่อใหม่ทันทีในคำขอถัดไป (ไม่ใช่ค่าที่แคชไว้ก่อนแก้)

#### Scenario: แอดมินซ่อนสินค้า (unpublish)
- **WHEN** แอดมินตั้งสินค้าเป็น `isPublished=false` แล้วผู้ใช้ที่ไม่ได้ login
  เปิดหน้า `/showcase/[id]` ของ content ที่ผูกกับสินค้านั้น
- **THEN** ได้ 404 ทันทีตามกฎเดิม — แคช SHALL ไม่ทำให้สินค้าที่ถูกซ่อนยังมองเห็นได้

#### Scenario: เพิ่ม route ใหม่ที่แก้สินค้าแต่ลืมล้าง tag
- **WHEN** มี route ใหม่ที่เขียนข้อมูลสินค้า/หมวดหมู่ โดยไม่ได้เรียก
  `revalidateTag("products")`
- **THEN** ชุดทดสอบล้มเหลว โดยระบุ route ที่ขาดการล้าง tag

### Requirement: แคชต้องมีเพดานอายุกันข้อมูลค้างถาวร
แคชของทั้งสองฟังก์ชัน SHALL มีเพดานเวลา (`revalidate`) เพื่อให้ข้อมูลที่ถูก
แก้ไขนอกเส้นทาง API (เช่น แก้ DB ตรงๆ) หรือกรณีที่การล้าง tag พลาดไป กลายเป็น
ความค้างที่มีขอบเขตจำกัด ไม่ใช่ค้างตลอดไป

#### Scenario: ข้อมูลถูกแก้โดยไม่ผ่าน API
- **WHEN** ข้อมูลในตาราง `products` ถูกแก้โดยตรงจากเครื่องมือภายนอก (ไม่มีการ
  ล้าง tag)
- **THEN** ข้อมูลใหม่ปรากฏภายในเพดานเวลาที่กำหนด ไม่ค้างค่าเดิมตลอดไป
