# Proposal: ค้นหาแจ้งเตือนตามวันที่ และเลื่อนวันหลายรายการพร้อมกัน

## Why
เจ้าของถามตรงๆ ว่า "1 query วัน เดือน ปี เพื่อดูว่าวันที่เลือกมีการเตือนอะไรบ้าง
ถ้าในการแจ้งเตือนก็ดูได้ทั้งอดีตและอนาคต พอ query มาแล้ว ให้เลือกอันที่จะแก้ไข
เวลาการเตือนได้พร้อมๆ กันโดยการติ๊กถูกข้างหน้า และมีปุ่มให้เลือกทั้งหมดด้วย ...
ให้เพิ่มโหลดเป็นดูแบบตารางได้ด้วย จะได้ดูง่าย" วันนี้ทำไม่ได้เลยสักข้อ ด้วยเหตุผล 3 ข้อ

**1. ฟีดแจ้งเตือนมองไม่เห็นทั้งอดีตและอนาคต — โดยการออกแบบ**
`getAlerts()` (`app/lib/crmStore.ts:1041`) ตัดทุกหมวดด้วยหน้าต่างของตัวเอง
กำหนดการที่ผูกกับเครื่องกรอง `s.scheduledDate <= ?` โดย `?` คือวันนี้ +
`scheduleDays` (ค่าเริ่มต้น 7 วัน — `app/lib/crmStore.ts:1111-1118`,
clamp 1–365 ที่ `app/api/admin/alerts/route.ts:21-24`), ประกันกรอง
`warrantyEndDate` ให้อยู่ระหว่างวันนี้ถึงวันนี้ + `warrantyDays`
(`app/lib/crmStore.ts:1054-1064`), ลูกหนี้กรอง `b.dueDate <= วันนี้ +
RECEIVABLE_ALERT_LEAD_DAYS` (`app/lib/crmStore.ts:1188-1199`) ผลคือ
**นัดของเดือนที่แล้วกับนัดของไตรมาสหน้า มองไม่เห็นเท่ากัน** — อันหนึ่งเพราะ
คิวรี่ไม่มีขอบล่าง อีกอันเพราะมันยังไม่เข้าขอบบน หน้าจอจึงตอบคำถาม
"วันที่ 12 มิ.ย. มีอะไรบ้าง" ไม่ได้ ทั้งที่ข้อมูลอยู่ในฐานข้อมูลครบ
หน้าต่างพวกนี้มีไว้ให้ **ฟีดเริ่มต้นสั้น** ไม่ได้มีไว้นิยามว่าอะไรมีอยู่จริง

**2. เลื่อนวันได้ทีละใบเท่านั้น**
วันนี้การเลื่อนนัด 1 ใบคือเปิดโมดัลแก้ไขกำหนดการ แล้วยิง
`PUT /api/admin/schedules/[id]` หนึ่งครั้ง (`app/crm/alerts/page.tsx:404-427`)
ส่วนงานบนกระดานคือเปิด `TaskFormModal` แล้วยิง `PATCH /api/admin/tasks/[id]`
หนึ่งครั้ง กลับจากทริป 3 วันแล้วต้องเลื่อนนัดทั้งสัปดาห์ = เปิดโมดัลสิบกว่ารอบ
และไม่มีทางเห็นทั้งสัปดาห์พร้อมกันเพื่อรู้ว่าต้องเลื่อนใบไหนบ้างตั้งแต่แรก

**3. การ์ดดีสำหรับ "อ่านทีละใบ" แต่แย่สำหรับ "กวาดสายตาทั้งวัน"**
ฟีดวันนี้เป็นกริดการ์ด 1–3 คอลัมน์ (`app/crm/alerts/page.tsx:477-487` +
แท็บที่ `:581-608`) ซึ่งเหมาะกับการเตือนไม่กี่ใบต่อวัน แต่ผลการค้นหาคือ
**รายการที่ต้องกวาดสายตาเทียบกัน** — วันไหน ใคร เรื่องอะไร เลื่อนได้ไหม —
นั่นคือของที่ตารางทำได้ดีกว่าการ์ดอย่างชัดเจน และเป็นเหตุผลที่เจ้าของขอตารางมา

## What Changes

### ไม่มีการเปลี่ยน schema
ทุกคอลัมน์ที่ฟีเจอร์นี้ต้องใช้มีอยู่แล้วครบ — `service_schedules.scheduledDate`,
`crm_tasks.dueDate`, `customer_equipments.warrantyEndDate` / `.calibrationDate`,
`billing_documents.dueDate` งานนี้จึง **ไม่แตะ `app/lib/db.ts` และไม่ bump
`SCHEMA_VERSION`** ถ้าระหว่างทำพบว่าจำเป็นต้อง migrate ให้ **หยุดแล้วยกขึ้นมาคุย**
ห้ามแอบเพิ่มคอลัมน์

### Store / logic
- `app/lib/alertThresholds.ts` — เพิ่มค่าคงที่ใหม่ 4 ตัว (`DATE_SEARCH_ROW_CAP`,
  `DATE_SEARCH_MAX_RANGE_DAYS`, `BULK_RESCHEDULE_MAX_ITEMS`,
  `BULK_RESCHEDULE_MAX_SHIFT_DAYS`) ในไฟล์เดียวกับเกณฑ์เดิม เพราะไฟล์นี้
  **ไม่มี import** จึงให้ทั้งคิวรี่ฝั่งเซิร์ฟเวอร์และคู่มือ (client component)
  อ่านเลขชุดเดียวกันได้ — เหตุผลเดียวกับที่ไฟล์นี้ถูกสร้างขึ้นมาแต่แรก
- `app/lib/crmStore.ts` — ฟังก์ชันใหม่ `searchDatedAlerts(from, to)` ค้น 5 หมวด
  ที่ store นี้เป็นเจ้าของ (กำหนดการผูกเครื่อง, นัดโทรลูกค้า, ประกัน, สอบเทียบ,
  ลูกหนี้) **โดยไม่ใช้หน้าต่างของฟีดเลย** — ไม่แตะ `getAlerts()` แม้แต่บรรทัดเดียว
- `app/lib/taskStore.ts` — ฟังก์ชันใหม่ `searchTasksByDueDate(from, to)`
  (crm_tasks เป็นของ store นี้ ไม่ใช่ของ crmStore) แล้วให้ route ประกอบสองอันเข้า
  ด้วยกัน — รูปแบบเดียวกับที่ `GET /api/admin/alerts` ประกอบ `getAlerts()` กับ
  `countDueTasks()` อยู่แล้ว
- `app/lib/alertDateSearch.ts` (ใหม่, pure) — ตรรกะที่ทดสอบได้โดยไม่ต้องมี DB:
  แถวไหนติ๊กได้/ไม่ได้, ข้อความเหตุผลภาษาไทยของแต่ละกรณี, การนับ "เลือกทั้งหมด",
  และตัวห่อการคำนวณวันที่ที่เรียก `addDaysToDateString` ตามแบบ
  `app/lib/alertEditRoute.ts` และ `app/lib/taskBoard.ts`
- `app/lib/alertReschedule.ts` (ใหม่) — เจ้าของ **ทรานแซกชันเดียว** ของการย้ายวัน
  แบบชุด ไฟล์เล็กและมี SQL แค่ `UPDATE` สองคำสั่ง (`service_schedules.scheduledDate`
  และ `crm_tasks.dueDate`) ที่แยกออกมาไว้ที่เดียวก็เพื่อให้ **พิสูจน์ได้ด้วยตาและ
  ด้วยเทสต์** ว่าเส้นทางนี้เขียนได้แค่สองคอลัมน์นี้เท่านั้น

### API
- `GET /api/admin/alerts/date-search?from=YYYY-MM-DD&to=YYYY-MM-DD` — ค้นหา
  (วันเดียวคือ `from === to`) คืนผลแยกตามหมวด พร้อมยอดจริงต่อหมวดตามแบบ
  `incompleteEquipmentsTotal`
- `POST /api/admin/alerts/bulk-reschedule` — ย้ายวันของรายการที่ติ๊ก ทั้งแบบ
  "ตั้งเป็นวันเดียวกันหมด" และ "เลื่อน ±N วันโดยคงระยะห่าง" คืน **รายงานรายรายการ**
  ว่าอันไหนย้ายแล้ว อันไหนไม่เปลี่ยน อันไหนถูกปฏิเสธและเพราะอะไร
- ทั้งสองเส้นใช้ `withRoute("<ข้อความ fallback ภาษาไทย>", handler)` +
  `await requireAuth()` และผ่าน `sanitizePlainText` ทุกค่าที่รับเข้ามาก่อนใช้งาน
  ตามธรรมเนียมเดิม

### UI
- `app/crm/alerts/page.tsx` — แถบค้นหาวันที่ (วันเดียว / ช่วงวัน) ใต้หัวข้อหน้า
  และ **ส่วนผลการค้นหาแยกของตัวเอง** คั่นระหว่างหัวหน้ากับฟีด —
  **ไม่ใช่แท็บใน `tabOptions`** และไม่กรองฟีดเดิม
- `app/components/AlertDateSearchPanel.tsx` (ใหม่) — ตัวควบคุมการค้นหา ใช้
  `app/components/DatePicker.tsx` และ (ถ้ามี dropdown ใดๆ) ใช้
  `app/components/SearchableDropdown.tsx` เท่านั้น ห้าม `<select>` ดิบ ตาม AGENTS.md
- `app/components/AlertDateSearchResults.tsx` (ใหม่) — สลับ **ตาราง / การ์ด**
  พร้อมช่องติ๊ก, ปุ่ม "เลือกทั้งหมด", แถบเครื่องมือย้ายวัน และแผงสรุปผล
- `app/components/AlertsGuidePanel.tsx` — เพิ่มหัวข้อที่ 8 อธิบายการค้นหาตามวันที่
  และกติกาว่าอะไรเลื่อนได้/ไม่ได้ เพราะอะไร โดยเลขเกณฑ์ทุกตัวเรนเดอร์จากค่าคงที่จริง
- ยืนยันก่อนย้ายทุกครั้งด้วย `app/components/ConfirmDialog.tsx`, แจ้งผลด้วย
  `showToast` ของหน้า, และกันออกจากหน้าระหว่างคำขอกำลังส่งด้วย
  `app/components/LeaveGuard.tsx` — **ห้าม `alert()`**

## Decisions (สิ่งที่ตัดสินแล้วในเอกสารนี้)

- **D1 — ผลการค้นหามาจาก 6 แหล่ง จับคู่คนละคอลัมน์** กำหนดการผูกเครื่องและนัดโทร
  ลูกค้าจับที่ `service_schedules.scheduledDate`, งานบนกระดานจับที่
  `crm_tasks.dueDate`, ประกันจับที่ `customer_equipments.warrantyEndDate`,
  สอบเทียบจับที่ **วันครบกำหนด** = `calibrationDate + CALIBRATION_VALIDITY_MONTHS`
  เดือน (ไม่ใช่ `calibrationDate` ดิบ ซึ่งคือวันที่สอบเทียบ *ครั้งล่าสุด*
  คนละความหมายกับ "วันนั้นมีอะไรครบกำหนด") และลูกหนี้จับที่
  `billing_documents.dueDate`
- **D2 — ข้อมูลไม่ครบ และ เอกสารค้าง ไม่อยู่ในผลค้นหาเลย** ไม่ใช่เพราะขี้เกียจทำ
  แต่เพราะสองหมวดนี้**ไม่มีวันของตัวเอง**: "ข้อมูลไม่ครบ" เกิดจากช่องที่ว่าง
  (ไม่มี serial / ไม่มีวันเริ่มประกัน) ซึ่งไม่มีวันผูกอยู่, ส่วน "เอกสารค้าง"
  วัดจาก *อายุ* นับจาก `saleDate` (20/30 วัน) แล้วเตือนต่อเนื่องไปไม่มีวันสิ้นสุด
  — `saleDate` คือวันที่ขาย ไม่ใช่วันที่ครบกำหนดอะไร การเอาไปจับคู่จะตอบคนละคำถาม
  (ต่างจากสอบเทียบซึ่งแม้เตือนต่อเนื่องเหมือนกัน แต่มี **วันครบกำหนดจริง** อยู่)
  หน้าจอต้องบอกเรื่องนี้ในผลลัพธ์ที่ว่างเปล่า ไม่ให้ "ว่าง" ถูกอ่านว่า "ค้นหาพัง"
- **D3 — รายการที่ปิดไปแล้วอยู่ในผลค้นหา แต่ติ๊กไม่ได้** เจ้าของค้นวันในอดีตเพื่อ
  **ทบทวนว่าวันนั้นควรเกิดอะไรขึ้น** ถ้าซ่อนนัดที่ปิดงานแล้ว หน้าจอของสัปดาห์ที่แล้ว
  จะเหลือแต่ของที่ค้าง แล้วอ่านออกมาว่า "ไม่ได้ทำอะไรเลย" ซึ่งกลับหัวกลับหางกับ
  ความจริง และคำถามที่ว่า "โทรไปหรือยัง" ก็ไม่มีที่ตอบ ส่วนวันในอนาคตใช้กติกา
  **เดียวกัน** (นัดที่ปิดก่อนกำหนดยังโผล่) เพราะกติกาที่เปลี่ยนตามว่าวันที่ค้นอยู่
  อดีตหรืออนาคต คือบั๊กที่รอถูกแจ้ง สถานะจึงเป็น **ป้าย + ตัวล็อกช่องติ๊ก
  ไม่ใช่ตัวกรอง**
- **D4 — ช่องติ๊กที่ปิดไว้มี 2 ตระกูล และต้องบอกทางออกเสมอ**
  (ก) *ข้อเท็จจริง*: ประกัน / สอบเทียบ / ลูกหนี้ — วันของมันคือข้อเท็จจริงของเครื่อง
  หรือของสัญญา ย้ายที่นี่คือปลอมเอกสารและปิดเสียงเตือนที่ควรดัง ต้องไปแก้ที่
  หน้าเครื่อง หรือหน้า `/billing/receivables`
  (ข) *ปิดไปแล้ว*: นัดที่ `completed`/`cancelled` และงานที่ `done` — ระบบเดิม
  ห้ามแก้ไขนัดที่ปิดแล้วอยู่แล้ว (`app/api/admin/schedules/[id]/route.ts:45-47`)
  และวันของนัดที่ปิดแล้วคือหลักฐานว่าไปเมื่อไหร่ ซึ่ง `service_logs` อ้างอยู่
  ส่วนงานที่เสร็จแล้วมีทางกลับที่ถูกต้องคือกด "เปิดใหม่" ก่อน
- **D5 — เลื่อนไปวันในอดีตทำได้ และตั้งใจให้ทำได้** แอดมินที่กำลังไล่เก็บงานค้าง
  มีเหตุผลเต็มร้อยที่จะดึงงานให้มาถึงกำหนดเร็วขึ้น การบล็อกไว้คืออุบัติเหตุของ
  validation ไม่ใช่กติกา แต่ต้อง **พูดออกมาดังๆ** ในกล่องยืนยันว่ามีกี่รายการที่จะ
  ไปตกก่อนวันนี้
- **D6 — ไม่มีการตัดทิ้งเงียบๆ ทั้งตอนเลือกและตอนย้าย** เกินเพดานจำนวนรายการต่อ
  คำขอ = **ปฏิเสธทั้งคำขอ** พร้อมบอกเพดานและจำนวนที่ส่งมา ไม่ใช่ย้ายให้บางส่วน
  ส่วนผลการค้นหาที่ยาวเกินเพดานแสดงผล = แสดงเท่าที่แสดงได้ + บอกยอดจริง
  ("และอีก N รายการ") ตามแบบ `incompleteEquipmentsTotal` ที่มีอยู่
- **D7 — ตารางคือค่าเริ่มต้นครั้งแรก แล้วหลังจากนั้นความชอบของเจ้าของชนะ**
  "เปิดเป็นตารางเสมอ" กับ "จำว่าครั้งก่อนดูแบบไหน" ขัดกันเองเมื่อเขาเลือกการ์ด
  จึงตัดสินว่า **ตารางคือค่าเริ่มต้นก่อนที่เขาจะเคยเลือก** และเมื่อเลือกแล้ว
  ความชอบนั้นชนะทุกครั้งถัดไป การยัดตารางกลับให้คนที่เพิ่งกดกลับไปดูการ์ด
  คือซอฟต์แวร์แบบที่ทำให้คนเลิกแตะปุ่มนั้นไปเลย
- **D8 — ความชอบนี้ครอบคลุมเฉพาะ "ผลการค้นหา" ไม่ใช่ทั้งหน้า** ฟีดอัตโนมัติและ
  กระดาน "สิ่งที่ต้องทำ" ยังเป็นการ์ดเหมือนเดิมทุกประการ กระดานงานห้ามกลายเป็น
  ตารางแจ้งเตือน และห้ามงอกปุ่ม "เลื่อนแจ้งเตือน" ขึ้นมา
- **D9 — รายการที่ถูก snooze ไว้ ยังโผล่ในผลค้นหา** snooze แปลว่า "อย่าเพิ่งเตือน
  ฉันจนถึงวันนั้น" ไม่ได้แปลว่า "ของชิ้นนี้ไม่มีอยู่" ถ้าผลค้นหาซ่อนมันไว้
  หน้าจอจะตอบว่า "วันนั้นไม่มีอะไร" ให้กับวันที่เจ้าของมีนัดอยู่จริง — ตอบผิด
  จึงแสดงพร้อมป้าย "เลื่อนแจ้งเตือนถึง …" และ **ติ๊กได้ตามปกติ** และการย้ายวัน
  **ไม่แตะแถว `alert_snoozes`** เลย (นอกขอบเขตของ endpoint นี้โดยเจตนา)
- **D10 — ฝั่งเซิร์ฟเวอร์ปฏิเสธเป็นรายรายการ ไม่ล้มทั้งชุด** ช่องติ๊กที่เป็นสีเทา
  คือมารยาท ไม่ใช่การควบคุม คำขอที่ประกอบเองยังต้องถูกปฏิเสธ และต้องปฏิเสธ
