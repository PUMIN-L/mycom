# Tasks: add-crm-task-board

## 1. Phase 1 — Database: ตารางใหม่ (schema v35)
- [ ] 1.1 เพิ่มตาราง `task_topics` ใน `app/lib/db.ts` — `id INT PRIMARY KEY`,
      `name VARCHAR(255)`, `icon VARCHAR(16)` (emoji), `color VARCHAR(32)`
      (เก็บเป็น **token** เช่น `blue`/`amber` ไม่ใช่ค่า CSS/class ดิบ),
      `sortOrder INT DEFAULT 0`, `isActive TINYINT(1) NOT NULL DEFAULT 1`,
      `createdAt VARCHAR(255) NOT NULL`
- [ ] 1.2 เพิ่ม index `idx_tt_active_sort (isActive, sortOrder)` สำหรับคิวรี่
      "หัวข้อที่ยังใช้งานอยู่ เรียงตามลำดับที่ผู้ใช้จัด"
- [ ] 1.3 เพิ่มตาราง `crm_tasks` — `id VARCHAR(36) PRIMARY KEY`,
      `topicId INT NOT NULL`, `title VARCHAR(255) NOT NULL`, `detail TEXT NULL`,
      `dueDate VARCHAR(20) DEFAULT NULL` (YYYY-MM-DD, **nullable ตั้งใจ** D5),
      `status VARCHAR(20) NOT NULL DEFAULT 'pending'` (`pending` | `done`),
      `completedAt VARCHAR(255) DEFAULT NULL`, `createdAt VARCHAR(255) NOT NULL`
- [ ] 1.4 เพิ่ม index `idx_ct_status_due (status, dueDate)` (คิวรี่ "งานที่ถึง
      กำหนดแล้ว" ของกระดิ่ง) และ `idx_ct_topic (topicId)` (ฟิลเตอร์ตามหัวข้อ)
      และ `idx_ct_createdAt (createdAt)` (เรียงงานที่ไม่มี dueDate)
- [ ] 1.5 เพิ่มตาราง `task_links` — `taskId VARCHAR(36) NOT NULL`,
      `targetType VARCHAR(20) NOT NULL` (`customer` | `equipment` |
      `quotation` | `document`), `targetId VARCHAR(255) NOT NULL`,
      `label VARCHAR(255) NOT NULL DEFAULT ''` (snapshot ตอนผูกลิงก์),
      `createdAt VARCHAR(255) NOT NULL`,
      `PRIMARY KEY (taskId, targetType, targetId)` +
      `INDEX idx_tl_target (targetType, targetId)`
      — คีย์ผสมแบบเดียวกับ `alert_snoozes (alertType, referenceId)`
- [ ] 1.6 **ห้ามผูก FK ใดๆ บน `task_links` เลย** รวมทั้ง `taskId` — ไม่มี
      `ON DELETE CASCADE` การลบงานต้องลบแถวลิงก์ของงานนั้นเองใน
      `withTransaction` เดียวกัน (ดูข้อ 4.8) เพื่อให้มีกติกาเดียวทั้งตาราง
      ตรงกับ spec `crm-task-board` ที่ระบุว่าทุกคอลัมน์อ้างอิงเป็น soft link
- [ ] 1.7 **ห้ามผูก FK จาก `task_links.targetId`** ไปตารางปลายทางใดๆ —
      soft link ตาม convention เดิม (`sales_records.quotationId`,
      `customer_equipments.salesRecordId`) เพราะใบเสนอราคาถูก purge ตาม
      retention 2 ปี ลิงก์ต้องไม่พาข้อมูลงานหายตาม
- [ ] 1.8 เขียนคอมเมนต์เหนือ `task_links` อธิบายว่า `label` คือ snapshot
      ตอนผูก ไม่ sync ตามชื่อจริงในภายหลัง (จงใจ — ใช้แสดงผลเมื่อปลายทางหายไป)
- [ ] 1.9 Bump `SCHEMA_VERSION` 34 → 35 ใน `app/lib/db.ts` — เลขต้อง
      **เพิ่มขึ้นเท่านั้น** ห้ามใช้เลขที่เคยขึ้น production แล้วซ้ำ (เคสของ v33)

## 2. Phase 1 — Database: seed หัวข้อเริ่มต้น + คอลัมน์เครื่อง
- [ ] 2.1 Seed หัวข้อเริ่มต้น 5 รายการตอน bootstrap: 📞 โทรหาลูกค้า,
      🚗 นัดเข้าไปหาลูกค้า, 📄 รอทำใบเสนอราคา, 🔧 นัดเข้า Service, 📌 อื่นๆ
      พร้อม `sortOrder` 1-5 และ color token คนละสี
- [ ] 2.2 Seed ต้อง **idempotent** และทำงาน **ครั้งเดียวตอนตารางยังว่าง**
      เท่านั้น (`INSERT ... SELECT ... WHERE NOT EXISTS (SELECT 1 FROM
      task_topics)`) — ห้าม seed ทีละแถวตาม id เพราะหัวข้อที่แอดมินลบทิ้งไป
      แล้วจะถูกใส่กลับคืนมาในการ deploy รอบถัดไป
- [ ] 2.3 ผลของข้อ 2.2: bootstrap รอบถัดไปต้องไม่ทับชื่อ/สี/emoji ที่แอดมิน
      แก้ไปแล้ว และต้องไม่ปลุกหัวข้อที่แอดมินซ่อนไว้ (`isActive = 0` ต้องคง
      เป็น 0) หรือหัวข้อที่ลบไปแล้วให้กลับมา
- [ ] 2.4 Seed ต้องปลอดภัยเมื่อหลาย instance บูตพร้อมกัน — ชนกันแล้วไม่ throw
      จน bootstrap ล้ม
- [ ] 2.5 เพิ่มคอลัมน์ `ownershipSource VARCHAR(20) NOT NULL DEFAULT
      'sold_by_us'` (`sold_by_us` | `customer_owned`) บน `customer_equipments`
      ทั้งใน `CREATE TABLE` และเป็น `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`
      แบบ additive สำหรับ DB เดิม
- [ ] 2.6 เพิ่มคอลัมน์ `warrantyAlertEnabled TINYINT(1) NOT NULL DEFAULT 1`
      บน `customer_equipments` ด้วยรูปแบบเดียวกัน (CREATE + ALTER additive)
- [ ] 2.7 ห้าม UPDATE แถวเดิมใน migration — แถวที่มีอยู่ต้องได้ค่า default คือ
      "เราขายเอง" + เตือนประกันตามเดิม (สถานะปัจจุบัน ไม่ reclassify เงียบๆ)
      ตาม D8
- [ ] 2.8 ห่อ `ALTER` ทั้งสองด้วย try/catch `isBenignSchemaError` ตามแบบ
      คอลัมน์ที่เพิ่มทีหลังตัวอื่นใน `db.ts`

## 3. Phase 1 — Store ใหม่ `app/lib/taskStore.ts`: หัวข้อ (topics)
- [ ] 3.1 `listTopics(includeHidden = false)` — เรียงตาม `sortOrder ASC, id ASC`
      และกรอง `isActive = 1` เมื่อไม่ขอรวมที่ซ่อน
- [ ] 3.2 `addTopic({ name, icon, color })` — allocate `id = MAX(id) + 1`
      พร้อม retry เมื่อชน `ER_DUP_ENTRY` ตามแบบ `addCategory`
      (`app/lib/productStore.ts:27-72`) และตั้ง `sortOrder` = id เมื่อไม่ระบุ
- [ ] 3.3 `updateTopic(id, { name?, icon?, color? })` — เปลี่ยนชื่อ/emoji/สี
- [ ] 3.4 `setTopicActive(id, isActive)` — "ซ่อน" หัวข้อคือ set `isActive = 0`
      เท่านั้น **ห้ามลบแถว และห้ามลบ/ย้ายงานที่อยู่ใต้หัวข้อนั้น**
      (กติกา "ไม่ลบข้อมูลอัตโนมัติ")
- [ ] 3.5 งานที่ผูกกับหัวข้อที่ถูกซ่อน ยังต้องอ่านขึ้นมาแสดงได้ปกติ (ป้าย
      หัวข้อยังโชว์) แค่ไม่ปรากฏเป็นตัวเลือกตอนสร้างงานใหม่
- [ ] 3.6 `reorderTopics(ids[])` — เขียน `sortOrder` ใหม่ทั้งชุดใน
      `withTransaction` เดียว และ ignore id ที่ไม่มีอยู่จริงแทนการ throw
- [ ] 3.7 validate: `name` ห้ามว่างหลัง trim, ยาวไม่เกิน 255, `color` ต้องอยู่
      ใน token ที่กำหนดไว้เท่านั้น (ค่านอกรายการ → 400 ไม่ใช่เขียนลง DB)
- [ ] 3.8 `sanitizePlainText` ทุกฟิลด์ที่มาจากผู้ใช้ก่อน persist
- [ ] 3.9 `deleteTopic(id)` — ลบได้เฉพาะหัวข้อที่ **ไม่มีแถวใน `crm_tasks`
      อ้างถึงเลย** (ทั้ง `pending` และ `done`); ถ้ายังมีงานอยู่ต้องปฏิเสธและ
      ให้ผู้เรียกแนะนำให้ "ซ่อน" แทน — `topicId` เป็น soft reference ไม่มี FK
      การลบจะทำให้งานเก่ากลายเป็นกำพร้าเงียบๆ
- [ ] 3.10 `listTasks` ต้องทน `topicId` ที่หาหัวข้อไม่เจอ (ข้อมูลถูกแก้จากนอก
      ระบบ) — คืนงานนั้นออกมาพร้อมหัวข้อ fallback "ไม่ระบุหัวข้อ" ห้าม
      throw และห้ามกรองงานนั้นทิ้ง

## 4. Phase 1 — Store: งาน (tasks) + ลิงก์ (links) + ตัวนับ
- [ ] 4.1 `listTasks({ topicId?, status?, limit })` — คืนงานพร้อมข้อมูลหัวข้อ
      (JOIN `task_topics`) และลิงก์ทั้งหมดของแต่ละงานในคิวรี่ที่สอง (ห้ามยิง
      คิวรี่ต่อ 1 งาน — N+1)
- [ ] 4.2 การเรียงเริ่มต้น: งานที่เลยกำหนด → ถึงกำหนดวันนี้ → มีกำหนดในอนาคต
      → ไม่มีกำหนด (เรียงตาม `createdAt DESC` ภายในกลุ่มสุดท้าย)
- [ ] 4.3 `addTask({ topicId, title, detail, dueDate, links[] })` — เขียนแถว
      `crm_tasks` + `task_links` ทุกแถวใน `withTransaction` เดียว
- [ ] 4.4 generate UUID **ภายใน** callback ของ `withTransaction`
      (retry ได้ถึง 3 ครั้ง → callback ต้อง idempotent)
- [ ] 4.5 `updateTask(id, {...})` — แก้หัวข้อ/ชื่อ/รายละเอียด/กำหนดวัน และ
      **ล้าง `dueDate` ให้เป็น NULL ได้** (ส่งค่าว่างมา ≠ ไม่ได้ส่งมา)
- [ ] 4.6 `completeTask(id)` — set `status = 'done'` + `completedAt` = ISO now;
      กดซ้ำบนงานที่ done แล้วต้องไม่ error และไม่ทับ `completedAt` เดิม
- [ ] 4.7 `reopenTask(id)` — set `status = 'pending'` + `completedAt = NULL`
- [ ] 4.8 `deleteTask(id)` — ลบเฉพาะเมื่อแอดมินสั่งเอง โดยลบแถว `task_links`
      ของงานนั้น **ด้วยคำสั่งของตัวเองใน `withTransaction` เดียวกัน**
      (ไม่มี FK cascade ตามข้อ 1.6) — ไม่มีการลบอัตโนมัติจากที่อื่นใดทั้งสิ้น
      และห้ามแตะข้อมูลปลายทางของลิงก์
- [ ] 4.9 `addTaskLink(taskId, { targetType, targetId, label })` — เขียน
      `label` เป็น snapshot ที่คำนวณ ณ เวลาผูก และผูกซ้ำคีย์เดิมต้องเป็น
      no-op/upsert ไม่ใช่ error (PK ซ้ำ)
- [ ] 4.10 กติกา label snapshot ต่อ targetType: `customer` = ชื่อลูกค้า
      (+ บริษัทถ้ามี), `equipment` = ชื่อสินค้า + S/N, `quotation` = docNo,
      `document` = ชื่อเอกสาร — และ label ห้าม sync ตามปลายทางภายหลัง (D4)
- [ ] 4.11 `removeTaskLink(taskId, targetType, targetId)`
- [ ] 4.12 validate `targetType` ให้อยู่ใน 4 ค่าเท่านั้น และ export เป็น
      const array (`TASK_LINK_TARGETS`) แบบเดียวกับ `SCHEDULE_TYPES`
- [ ] 4.13 `countDueTasks()` — `COUNT(*) FROM crm_tasks WHERE status =
      'pending' AND dueDate IS NOT NULL AND dueDate <= <วันนี้ตามเวลาไทย>`
      โดยใช้ `bangkokDateString` ตัวเดียวกับ `getAlerts()` (D6)
- [ ] 4.14 คอมเมนต์กำกับ `countDueTasks` ว่า **งานที่ไม่มี `dueDate` และงานที่
      กำหนดในอนาคต ไม่นับ** โดยเจตนา — กระดิ่งมีไว้เตือน "ต้องทำแล้ว"

## 5. Phase 1 — แยกคิวรี่ schedule ใน `getAlerts()`
- [ ] 5.1 แยกคิวรี่ `upcomingSchedules` เดิม (`app/lib/crmStore.ts:798-876`)
      เป็นสองคิวรี่: equipment-scoped (`s.equipmentId IS NOT NULL`) และ
      customer-scoped (`s.equipmentId IS NULL AND s.customerId IS NOT NULL`)
- [ ] 5.2 คิวรี่ equipment-scoped **คงเงื่อนไขเดิมทุกตัวอักษร** —
      `status = 'pending' AND scheduledDate <= <today + scheduleDays>`
      (ค่า default 7 วัน) และยังคืนใต้คีย์ `upcomingSchedules` ชื่อเดิม
- [ ] 5.3 คิวรี่ customer-scoped **ไม่มีหน้าต่างวันเลย** — เงื่อนไขคือ
      `status = 'pending'` อย่างเดียว นัดที่ตั้งไว้อีก 6 เดือนต้องขึ้นทันทีที่
      สร้าง และอยู่จนกว่าจะกด "เสร็จแล้ว" (D1)
- [ ] 5.4 คืนผลลัพธ์ใหม่ใต้คีย์ `customerCallFollowUps` ใน `CrmAlerts`
      (`app/lib/types.ts`) — เป็น **คนละหมวด** กับ `upcomingSchedules`
- [ ] 5.5 คงการ LEFT JOIN `alert_snoozes` ด้วย `alertType = 'schedule'`
      **ค่าเดิม** ในทั้งสองคิวรี่ เพื่อให้การเลื่อนแจ้งเตือนที่บันทึกไว้แล้ว
      ยังมีผลหลังอัปเดต (ห้ามเปลี่ยน alertType เป็นค่าใหม่)
- [ ] 5.6 คง `COALESCE` ชื่อลูกค้า/บริษัทของ customer-scoped ที่มาจาก
      `s.customerId` (join `c2`/`co2`) ให้เหมือนเดิม — การ์ดต้องไม่ขึ้น
      "ลูกค้าทั่วไป" เมื่อมีชื่อจริงอยู่
- [ ] 5.7 ธง `overdue` ของทั้งสองหมวดคำนวณจาก `scheduledDate < today` ตาม
      เกณฑ์เดิม — นัดในอนาคตขึ้นแสดงแต่ **ไม่ใช่** สถานะเลยกำหนด
- [ ] 5.8 เรียง `customerCallFollowUps` ด้วย `scheduledDate ASC` (เลยกำหนด
      ขึ้นก่อนโดยธรรมชาติ)
- [ ] 5.9 เพราะหมวดนี้ไม่มีหน้าต่างวัน ลิสต์อาจยาวไม่จำกัด — ใส่ `LIMIT 100`
      ให้แถวที่ส่งไปแสดงผล ตามแบบ `incompleteEquipments` ที่ทำอยู่แล้ว
- [ ] 5.10 คืนยอดจริงทั้งหมด (คิวรี่ `COUNT(*)` เงื่อนไขเดียวกัน ไม่มี cap)
      ใต้คีย์ `customerCallFollowUpsTotal` ตามแบบ
      `incompleteEquipmentsTotal` — หน้าจอจะได้บอก "และอีก N รายการ" แทนการ
      ซ่อนงานค้างเงียบๆ และกระดิ่งจะได้นับจากยอดจริงไม่ใช่จำนวนแถวที่ถูกตัด
