# Spec Delta: crm-task-board

## ADDED Requirements

### Requirement: สร้างงานบนกระดานได้ด้วยหัวข้อ + ชื่องาน โดยวันครบกำหนดเป็นตัวเลือก
`/crm/alerts` SHALL มี "กระดานงานที่ต้องทำ" ที่ admin สร้างงานเองได้ โดยข้อมูล
**ที่บังคับ** มีเพียง 2 อย่าง: `topicId` (ต้องเป็นหัวข้อที่มีอยู่จริงและยัง
`isActive`) และ `title` (ต้องไม่ว่างหลังผ่าน `sanitizePlainText`) ส่วน `detail`,
`dueDate` และลิงก์ข้ามเอนทิตี้ SHALL เป็น **ตัวเลือกทั้งหมด** — งานที่ไม่มี
วันครบกำหนดคือโพสต์อิตที่ถูกต้องสมบูรณ์ (D5) ห้ามบังคับให้ใส่วันที่

เมื่อบันทึกสำเร็จ ระบบ SHALL เขียน `crm_tasks` 1 แถว (`id` =
`crypto.randomUUID()`, `status` = `"pending"`, `completedAt` = null,
`createdAt` เป็น ISO string) พร้อมแถวใน `task_links` ทุกลิงก์ **ใน
`withTransaction` เดียวกัน** — สำเร็จทั้งชุดหรือไม่มีอะไรถูกเขียนเลย และเพราะ
`withTransaction` retry callback ได้ถึง 3 ครั้ง callback SHALL idempotent คือ
mint UUID ไว้ **ภายใน** callback งานที่บันทึกแล้ว SHALL ปรากฏบนกระดานทันที
โดยไม่ต้อง reload หน้า และ SHALL ค้างอยู่จนกว่าจะถูกกด "สำเร็จ" เท่านั้น
ไม่มีการหมดอายุหรือลบตัวเองตามเวลาใดๆ

ค่าที่รับเข้ามาทุกช่อง SHALL ผ่าน `sanitizePlainText` ก่อนบันทึก, `dueDate`
SHALL เป็นสตริง `YYYY-MM-DD` เท่านั้น และทุก route SHALL เป็น
`withRoute("<ข้อความ fallback ภาษาไทย>", handler)` + `await requireAuth()`

#### Scenario: สร้างงานแบบสั้นที่สุด
- **WHEN** admin เลือกหัวข้อ "📞 โทรหาลูกค้า" พิมพ์ชื่องาน แล้วกดบันทึก
  โดยไม่กรอกรายละเอียด ไม่ใส่วันครบกำหนด และไม่ผูกลิงก์ใดเลย
- **THEN** งานถูกบันทึกสำเร็จ (`dueDate` เป็น null, `status` = `"pending"`)
  และการ์ดของงานนั้นปรากฏบนกระดานทันทีโดยไม่ต้อง reload

#### Scenario: ไม่ได้พิมพ์ชื่องาน
- **WHEN** admin กดบันทึกโดยที่ช่องชื่องานว่าง หรือมีแต่ช่องว่าง/แท็ก HTML
  ที่เหลือค่าว่างหลัง `sanitizePlainText`
- **THEN** API ตอบ 400 พร้อมข้อความภาษาไทยว่าต้องระบุชื่องาน และไม่มีแถวใน
  `crm_tasks` หรือ `task_links` ถูกเขียนเลย

#### Scenario: หัวข้อที่ส่งมาไม่มีอยู่จริงหรือถูกซ่อนไปแล้ว
- **WHEN** payload มี `topicId` ที่ไม่มีในตาราง `task_topics` หรือมีอยู่แต่
  `isActive` = false (เช่นแท็บเปิดค้างไว้ก่อนที่ admin จะซ่อนหัวข้อนั้น)
- **THEN** API ตอบ 400 พร้อมบอกว่าหัวข้อนี้ใช้ไม่ได้แล้ว ไม่มีการเขียนข้อมูล
  และ **ไม่** สร้างหัวข้อขึ้นมาเองอัตโนมัติ

#### Scenario: รูปแบบวันครบกำหนดไม่ถูกต้อง
- **WHEN** `dueDate` ที่ส่งมาไม่ใช่ `YYYY-MM-DD` (เช่น `"31/12/2569"` หรือ
  ISO timestamp เต็ม)
- **THEN** API ตอบ 400 และไม่มีการเขียนข้อมูล — ห้ามบันทึกค่าที่เทียบกับ
  คอลัมน์ VARCHAR วันที่แบบ lexical ไม่ได้

#### Scenario: เขียนลิงก์ล้มเหลวกลางทาง
- **WHEN** งานถูกสร้างพร้อมลิงก์ 3 รายการ แล้วการ insert ลิงก์รายการที่ 3
  ล้มเหลว (DB error)
- **THEN** ไม่มีแถวใน `crm_tasks` และ `task_links` ถูกเขียนเลย และกระดานยังคง
  แสดงรายการเดิมตามปกติ

#### Scenario: transaction ถูก retry
- **WHEN** `withTransaction` retry callback เพราะ connection หลุดชั่วคราว
- **THEN** ผลลัพธ์สุดท้ายคืองานเพียง 1 แถว (id ถูกสร้างใหม่ภายใน callback
  ทุกรอบ) ไม่เกิดงานซ้ำจากรอบที่ถูกยกเลิกไป

#### Scenario: Guest เรียก route ของกระดานงาน
- **WHEN** ผู้ที่ไม่ได้ login เรียก route สร้าง/อ่าน/แก้ไขงานหรือหัวข้อ
- **THEN** ได้ 401 Unauthorized และไม่มีข้อมูลลูกค้า/งานรั่วออกไป

### Requirement: หัวข้องานเป็นข้อมูลในตาราง ไม่ใช่ enum — เพิ่ม แก้ชื่อ เปลี่ยนสี และจัดลำดับได้
หัวข้อของงาน SHALL เก็บในตาราง `task_topics` (`id` INT PK, `name`, `icon`,
`color`, `sortOrder`, `isActive`, `createdAt`) — **ห้ามฝังเป็น enum หรือค่าคงที่
ในโค้ด** เพราะเจ้าของระบบต้องเพิ่มหัวข้อเองได้ในอนาคต (D3) ตอน bootstrap ระบบ
SHALL seed หัวข้อเริ่มต้น 5 รายการ: 📞 โทรหาลูกค้า, 🚗 นัดเข้าไปหาลูกค้า,
📄 รอทำใบเสนอราคา, 🔧 นัดเข้า Service, 📌 อื่นๆ — การ seed SHALL ทำ **ครั้ง
เดียวเมื่อตารางยังว่าง** เท่านั้น เพื่อไม่ให้หัวข้อที่ admin เปลี่ยนชื่อ ซ่อน
หรือลบไปแล้ว ถูกใส่กลับคืนมาเงียบๆ ในการ deploy ครั้งถัดไป

admin SHALL เพิ่มหัวข้อใหม่, แก้ชื่อ, เปลี่ยน icon (emoji), เปลี่ยนสี และ
จัดลำดับ (`sortOrder`) ได้ทุกเมื่อ โดย:
- `color` SHALL เก็บเป็น **token จากชุดสีที่กำหนดไว้** (เช่น `"blue"`,
  `"amber"`) ไม่ใช่ CSS/hex ดิบจากผู้ใช้ และ token ที่ไม่รู้จัก SHALL ถูก
  render ด้วยสีกลาง — ห้ามนำค่าจาก DB ไปต่อเป็น class/style โดยตรง
- การ **แก้ชื่อ/สี/icon SHALL ไม่แตะแถวใน `crm_tasks` เลย** เพราะงานอ้างถึง
  `topicId` ไม่ใช่ชื่อ — งานเดิมทุกใบ (รวมงานที่ปิดไปแล้ว) แสดงชื่อใหม่ทันที
- การจัดลำดับหลายแถว SHALL เขียนใน `withTransaction` เดียว (all-or-nothing)
- `id` SHALL ถูกจองแบบ `MAX(id)+1` แล้ว insert พร้อม **retry เมื่อชน
  duplicate key** ตามแบบ `addCategory` ใน `app/lib/productStore.ts`
- ชื่อหัวข้อ SHALL ผ่าน `sanitizePlainText` และห้ามว่าง

#### Scenario: ระบบใหม่ยังไม่มีหัวข้อเลย
- **WHEN** DB ถูก bootstrap ครั้งแรกหลังการเปลี่ยนแปลงนี้
- **THEN** `task_topics` มี 5 แถวตามค่าเริ่มต้น เรียงตาม `sortOrder` และ
  `isActive` = true ทุกแถว

#### Scenario: deploy ซ้ำหลังจาก admin แก้หัวข้อไปแล้ว
- **WHEN** admin เปลี่ยนชื่อ "📌 อื่นๆ" เป็น "📌 งานจิปาถะ" และซ่อนหัวข้อ
  "🚗 นัดเข้าไปหาลูกค้า" ไปแล้ว จากนั้นระบบถูก deploy/bootstrap อีกครั้ง
- **THEN** ชื่อที่แก้ไว้ยังเป็น "📌 งานจิปาถะ", หัวข้อที่ซ่อนยังซ่อนอยู่ และ
  **ไม่มี** หัวข้อเริ่มต้นถูก insert ซ้ำเข้ามา

#### Scenario: สองแท็บเพิ่มหัวข้อพร้อมกัน (id ชนกัน)
- **WHEN** admin เปิด 2 แท็บแล้วกดเพิ่มหัวข้อพร้อมกัน ทั้งคู่อ่าน
  `MAX(id)` ได้ค่าเดียวกันจึงคำนวณ id ถัดไปตรงกัน
- **THEN** ฝ่ายที่แพ้ได้ duplicate-key แล้ว **retry ด้วย `MAX(id)` ที่อ่านใหม่**
  จนสำเร็จ — สุดท้ายมีหัวข้อใหม่ครบ **2 แถว** คนละ id ไม่มีแถวใดถูกเขียนทับ
  และไม่มี request ใดล้มเหลว

#### Scenario: retry จนครบจำนวนครั้งแล้วยังไม่สำเร็จ
- **WHEN** การจอง id ชนซ้ำจนครบจำนวนครั้งที่กำหนด
- **THEN** API ตอบ error พร้อมข้อความภาษาไทย และไม่มีหัวข้อครึ่งๆ กลางๆ
  ถูกสร้างขึ้น

#### Scenario: เปลี่ยนชื่อหัวข้อที่มีงานผูกอยู่
- **WHEN** หัวข้อ "📄 รอทำใบเสนอราคา" มีงานค้าง 4 ใบและงานที่ปิดแล้ว 10 ใบ
  แล้ว admin เปลี่ยนชื่อเป็น "📄 ค้างทำใบเสนอราคา" และเปลี่ยนสี
- **THEN** งานทั้ง 14 ใบยังผูกกับ `topicId` เดิม และแสดงชื่อ/สีใหม่ทันที
  โดยไม่มีการ UPDATE แถวใดใน `crm_tasks`

#### Scenario: ส่งค่าสีที่ไม่รู้จักมา
- **WHEN** `color` ที่ส่งมาไม่อยู่ในชุด token ที่กำหนด (เช่น CSS ดิบ)
- **THEN** ระบบปฏิเสธค่านั้น หรือเก็บ/แสดงเป็นสีกลาง — และไม่มีสตริงจากผู้ใช้
  ถูกนำไปใส่ใน style/class ที่ render ออกหน้าเว็บ

### Requirement: ซ่อนหัวข้อได้โดยงานใต้หัวข้อนั้นต้องไม่หายไป และหัวข้อที่มีงานอยู่ห้ามลบ
การเลิกใช้หัวข้อ SHALL ทำด้วยการ **ซ่อน** (`isActive` = false) ไม่ใช่การลบ
หัวข้อที่ถูกซ่อน SHALL หายไปจาก dropdown ตอนสร้าง/แก้งานเท่านั้น ส่วน
**งานทุกใบที่อยู่ใต้หัวข้อนั้น SHALL ยังคงอยู่ครบและยังเห็นบนกระดานเหมือนเดิม**
(ทั้งในมุมมอง "ทั้งหมด" และยังถูกนับในกระดิ่งตามกฎเดิม) หัวข้อที่ถูกซ่อนแต่
**ยังมีงานค้างอยู่** SHALL ยังปรากฏในตัวกรองพร้อมป้าย "(ซ่อนแล้ว)" เพื่อไม่ให้
มีงานที่กรองเข้าไปดูไม่ได้ และ admin SHALL เปิดหัวข้อกลับมาใช้ (unhide) ได้

การ **ลบ** หัวข้อ SHALL ถูกปฏิเสธเมื่อยังมีแถวใน `crm_tasks` อ้างถึงหัวข้อนั้น
ไม่ว่าจะ `pending` หรือ `done` โดยตอบ 400 พร้อมแนะนำให้ "ซ่อน" แทน — เหตุผลคือ
`topicId` เป็น soft reference ที่ไม่มี FK การลบจะทำให้งานเก่ากลายเป็นกำพร้าและ
ประวัติหายไปเงียบๆ ซึ่งขัดกับกฎของโปรเจกต์ที่ห้ามลบข้อมูลอัตโนมัติ และเป็น
guard แบบเดียวกับการห้ามลบลูกค้าที่ยังมีอุปกรณ์ผูกอยู่ (`crm-data-integrity`)
หัวข้อที่ **ไม่มีงานอ้างถึงเลย** SHALL ลบได้จริง เพราะไม่มีข้อมูลใดสูญหาย
ทั้งนี้ระบบ SHALL ทนต่อกรณีที่ `topicId` หาแถวหัวข้อไม่เจอ (เช่นถูกแก้ DB
ตรงๆ) ด้วยการแสดงงานนั้นภายใต้ "ไม่ระบุหัวข้อ" — ห้าม crash และห้ามซ่อนงานทิ้ง

#### Scenario: ซ่อนหัวข้อที่ยังมีงานค้าง
- **WHEN** หัวข้อ "🔧 นัดเข้า Service" มีงานค้าง 3 ใบ แล้ว admin กดซ่อน
- **THEN** งานทั้ง 3 ใบยังอยู่บนกระดานภายใต้มุมมอง "ทั้งหมด" ครบถ้วน,
  ตัวกรองยังมีหัวข้อนี้พร้อมป้าย "(ซ่อนแล้ว)" แต่ dropdown ตอนสร้างงานใหม่
  ไม่มีหัวข้อนี้ให้เลือกแล้ว

#### Scenario: ซ่อนหัวข้อที่ไม่มีงานค้างเหลืออยู่
- **WHEN** หัวข้อที่ถูกซ่อนมีแต่งานที่ปิดไปแล้ว (ไม่มีงาน `pending`)
- **THEN** หัวข้อนั้นไม่รกอยู่ในตัวกรองของกระดานงานค้าง แต่ยังใช้แสดงชื่อ
  หัวข้อของงานที่ปิดแล้วในรายการงานสำเร็จได้ตามปกติ

#### Scenario: พยายามลบหัวข้อที่มีงานอ้างถึง
- **WHEN** admin กดลบหัวข้อที่มีงาน (pending หรือ done ก็ตาม) อ้างถึงอยู่
- **THEN** API ตอบ 400 พร้อมข้อความทำนอง "หัวข้อนี้มีงานอยู่ ไม่สามารถลบได้
  กรุณาซ่อนแทน" และไม่มีแถวใดถูกลบทั้งใน `task_topics` และ `crm_tasks`

#### Scenario: ลบหัวข้อที่ยังไม่เคยถูกใช้
- **WHEN** admin เพิ่มหัวข้อผิด แล้วกดลบทันทีก่อนสร้างงานใดๆ ใต้หัวข้อนั้น
- **THEN** หัวข้อถูกลบจริง และไม่มีงานใดได้รับผลกระทบ

#### Scenario: เปิดหัวข้อที่ซ่อนไว้กลับมาใช้
- **WHEN** admin กดเลิกซ่อนหัวข้อ
- **THEN** หัวข้อกลับมาอยู่ใน dropdown สร้างงานตามลำดับ `sortOrder` เดิม และ
  ป้าย "(ซ่อนแล้ว)" ในตัวกรองหายไป

#### Scenario: งานที่ชี้ไปยังหัวข้อที่ไม่มีอยู่แล้ว
- **WHEN** แถวใน `crm_tasks` มี `topicId` ที่ไม่มีแถวใน `task_topics` (ข้อมูล
  ถูกแก้จากนอกระบบ)
- **THEN** กระดานยังโหลดได้ปกติ งานนั้นแสดงภายใต้ "ไม่ระบุหัวข้อ" และ admin
  ยังกดปิดงานหรือย้ายไปหัวข้ออื่นได้ — ไม่มี error หน้าจอขาว

### Requirement: กรองกระดานตามหัวข้อได้ รวมตัวเลือก "ทั้งหมด" และการกรองเป็นเรื่องของการมองเท่านั้น
กระดานงาน SHALL มีตัวกรองตามหัวข้อ โดยมีตัวเลือก **"ทั้งหมด" เป็นค่าเริ่มต้น**
และมีหัวข้อที่ `isActive` ทุกหัวข้อ บวกหัวข้อที่ซ่อนแล้วแต่ยังมีงานค้าง
ตัวกรอง SHALL เป็น **มุมมองล้วนๆ**: SHALL ไม่เขียน ไม่แก้ ไม่ลบข้อมูลใดๆ,
SHALL ไม่เปลี่ยนตัวเลขบนกระดิ่ง, และ SHALL ไม่ทำให้งานหายถาวร — เปลี่ยนกลับไป
"ทั้งหมด" ต้องเห็นงานครบเท่าเดิมเสมอ ตัวเลือกที่กรองอยู่ SHALL แสดงจำนวนงาน
ค้างของแต่ละหัวข้อ และเมื่อกรองแล้วไม่พบงานเลย SHALL แสดงข้อความว่าง
ที่บอกชัดว่ากำลังกรองหัวข้อไหนอยู่ พร้อมทางกลับไป "ทั้งหมด"

ถ้า admin สร้างงานในหัวข้อที่ **ไม่ตรง** กับตัวกรองที่เปิดอยู่ ระบบ SHALL ไม่

`docNo`** เพราะ `docNo` แก้ได้เองและเปลี่ยนเมื่อ clone จึงไม่ปลอดภัยที่จะเป็น

เงื่อนไขครบทั้งสองข้อ** เท่านั้น (D6):

`bangkokDateString(new Date())` จาก `app/lib/dateFormat.ts` — **ห้ามใช้วันที่
UTC ของเซิร์ฟเวอร์** (Vercel รันที่ UTC ซึ่งช่วง 00:00–06:59 เวลาไทยจะยังเป็น

เป็นการเทียบสตริง `YYYY-MM-DD` แบบ lexical เช่นเดียวกับ `getAlerts()`

งานที่ **ไม่มี `dueDate`** SHALL ไม่ถูกนับเลยไม่ว่าจะสร้างไว้นานแค่ไหน และงาน
ที่ครบกำหนดในอนาคต SHALL ยังไม่ถูกนับ — เจตนาคือกระดิ่งมีไว้บอกว่า "ต้องทำ
ตอนนี้" ไม่ใช่ให้ to-do list มาทำให้ตัวเลขเฟ้อ จำนวนนี้ SHALL ถูกส่งออกมาจาก
`/api/admin/alerts` เป็น **ฟิลด์ของตัวเอง** ชื่อ `dueTaskCount`
แล้วบวกเข้ากับผลรวมเดิมของกระดิ่ง
และ SHALL เป็นตัวเลขเดียวกันกับที่ป้ายจำนวนของกระดานงานบน `/crm/alerts` แสดง

#### Scenario: งานไม่มีวันครบกำหนด
- **WHEN** มีงานค้าง 5 ใบที่ไม่ได้ใส่วันครบกำหนดเลย และไม่มีงานอื่นในระบบ
- **THEN** กระดิ่งไม่แสดงตัวเลขเพิ่มจากงานเหล่านี้เลย (นับเป็น 0) แต่ทั้ง 5 ใบ
  ยังแสดงอยู่บนกระดานตามปกติ

#### Scenario: งานครบกำหนดพรุ่งนี้
- **WHEN** งานค้าง 1 ใบมี `dueDate` เป็นวันพรุ่งนี้ตามปฏิทินกรุงเทพฯ
- **THEN** ยังไม่ถูกนับในกระดิ่ง

#### Scenario: งานครบกำหนดวันนี้
- **WHEN** งานค้าง 1 ใบมี `dueDate` ตรงกับวันนี้ตามปฏิทินกรุงเทพฯ
- **THEN** ถูกนับในกระดิ่ง 1 รายการ

#### Scenario: งานเลยกำหนดมาแล้ว
- **WHEN** งานค้าง 1 ใบมี `dueDate` เป็นเมื่อ 10 วันก่อน
- **THEN** ถูกนับในกระดิ่ง และไม่หายไปจากกระดานเองไม่ว่าจะเลยกำหนดนานแค่ไหน

#### Scenario: งานเลยกำหนดแต่ปิดไปแล้ว
- **WHEN** งานที่ `dueDate` เลยมาแล้วถูกกด "สำเร็จ"
- **THEN** ไม่ถูกนับในกระดิ่งอีก แม้ `dueDate` จะยังเป็นวันในอดีตก็ตาม

#### Scenario: ตอนตี 1 ของวันครบกำหนด (เส้นแบ่งวัน UTC)
- **WHEN** เวลาปัจจุบันคือ 01:00 ตามเวลาไทยของวันที่งานครบกำหนด ซึ่ง UTC ยัง
  เป็นวันก่อนหน้า
- **THEN** งานนั้นถูกนับแล้ว เพราะ "วันนี้" ถูกคำนวณจากปฏิทินกรุงเทพฯ
  ไม่ใช่วันที่ UTC ของเซิร์ฟเวอร์

#### Scenario: ตัวเลขบนกระดิ่งกับบนหน้าตรงกัน
- **WHEN** admin เปิด `/crm/alerts` หลังเห็นตัวเลขบนกระดิ่ง
- **THEN** จำนวนงานที่ถึงกำหนดที่แสดงบนกระดานตรงกับส่วนที่กระดิ่งนับไว้พอดี
  (กระดิ่งยังซ่อนตัวเองบนหน้า `/crm/alerts` ตามพฤติกรรมเดิม)

### Requirement: กระดานงานต้องแยกให้เห็นชัดจากการแจ้งเตือนอัตโนมัติบนหน้าเดียวกัน
กระดานงาน SHALL ถูกนำเสนอเป็น **คนละส่วน** กับการ์ดแจ้งเตือนอัตโนมัติของ
`getAlerts()` บน `/crm/alerts` เพราะมันคือโน้ตที่ admin เขียนเตือนตัวเอง ไม่ใช่
สิ่งที่ระบบตรวจพบ (D2) โดยเฉพาะ:
- กระดานงาน SHALL เป็น **บล็อกของตัวเองบนหน้า** (มีหัวข้อและพื้นหลังของตัวเอง)
  และ SHALL **ไม่** ถูกเพิ่มเป็นแท็บหนึ่งใน `tabOptions` ของ
  `app/crm/alerts/page.tsx` ซึ่งเป็นชุดแท็บของ "สิ่งที่ระบบตรวจพบเอง" ล้วนๆ
  (`tabOptions` เปลี่ยนแปลงเฉพาะเพื่อรับแท็บ "นัดโทรลูกค้า" ตาม spec
  `crm-alert-surface` เท่านั้น) กระดานงาน SHALL หาเจอได้เสมอโดยไม่ขึ้นกับ
  แท็บแจ้งเตือนที่เลือกอยู่
- ในมุมมอง "ทั้งหมด" การ์ดงานที่บันทึกเอง SHALL **ไม่ถูกผสมสลับ** อยู่ใน
  `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3` ของการ์ดแจ้งเตือนอัตโนมัติ
  แต่อยู่ในบล็อกที่มีหัวข้อกำกับของตัวเอง
- การ์ดงานทุกใบ SHALL มีป้ายกำกับที่อ่านออกทันทีว่า **"บันทึกเอง"** และ SHALL
  ใช้สไตล์/โทนสีที่แยกจากการ์ดเตือนอัตโนมัติอย่างชัดเจน
- ข้อความบนการ์ดงาน SHALL ไม่ใช้ถ้อยคำที่ทำให้เข้าใจว่าระบบตรวจพบเอง (เช่น
  "ประกันใกล้หมด" / "ข้อมูลไม่ครบ") — ข้อความบนการ์ดคือสิ่งที่ admin พิมพ์เอง
- กระดานงาน SHALL ไม่มีปุ่ม "เลื่อนการแจ้งเตือน" (snooze) ของระบบเตือนอัตโนมัติ
  และ SHALL ไม่เขียนแถวใดลง `alert_snoozes`

#### Scenario: เปิดแท็บ "ทั้งหมด"
- **WHEN** admin เปิด `/crm/alerts` ที่แท็บ "ทั้งหมด" ขณะที่มีทั้งงานที่บันทึก
  เองและการแจ้งเตือนอัตโนมัติ
- **THEN** เห็นสองส่วนแยกกันชัดเจนพร้อมหัวข้อกำกับ ไม่มีการ์ดงานที่บันทึกเอง
  แทรกอยู่กลาง grid ของการแจ้งเตือนอัตโนมัติ

#### Scenario: อ่านการ์ดงานแล้วต้องรู้ว่าใครเป็นคนสร้าง
- **WHEN** มีคนเปิดดูการ์ดงาน "โทรตามลูกค้าเรื่องเครื่องชั่ง"
- **THEN** เห็นป้าย "บันทึกเอง" บนการ์ด และไม่มีข้อความใดที่สื่อว่าระบบตรวจพบ
  เงื่อนไขอะไรให้

#### Scenario: การแจ้งเตือนอัตโนมัติยังทำงานเหมือนเดิม
- **WHEN** มีการเพิ่มกระดานงานเข้ามาบนหน้า `/crm/alerts`
- **THEN** แท็บเดิมทั้ง 6 (ทั้งหมด / กำหนดการ / ประกันใกล้หมด / ใกล้ถึงกำหนด
  สอบเทียบ / ข้อมูลไม่ครบ / เอกสารค้าง) และปุ่ม snooze ของการ์ดเดิมยังทำงาน
  เหมือนเดิมทุกประการ และไม่มีแท็บของกระดานงานถูกเพิ่มเข้าไปในชุดแท็บนั้น

#### Scenario: สลับแท็บแจ้งเตือนแล้วกระดานงานต้องยังหาเจอ
- **WHEN** admin สลับจากแท็บ "ทั้งหมด" ไปแท็บ "เอกสารค้าง"
- **THEN** บล็อกกระดานงานยังอยู่ในตำแหน่งเดิมที่หาเจอได้ ไม่ถูกตัวกรองของแท็บ
  แจ้งเตือนกรองหายไป

### Requirement: ตารางของกระดานงานต้องเป็น soft link และต้อง bump SCHEMA_VERSION
การเปลี่ยนแปลงนี้ SHALL เพิ่มตาราง `task_topics`, `crm_tasks` และ `task_links`
ใน `app/lib/db.ts` และ SHALL **bump `SCHEMA_VERSION` จาก 34 เป็น 35** —
ตัวเลขนี้ SHALL เพิ่มขึ้นอย่างเดียวเท่านั้น เพราะการตรวจข้ามใช้เงื่อนไข
`stored >= SCHEMA_VERSION` การนำเลขที่เคยใช้แล้วกลับมาใช้ซ้ำจะทำให้ migration
ทั้งก้อนถูกข้ามไปเงียบๆ (เคยเกิดมาแล้วกับ v33)

ทุกคอลัมน์อ้างอิงของสามตารางนี้ (`crm_tasks.topicId`, `task_links.taskId`,
`task_links.targetId`) SHALL เป็น soft link: มี index/PK แต่ **ไม่มี FOREIGN
KEY และไม่มี ON DELETE CASCADE เลยแม้แต่ตัวเดียว** เพื่อให้ปลายทางถูกลบ/purge
ได้โดยที่งานไม่หายตามไปด้วย และเพื่อให้มีกติกาเดียวทั้งชุดตาราง ผลที่ตามมาคือ
การลบงาน SHALL ลบแถวใน `task_links` ของงานนั้น **ด้วยคำสั่งของตัวเองใน
`withTransaction` เดียวกัน** ไม่ใช่ปล่อยให้ FK cascade จัดการ การ bootstrap
SHALL idempotent (รันซ้ำแล้วไม่พัง ไม่สร้างซ้ำ) และ SHALL ไม่แก้หรือลบข้อมูลเดิม
ใดๆ ในตารางอื่น

#### Scenario: bootstrap บน DB ที่มีข้อมูลอยู่แล้ว
- **WHEN** DB เดิมที่ `schema_version` = 34 ถูก bootstrap ด้วยโค้ดใหม่
- **THEN** ตารางใหม่ทั้ง 3 ถูกสร้าง, หัวข้อเริ่มต้นถูก seed, `schema_version`
  กลายเป็น 35 และข้อมูลเดิมทุกตารางยังอยู่ครบไม่ถูกแตะ

#### Scenario: bootstrap ซ้ำอีกรอบ
- **WHEN** โค้ดชุดเดิมถูก deploy ซ้ำและ bootstrap ทำงานอีกครั้ง
- **THEN** ไม่มี error, ไม่มีตาราง/หัวข้อถูกสร้างซ้ำ และงานที่มีอยู่ไม่ถูก
  เปลี่ยนแปลง

#### Scenario: ปลายทางถูกลบทั้งที่ยังมีลิงก์ชี้อยู่
- **WHEN** ใบเสนอราคาหรือเอกสารที่มี `task_links` ชี้อยู่ถูกลบออกจากระบบ
- **THEN** การลบสำเร็จตามปกติ (ไม่ติด FK constraint) และแถวใน `task_links`
  ยังอยู่ครบเพื่อใช้แสดง label snapshot + "ถูกลบแล้ว"

## Non-goals
- ไม่มีการมอบหมายงานให้คนอื่น (`assignedTo`) — ระบบนี้เป็น single-admin
  กระดานจึงเป็นของ admin คนเดียว
- ไม่มีงานประจำแบบวนซ้ำ (recurring task) ในเฟสนี้ — สร้างใหม่ทีละใบ
- ไม่มีการเตือนซ้ำทางอีเมล/LINE — การเตือนอยู่บนกระดิ่งและหน้า `/crm/alerts`
  เท่านั้น
- ไม่แตะ `service_schedules` และกฎการเตือนอัตโนมัติเดิม — กระดานงานเป็นคนละ
  ระบบกัน
- ไม่ลบงานหรือหัวข้อโดยอัตโนมัติไม่ว่ากรณีใด
