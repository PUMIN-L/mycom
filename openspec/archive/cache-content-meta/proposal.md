# Proposal: แคช `getAllContentsMeta()` (ส่วนที่ 2)

ต่อจาก `cache-catalog-reads` (ส่วนที่ 1 — สินค้า + หมวดหมู่) ซึ่ง merge ไปแล้ว
change นี้คือตัวที่เหลือ และ **เสี่ยงกว่าอย่างมีนัยสำคัญ** ด้วยเหตุผลที่อธิบายไว้
ทั้งหมดด้านล่าง

## Why

`getAllContentsMeta()` (`app/lib/contentStore.ts:176`) อ่านทั้งตาราง `contents`
และปัจจุบัน **ไม่มีแคชข้าม request เลย** — มีแค่ `cache()` ของ React ที่ dedupe
ได้ภายใน request เดียว

ผู้เรียกทั้งหมด 3 จุด — แต่ **ความถี่ไม่เท่ากัน** ต้องแยกให้ชัดเพื่อไม่ประเมิน
ผลลัพธ์เกินจริง:

| ผู้เรียก | ความถี่จริง |
|---|---|
| `app/showcase/[id]/page.tsx:96` | **ทุก request** — หน้าเป็น `force-dynamic` |
| `app/sitemap.ts:28` | **ทุก request** — `force-dynamic` เช่นกัน |
| `app/components/ProductsJsonLd.tsx:31` | อย่างมาก **1 ครั้งต่อ 60 วินาที** — หน้าแรกเป็น ISR (`app/page.tsx:17`, `revalidate = 60`) ไม่ได้ยิงทุก view |

กำไรจริงจึงมาจากสองจุดแรก ไม่ใช่หน้าแรก (หน้าแรกได้ประโยชน์น้อยมากเพราะ ISR
กันไว้ให้อยู่แล้ว) — เขียนไว้ตรงนี้เพราะการเคลมว่า "หน้าแรกยิงทุกครั้ง" เป็นความ
เข้าใจผิดที่ทำให้ประเมินคุณค่าของ change นี้สูงเกินจริง

ทั้งสามจุดต่างคนต่างยิงคิวรีของตัวเอง — ห่อแคชแล้วจะใช้ผลลัพธ์ก้อนเดียวร่วมกัน

> หมายเหตุ: commit `5b0f220` ตัดคอลัมน์ `blocks` ออกจากคิวรีนี้ไปแล้ว ต้นทุนต่อ
> ครั้งจึงถูกลงมากเมื่อเทียบกับก่อนหน้า สิ่งที่เหลือคือ **จำนวนครั้ง** ที่ยังยิงซ้ำ
> ทุก request ซึ่งเป็นสิ่งที่ change นี้แก้

## ตัวขวางที่แท้จริง: ยังไม่มี invalidation เลยสักจุด

ต่างจากฝั่งสินค้าที่มี `revalidateTag("products", { expire: 0 })` ครบ 10 จุดอยู่แล้ว
**ไม่มี route ไหนของ content เรียก `revalidateTag` เลย** ดังนั้นการห่อแคชโดยไม่ทำ
ส่วนนี้ก่อน = แอดมินแก้บทความแล้วหน้าเว็บไม่อัปเดตจนกว่าแคชจะหมดอายุเอง

## สำรวจเส้นทางเขียนตาราง `contents` ให้ครบ (หัวใจของ change นี้)

ถ้าตกหล่นแม้จุดเดียว แคชจะค้างแบบไม่มีใครรู้ ผมไล่จาก `INSERT/UPDATE/DELETE
FROM contents` ในโค้ดทั้งหมด ไม่ได้ไล่จากชื่อ route — ได้ **5 เส้นทาง ไม่ใช่ 3**

| # | เส้นทาง | ฟังก์ชัน | ตอนนี้ล้าง tag ไหม |
|---|---|---|---|
| 1 | `POST /api/contents` | `addContent` | ❌ ไม่มี |
| 2 | `PUT /api/contents/[id]` | `updateContent` | ❌ ไม่มี |
| 3 | `DELETE /api/contents/[id]` | `deleteContent` | ❌ ไม่มี |
| 4 | `PUT /api/revisions/[id]/restore` (`case "content"`) | `updateContent` | ❌ ไม่มี — **มองข้ามง่ายมาก** |
| 5 | `DELETE /api/products/[id]` (hard delete) | `hardDeleteProduct` → `deleteContent` | ⚠️ ล้างแค่ `"products"` |

เส้นทางที่ 4 และ 5 คือจุดที่ "เพิ่ม revalidateTag ใน 3 route ของ content" —
ซึ่งเป็นสิ่งที่ผมเองเคยสรุปไว้ตอนวิเคราะห์รอบแรก — **ยังไม่พอ**

## ⚠️ ความเสี่ยงหลัก: เส้นทางที่ 5 จะทำให้ bug ที่เพิ่งแก้กลับมา

`app/lib/productDeleter.ts:26` — การ **hard delete สินค้า ลบ content ที่ผูกอยู่ทิ้งด้วย**

```ts
const linkedContents = allContents.filter((c) => c.productId === id);
for (const content of linkedContents) {
  await deleteContent(content.id);      // ← เขียนตาราง contents
}
```

แต่ route ที่เรียกมัน (`app/api/products/[id]/route.ts:99`) ล้างแค่ tag
`"products"` เท่านั้น

ถ้าแคช `getAllContentsMeta` ด้วย tag ใหม่แยก แล้วลืมจุดนี้ ลำดับเหตุการณ์จะเป็น:

1. แอดมิน hard delete สินค้า → content ที่ผูกอยู่ถูกลบจาก DB
2. `revalidateTag("products")` ทำงาน → แคชสินค้าสดใหม่
3. **แคช contents ไม่ถูกล้าง → ยังจำ content ที่ถูกลบไปแล้วได้**
4. `sitemap.ts` อ่านจากแคชนั้น → ประกาศ `/showcase/{id}` ที่ไม่มีอยู่จริงให้ Google
5. Googlebot ตามไปเจอ **404**

นั่นคือ **bug เดียวกันเป๊ะกับที่เพิ่งแก้ไปใน commit `5b0f220`** — ต่างกันแค่สาเหตุ
(รอบก่อนคือ "ไม่ได้กรอง" รอบนี้คือ "แคชค้าง") ผลลัพธ์ที่ Search Console เห็นเหมือนกัน

## What Changes — และการตัดสินใจเรื่อง tag

ทั้งสองทางเลือกต้องเพิ่ม `revalidateTag` ใน 4 route ของ content (เส้นทาง 1-4)
เหมือนกัน ต่างกันแค่ว่า **เส้นทางที่ 5 (cascade) ถูกครอบคลุมอัตโนมัติหรือไม่**

### ทางเลือก A (แนะนำ): ใช้ tag `"products"` ตัวเดิม

- เส้นทางที่ 5 **ถูกครอบคลุมอยู่แล้วโดยอัตโนมัติ** เพราะ route นั้นล้าง
  `"products"` อยู่แล้ว → ความเสี่ยงหลักข้างบน **หายไปเชิงโครงสร้าง** ไม่ใช่แค่
  "ระวังให้ดี"
- ต้องแก้ 4 จุด ไม่ใช่ 5
- ข้อเสีย: แก้บทความจะล้างแคชสินค้าไปด้วยโดยไม่จำเป็น — เสียเปล่าเล็กน้อย
  **ไม่มีผลต่อความถูกต้อง** และแคชสร้างใหม่ถูกมาก (คิวรีเดียว ไม่มี `blocks` แล้ว)
- ข้อเสียเชิงความหมาย: tag ชื่อ `"products"` จะหมายถึง "ข้อมูลแคตตาล็อก" กว้างๆ
  ไม่ใช่แค่สินค้า — ต้องเขียนคอมเมนต์กำกับให้ชัด

### ทางเลือก B: tag ใหม่ `"contents"` แยก

- แม่นยำกว่าเชิงความหมาย ล้างเฉพาะที่ควรล้าง
- แต่ต้องแก้ **5 จุด** และจุดที่ 5 คือจุดที่มองข้ามง่ายที่สุด (อยู่ในไฟล์ฝั่งสินค้า
  ไม่ใช่ฝั่ง content) — ถ้าพลาด = สถานการณ์ 404 ข้างบน
- ถ้าเลือกทางนี้ **ต้อง** มีเทสต์บังคับว่า route ที่เรียก `hardDeleteProduct`
  ล้างทั้งสอง tag ไม่ใช่พึ่งความจำ

**ข้อเสนอ: เลือก A** — เพราะ failure mode ของ A คือ "เสียประสิทธิภาพนิดหน่อย"
ส่วน failure mode ของ B คือ "ส่ง 404 ให้ Google โดยไม่มีใครรู้" ในงานที่เป้าหมาย
คือประสิทธิภาพ การแลกความเสี่ยงด้านความถูกต้องเพื่อประสิทธิภาพเพิ่มอีกนิดไม่คุ้ม

> ถ้าภายหลังพบว่าการล้างเกินเป็นปัญหาจริง (วัดได้) ค่อยแยก tag ทีหลังได้ โดยตอนนั้น
> จะมีเทสต์จากข้อ 4 ของ tasks คอยกันเส้นทางที่ 5 ไว้ให้แล้ว

## ความเสี่ยงอื่น และวิธีกัน/ตรวจแต่ละข้อ

**R1. เทสต์เดิมพังแบบเงียบๆ**
`__tests__/lib/contentStore.test.ts` เรียก `getAllContentsMeta()` ตรงๆ โดย mock
แค่ `@/app/lib/db` พอห่อ `unstable_cache` การเรียกครั้งที่สองจะได้ผลจากครั้งแรก
→ *กัน:* เพิ่ม `vi.mock('next/cache', ...)` **ก่อน** แตะโค้ดจริง แล้วรันให้ผ่าน
ก่อน เหมือนที่ทำกับ `productStore.test.ts` ใน change ที่แล้ว (แพทเทิร์นที่
`__tests__/lib/getProductsData.test.ts:15`)

**R2. ลืมเส้นทางเขียนสักจุด (ทั้งตอนนี้และในอนาคต)**
→ *กัน:* เทสต์ที่อ่าน route จากดิสก์จริงแล้วบังคับว่า route ไหนที่เรียก
`addContent`/`updateContent`/`deleteContent`/`hardDeleteProduct` ต้องมี
`revalidateTag` — แบบเดียวกับ `__tests__/catalogCacheInvalidation.test.ts` ที่
ทำไว้แล้วสำหรับฝั่งสินค้า → *ตรวจ:* พิสูจน์ว่าเทสต์จับจริงโดยลบ `revalidateTag`
ออก 1 จุดแล้วต้อง fail

**R3. ข้อมูลเปลี่ยนรูปร่างตอน serialize**
ตรวจแล้ว: `ContentMeta` หลัง commit `5b0f220` เหลือ `{id, title, createdAt,
productId}` และ `contents.createdAt` เป็น `VARCHAR(255)` (`app/lib/db.ts:96`)
ไม่มี `Date` object → **ปลอดภัย** เหมือนกรณีสินค้า

**R4. มีใครแก้ array ที่ได้กลับมาแบบ in-place**
ตรวจแล้ว: ผู้เรียกทั้ง 3 จุดใช้แค่ `.map()` / `.filter()` / `.find()` — **ไม่มี**
`.sort()` / `.push()` → *กัน:* เทสต์ข้อ R2 ไม่ครอบคลุมเรื่องนี้ ต้องระวังตอน
review ถ้ามีคนเพิ่มการเรียงลำดับฝั่งผู้เรียกในอนาคต

**R5. sitemap อ่านสองแคชพร้อมกันแล้วได้ผลผสม**
`sitemap.ts` อ่าน contents + products แล้วกรองรวมกัน — การกรอง **คำนวณใหม่ทุก
request** ไม่ได้ถูกแคช ดังนั้นต่อให้แคชสองก้อนถูกล้างคนละจังหวะ ผลลัพธ์ก็ยังถูก
ตราบใดที่แต่ละก้อนถูกต้องในตัวเอง → ไม่ต้องทำอะไรเพิ่ม แต่บันทึกไว้เพราะเป็น
คำถามที่คนอ่านโค้ดจะสงสัย

**R6. `getContent(id)` ยังไม่ถูกแคช — จะไม่ตรงกันไหม**
ไม่ — `getContent` อ่านทีละแถวด้วย PK (ถูกและเร็วอยู่แล้ว) และไม่มีแคชข้าม request
จึงสดเสมอ ส่วนรายการ meta ถูกล้างทุกครั้งที่เขียน ทั้งสองจึงตรงกันเสมอ
→ **จงใจไม่แคช** `getContent` ใน change นี้ เพราะไม่ได้แก้ปัญหาอะไรและเพิ่ม
พื้นที่ให้พลาด

**R7. build/tsc ผ่านแต่ Next.js ไม่ยอมตอนรันจริง**
→ *ตรวจ:* รัน `npx next build` เทียบกับ baseline (เครื่อง dev ไม่มี DB จึงจะ
fail ที่ `/catalog` เหมือนกันทั้งสองฝั่ง — ดูว่า **ไม่มี** error เรื่อง
`unstable_cache` โผล่เพิ่ม)

## ที่ไม่ทำใน change นี้

- **ไม่แคช `getContent(id)`** — เหตุผลใน R6
- **ไม่แคช `getAllContents()`** (ตัวเต็มพร้อม `blocks`) — ใช้โดย
  `hardDeleteProduct` ในเส้นทางเขียน การแคชตัวที่ถูกอ่านระหว่างลบมีความเสี่ยง
  อ่านของเก่าแล้วลบไม่ครบ ไม่คุ้มเสี่ยง
- **ไม่แก้ schema** — `SCHEMA_VERSION` ต้องอยู่ที่ **41** เท่าเดิม
- **ไม่เปลี่ยน `force-dynamic`** ของหน้าไหนทั้งสิ้น
