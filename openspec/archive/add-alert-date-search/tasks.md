## 2. Phase 1 — pure helper `app/lib/alertDateSearch.ts` (ใหม่)
- [ ] 2.1 ไฟล์นี้ **ห้าม import อะไรที่แตะ DB** — เป็น pure logic ที่ทั้ง route
      และ UI ใช้ร่วมกัน และทดสอบได้โดยไม่ต้อง render/ไม่ต้อง mock DB
      (แบบเดียวกับ `app/lib/alertEditRoute.ts` และ `app/lib/taskBoard.ts`)
- [ ] 2.2 `isRowMovable(row)` — `true` เฉพาะ `kind` เป็น `schedule` /
      `customer_call` (สถานะ `pending`) หรือ `task` (สถานะ `pending` และ
      `dueDate` ไม่ว่าง) นอกนั้น `false` ทั้งหมด
- [ ] 2.3 `immovableReasonFor(row)` — ข้อความไทยต่อกรณี ครบทั้ง 6 กรณี: ประกัน,
      สอบเทียบ, ลูกหนี้, นัดที่ `completed`, นัดที่ `cancelled`, งานที่ `done`
      แต่ละข้อความต้องบอก **ทางออกที่ทำได้จริง** (ไปแก้ที่ข้อมูลเครื่อง /
      บันทึกวันสอบเทียบใหม่ / หน้า `/billing/receivables` / กด "เปิดใหม่" ก่อน /
      สร้างนัดใหม่แทน) ห้ามเป็นข้อความ "ไม่สามารถแก้ไขได้" ลอยๆ
- [ ] 2.4 ข้อความทุกอันอ่านรู้เรื่องโดย **ไม่ต้องรู้ชื่อคอลัมน์** — ห้ามมีคำว่า
      `warrantyEndDate` / `dueDate` โผล่ในข้อความที่ผู้ใช้เห็น
- [ ] 2.5 `selectableRows(rows, filterKind)` — คืนเฉพาะแถวที่ย้ายได้ ภายใน
      ขอบเขตตัวกรองหมวดที่เปิดอยู่ (ใช้ทั้งกับปุ่มเลือกทั้งหมดและกับข้อความ
      "x จาก y รายการ")
- [ ] 2.6 `selectAllPlan(rows, filterKind, cap)` — คืน `{ ids, selectedCount,
      eligibleCount, cappedOut }` เพื่อให้ UI บอกได้ว่าติ๊กให้กี่อัน เพดานเท่าไร
      และเหลืออีกกี่อัน — **ห้ามตัดเงียบ**
- [ ] 2.7 `computeTargetDate(mode, row, { targetDate, shiftDays })` — เรียก
      `addDaysToDateString` จาก `app/lib/dateFormat.ts` เท่านั้น ห้ามมี
      `new Date()` / `setDate()` / `toISOString()` บนสตริงวันที่ในไฟล์นี้
- [ ] 2.8 `computeTargetDate` ตรวจผลลัพธ์ด้วย `isValidDateString` ก่อนคืนค่า และ
      คืน `null` เมื่อไม่ผ่าน (ผู้เรียกแปลงเป็น `invalid_result`) — ห้ามคืน
      สตริงที่ผิดรูปออกไปให้ใครเขียนลง DB
- [ ] 2.9 `summariseShift(rows, shiftDays, today)` — คืนวันที่ผลลัพธ์เร็วสุด/ช้าสุด
      และ **จำนวนรายการที่จะไปตกก่อนวันนี้** สำหรับกล่องยืนยัน (D5: อนุญาต
      แต่ต้องพูดออกมา) โดย `today` รับเข้ามาเป็นพารามิเตอร์ ไม่เรียกนาฬิกาเอง
      (จะได้ทดสอบได้)
- [ ] 2.10 `validateSearchRange(from, to)` — คืนข้อความไทยของข้อผิดพลาด หรือ null
      ครอบคลุม: รูปแบบผิด, `from > to`, ช่วงกว้างเกิน `DATE_SEARCH_MAX_RANGE_DAYS`
      (วัดด้วย `daysBetweenDateStrings`) — route และ UI ใช้ฟังก์ชันเดียวกัน
      จะได้ไม่มีทางบอกกติกาคนละอย่าง

## 3. Phase 1 — คิวรี่ค้นหา (ไม่แตะ `getAlerts()`)
- [ ] 3.1 `searchDatedAlerts(from, to)` ใน `app/lib/crmStore.ts` — ฟังก์ชันใหม่
      **แยกจาก `getAlerts()` โดยสิ้นเชิง** ห้ามแก้ `getAlerts()` แม้แต่บรรทัดเดียว
      และห้ามใช้ `SCHEDULE_ALERT_SELECT` ร่วมกันถ้าการใช้ร่วมทำให้ต้องแก้ของเดิม
- [ ] 3.2 กำหนดการผูกเครื่อง: `WHERE s.equipmentId IS NOT NULL AND
      s.scheduledDate BETWEEN ? AND ?` — **ไม่มี** `scheduleDays`, **ไม่มี**
      เงื่อนไข `status` (สถานะเป็นป้าย ไม่ใช่ตัวกรอง) และ **ไม่ join
      `alert_snoozes` เพื่อกรอง** (join ได้เพื่ออ่าน `snoozeUntil` มาแสดงป้าย)
- [ ] 3.3 นัดโทรลูกค้า: `WHERE s.equipmentId IS NULL AND s.customerId IS NOT NULL
      AND s.scheduledDate BETWEEN ? AND ?` ด้วยกติกาเดียวกันกับข้อ 3.2
- [ ] 3.4 ประกัน: `WHERE e.warrantyEndDate BETWEEN ? AND ?` — **ไม่กรอง**
      `status != 'Expired'` และ **ไม่กรอง** `warrantyAlertEnabled` แต่ต้อง
      SELECT สองค่านี้ออกมาเพื่อทำป้ายบอกเหตุที่มันไม่เคยขึ้นในฟีด
- [ ] 3.5 สอบเทียบ: `WHERE e.calibrationDate IS NOT NULL AND
      DATE_ADD(e.calibrationDate, INTERVAL ? MONTH) BETWEEN ? AND ?` โดย `?`
      แรกคือ `CALIBRATION_VALIDITY_MONTHS` (**ไม่ใช่** `12 − 2` ที่ฟีดใช้) และ
      คืนวันครบกำหนดที่คำนวณแล้วออกมาเป็น `matchedDate`
- [ ] 3.6 คอมเมนต์เหนือคิวรี่สอบเทียบว่าทำไมใช้ 12 เดือนที่นี่ แต่ 10 เดือนในฟีด
      (ฟีดถามว่า "เริ่มเตือนหรือยัง" การค้นหาถามว่า "วันนั้นครบกำหนดอะไร")
- [ ] 3.7 ลูกหนี้: `WHERE b.dueDate BETWEEN ? AND ? AND b.cancelledAt IS NULL AND
      b.supersededById IS NULL` พร้อมกติกา `receivableOverride` / `docType`
      ชุดเดียวกับฟีด แต่ **ไม่กรองยอดค้าง** (เอกสารที่ชำระครบแล้วยังครบกำหนด
      วันนั้นจริง) — คืน `outstanding` มาด้วยเพื่อทำป้าย "ชำระครบแล้ว"
- [ ] 3.8 ทุกคิวรี่ `ORDER BY <คอลัมน์ที่จับคู่> ASC LIMIT ${DATE_SEARCH_ROW_CAP}`
      และมีคิวรี่ `COUNT(*)` เงื่อนไขเดียวกันแบบไม่ cap คู่กันเสมอ
- [ ] 3.9 DECIMAL ที่ mysql2 คืนมาเป็น **สตริง** (ยอดเงินของลูกหนี้) ต้อง
      `Number()` ที่ชั้น store ครั้งเดียว ตามที่ `getAlerts()` ทำอยู่แล้ว
- [ ] 3.10 `searchTasksByDueDate(from, to)` ใน `app/lib/taskStore.ts` —
      `WHERE dueDate IS NOT NULL AND dueDate BETWEEN ? AND ?` ไม่กรอง `status`
      พร้อม JOIN `task_topics` เพื่อได้ชื่อ/สี/emoji ของหัวข้อ และ **ทน `topicId`
      ที่หาหัวข้อไม่เจอ** ด้วย fallback เดิม (`UNASSIGNED_TOPIC_NAME`)
      ห้าม throw ห้ามกรองงานนั้นทิ้ง
- [ ] 3.11 `crm_tasks` เป็นของ `taskStore` — `crmStore` ห้ามคิวรี่ตารางนี้เอง
      (route เป็นคนประกอบสองผลลัพธ์เข้าด้วยกัน แบบเดียวกับที่
      `GET /api/admin/alerts` ประกอบ `getAlerts()` กับ `countDueTasks()`)
- [ ] 3.12 การเทียบวันทุกจุดใช้ `bangkokDateString(new Date())` เป็น "วันนี้"
      สำหรับธง `overdue` — ห้ามใช้นาฬิกา UTC ของ Vercel ตรงๆ
- [ ] 3.13 ทุกคิวรี่ใช้ bound parameter สำหรับ `from`/`to` — ห้าม interpolate
      สตริงวันที่เข้าไปใน SQL (ค่าคงที่เพดานที่เป็นเลขคงที่ interpolate ได้
      ตามที่ไฟล์นี้ทำอยู่)

## 4. Phase 1 — `app/lib/alertReschedule.ts` (ใหม่): ทรานแซกชันเดียว
- [ ] 4.1 `rescheduleDatedAlerts({ mode, targetDate, shiftDays, items })` —
      ทั้งชุดอยู่ใน `withTransaction` **ครั้งเดียว** ไม่ว่าจะกี่รายการและข้ามกี่ตาราง
- [ ] 4.2 ไฟล์นี้มี SQL ได้แค่ 2 รูปแบบ: `UPDATE service_schedules SET
      scheduledDate = ? WHERE id = ? AND status = 'pending'` และ
      `UPDATE crm_tasks SET dueDate = ? WHERE id = ? AND status = 'pending'`
      (บวก `SELECT` เพื่ออ่านสถานะ/วันที่ปัจจุบัน) — **ห้ามมีคำสั่งใดที่เขียน
      `customer_equipments` หรือ `billing_documents` อยู่ในไฟล์นี้เลย**
- [ ] 4.3 ห้ามเรียก `updateSchedule()` — มัน merge ทั้งแถวแล้วเขียน
      `scheduleType` / `notes` / `assignedToAdminId` กลับลงไปด้วย
      (`app/lib/crmStore.ts:886-923`) เส้นทางเป็นชุดต้องแตะให้น้อยที่สุด
- [ ] 4.4 อ่านสถานะและวันที่ปัจจุบันของทุก item **ภายในทรานแซกชันเดียวกัน** ด้วย
      คิวรี่รวม (`WHERE id IN (...)`) ต่อชนิด — ห้ามยิงคิวรี่ต่อ 1 item (N+1)
- [ ] 4.5 จัดประเภทแต่ละ item เป็น `moved` / `unchanged` / `refused` พร้อม `code`
      และ `reason` ไทย ครบทุกรหัส: `immovable_fact`, `closed`, `no_date`,
      `not_found`, `stale`, `invalid_result`
- [ ] 4.6 `expectedDate` ไม่ตรงกับค่าที่เก็บอยู่ → `stale` เฉพาะรายการนั้น
      (หน้าจอที่เปิดค้างไว้ต้องไม่ย้ายของที่ถูกแก้ไปแล้ว)
- [ ] 4.7 วันปลายทางเท่ากับวันเดิมอยู่แล้ว → `unchanged` (ไม่ยิง UPDATE) เพื่อให้
      สรุปผลไม่โกหกว่า "ย้าย 12 รายการ" ทั้งที่ 3 รายการไม่ได้ขยับ
- [ ] 4.8 `affectedRows = 0` (สถานะเปลี่ยนไประหว่างอ่านกับเขียน) → `refused` +
      `closed` ของรายการนั้น **ห้าม rollback ทั้งชุดเพราะเรื่องนี้**
- [ ] 4.9 callback ต้อง **idempotent** เพราะ `withTransaction` retry ได้ 3 ครั้ง:
      คำนวณวันปลายทางจากค่าที่อ่านได้ในรอบนั้น และสร้าง `results` ใหม่ทั้งชุด
      ในทุกรอบ **ห้าม append ต่อท้ายอาเรย์ที่ประกาศไว้นอก callback**
- [ ] 4.10 คอมเมนต์กำกับว่าเงื่อนไข `expectedDate` คือสิ่งที่กัน "เลื่อนซ้ำสองเท่า"
      เมื่อ commit สำเร็จแต่ ack หายแล้วถูก retry — กรณีนั้นรายงานจะบอก `stale`
      ทั้งที่งานลงแล้ว ซึ่งเป็นด้านที่ยอมพลาดได้ (ข้อมูลถูก รายงานผิด)
- [ ] 4.11 error ของ DB ที่ไม่ใช่การจัดประเภทข้างต้น → ปล่อยให้ throw ออกไป
      ทรานแซกชัน rollback และ **ไม่มีรายการใดถูกย้าย**
- [ ] 4.12 ห้ามเขียน `alert_snoozes`, ห้ามสร้าง `service_logs`, ห้ามเปลี่ยน
      `status` / `completedAt` ของแถวใด
- [ ] 4.13 `sanitizePlainText` กับ `id` และค่าที่เป็นสตริงทุกตัวก่อนนำไปใช้
      แม้จะเป็น bound parameter ก็ตาม (ธรรมเนียมของโปรเจกต์)
