# Proposal: ใบ Job — ใบบันทึกงานบริการหน้างานที่พิมพ์ไปให้ลูกค้าเซ็น

## Why

เวลาช่างออกไป service ที่ไซต์ลูกค้า — PM, เช็คไฟ, ซ่อมโหลดเซลล์, ตั้งค่าเครื่อง —
ทุกวันนี้ **ไม่มีเอกสารอะไรออกจากระบบไปกับช่างเลย** ช่างไปมือเปล่า เขียนลงกระดาษ
ที่หามาเอง แล้วงานที่ทำไปก็ไม่ได้กลับเข้าระบบ

ผลที่ตามมามี 3 อย่าง

**1. ลูกค้าไม่มีหลักฐานว่าเราเข้าไปทำอะไร และเราก็ไม่มี**
งานบริการที่ไม่มีใบเซ็นรับคืองานที่พิสูจน์ไม่ได้ว่าเกิดขึ้น ทั้งตอนลูกค้าถาม
ย้อนหลัง ตอนเคลมประกัน และตอนลูกค้าเอาไปเก็บเข้าแฟ้มตรวจสอบของเขาเอง

**2. ประวัติเครื่องรายตัวขาดครึ่งเดียว**
`customer_equipments` เก็บเครื่องรายตัวพร้อม S/N ประกัน และวันสอบเทียบไว้ครบ แต่
ประวัติ "เคยเข้าไปดูแลเมื่อไร ครั้งไหนบ้าง" ไม่มีที่อยู่ — `service_logs` มีช่อง
`serviceReportNumber` รออยู่แล้วตั้งแต่แรก แต่มันเป็น **เลขอ้างอิงเปล่าๆ**
ที่ไม่มีเอกสารจริงอยู่ปลายทาง เพราะสเปกเดิม (`add-crm-service-tracking`) ตั้งใจ
ให้เป็นแค่ text reference ไม่มีไฟล์แนบ

**3. ข้อมูลที่ระบบมีอยู่แล้ว ต้องมาพิมพ์ใหม่ทุกครั้ง**
ชื่อบริษัทลูกค้า ชื่อผู้ติดต่อ ชื่อเครื่อง และ **หมายเลขเครื่อง** อยู่ในระบบครบ
(`companies`, `customers`, `customer_equipments`) การให้ช่างจดหมายเลขเครื่องเอง
หน้างานคือการเปิดช่องให้จดผิด แล้วประวัติก็ไปเกาะเครื่องผิดตัว

## What Changes

สิ่งที่จะสร้างคือ **ฟอร์มพิมพ์ที่กรอกข้อมูลให้ล่วงหน้า** ไม่ใช่ระบบเซ็นบนจอ
เจ้าของเลือกไว้ชัดเจนว่าจะ **ปริ้นกระดาษไปให้เซ็นแล้วเอากระดาษกลับมา**
ระบบไม่ต้องแนบไฟล์ใบที่เซ็นแล้ว แค่บันทึกไว้ในประวัติเครื่องว่าเคยเข้าไป service
และใบ Job นั้นเลขที่อะไร

วงจรการใช้งานจึงเป็น 3 ช่วง และระบบรับผิดชอบแค่ช่วงหัวกับช่วงท้าย

| ช่วง | ที่ไหน | ระบบทำอะไร |
| --- | --- | --- |
| ก่อนออก | ออฟฟิศ | เลือกบริษัท → ผู้ติดต่อ → เครื่อง (หลายเครื่องได้) → วันที่ → ช่าง แล้วดาวน์โหลด PDF ไปปริ้น |
| หน้างาน | ไซต์ลูกค้า | **ระบบไม่เกี่ยว** — ช่างเขียนงานที่ทำลงในช่องว่างที่เว้นไว้ ลูกค้าเซ็นบนกระดาษ |
| กลับเข้าออฟฟิศ | ออฟฟิศ | กดปิดงาน 1 ครั้ง → ใบนั้นขึ้นในประวัติของทุกเครื่องที่อยู่ในใบ |

### Database (schema v38)

> **ลำดับสำคัญ:** `add-receivables` จอง v37 ไว้แล้ว ใบ Job จึงต้องเป็น **v38**
> และ `SCHEMA_VERSION` ห้ามลดหรือใช้เลขซ้ำเด็ดขาด — เลขที่เคยขึ้น production
> แล้วถูกนำกลับมาใช้ จะทำให้ migration ถูกข้ามทั้งก้อนแบบเงียบๆ (เคยพังมาแล้ว
> ตอน v33)

- ตารางใหม่ `service_jobs` — 1 แถวต่อ 1 ใบ: `id` VARCHAR(36) PK,
  `jobNo` VARCHAR(255) UNIQUE, `companyId`, `customerId`, `jobDate` VARCHAR(20)
  (`YYYY-MM-DD`), `technicianName` VARCHAR(255) **ว่างได้** (ไม่พิมพ์ = เว้นให้
  ช่างเขียนเองบนกระดาษ), `scheduleId` VARCHAR(36) NULL (ผูกนัดหมายเดิม),
  `status` VARCHAR(20) DEFAULT `'issued'` (`issued` | `completed` | `cancelled`),
  `workSummary` TEXT NULL (พิมพ์ย้อนหลังจากกระดาษที่เซ็นกลับมา — ตัวเลือก),
  `completedAt`, `createdAt`
- ตารางใหม่ `service_job_equipments` — เครื่องหลายตัวใน 1 ใบ:
  `jobId` + `equipmentId` เป็น composite PK, `sortOrder` INT
  ใช้แบบเดียวกับ `task_links (taskId, targetType, targetId)` ที่ใช้อยู่แล้ว
- **ผูกด้วย id ธรรมดา + index ไม่ใช้ FK** ไปยัง `service_schedules` ตามแบบ
  `sales_records.quotationId` เพราะปลายทางถูกล้างได้อิสระ

### เลขที่เอกสาร

- รูปแบบ `JOB<DDMMYY>-NN` ตามที่ใบเสนอราคาเปลี่ยนไปแล้ว ไม่สร้างรูปแบบที่สาม
- จองเลขผ่าน `used_docnos` **ทะเบียนเดียวกับใบเสนอราคาและใบวางบิล** ซึ่งกัน
  เลขซ้ำด้วย PRIMARY KEY อยู่แล้ว และได้การกันเลขชนข้ามปีที่ `add-receivables`
  กำลังแก้อยู่มาใช้ฟรีๆ
- **ต้องรอ `add-receivables` ลงก่อน** เพราะมันกำลังแก้ตัวออกเลขอยู่ ถ้าทำคู่กัน
  จะแย่งไฟล์เดียวกัน

### หน้าจอและเอกสาร

- หน้าใหม่ `/service-job` สร้าง/แก้ใบ และ `/service-job/saved` รายการใบที่ออกแล้ว
  โครงเดียวกับ `/quotation` และ `/billing` ที่มีอยู่
- เลือกข้อมูลด้วย `SearchableDropdown` ทุกช่อง: บริษัท → ผู้ติดต่อ (กรองตาม
  บริษัทที่เลือก) → เครื่อง (กรองตามลูกค้า) **หมายเลขเครื่องขึ้นเองจากเครื่อง
  ที่เลือก ห้ามให้พิมพ์เอง**
- **ดาวน์โหลดเป็น PDF ได้เหมือนใบเสนอราคา** ใช้ jspdf + html2canvas-pro
  ตัวเดียวกับที่ `/quotation` ใช้อยู่
- บนกระดาษต้องมี **ช่องว่างจริงให้เขียน**: ตารางเครื่องมีคอลัมน์ "งานที่ทำ" เว้น
  ว่าง + ช่องบรรยายรวมด้านล่างแบบมีเส้นบรรทัด + บล็อกลายเซ็น 2 ฝั่ง
  (ช่างผู้ปฏิบัติงาน / ลูกค้าผู้รับบริการ) พร้อมชื่อตัวบรรจงและวันที่

### เชื่อมกับของเดิม

- สร้างใบ Job จากนัดหมายใน `service_schedules` ได้ตรงๆ — ข้อมูลลูกค้าและเครื่อง
  มาจากนัดนั้น
- กด "ปิดงาน" แล้ว: `service_jobs.status` เป็น `completed`, นัดที่ผูกไว้เป็น
  `done`, และเขียน `service_logs` 1 แถวต่อ 1 เครื่องในใบ โดย
  `serviceReportNumber` = `jobNo` — ซึ่งคือความหมายที่ช่องนั้นถูกสร้างมาตั้งแต่แรก
- ประวัติของเครื่องแต่ละตัวแสดงใบ Job ที่เครื่องนั้นเคยอยู่ พร้อมสถานะ

## ที่ยังไม่ทำ และเหตุผล

- **ไม่แนบไฟล์ใบที่เซ็นแล้ว** — เจ้าของสั่งชัดว่าไม่ต้อง กระดาษเก็บเข้าแฟ้มเอง
- **ไม่มีรายการงานให้ติ๊ก** — เจ้าของสั่งว่าเว้นช่องให้ช่างเขียนเองหน้างาน
  ไม่ต้องมีเช็คลิสต์
- **ไม่แตะ `calibrationDate` ของเครื่องอัตโนมัติ** — ในเมื่องานที่ทำเป็นลายมือ
  บนกระดาษ ระบบไม่มีทางรู้ว่าใบนั้นสอบเทียบจริงหรือแค่ไปเช็คไฟ การเดาแล้วเลื่อน
  วันสอบเทียบครั้งหน้าออกไป คือการปิดเสียงแจ้งเตือนที่ควรจะดัง
- **ไม่มีค่าบริการ/ยอดเงินในใบนี้** — เป็นใบบันทึกงาน ไม่ใช่เอกสารการเงิน
  การเก็บเงินยังไปทางใบแจ้งหนี้เหมือนเดิม

## จุดที่ยังต้องตัดสินใจ

1. **ประวัติเครื่องขึ้นตอนไหน** — ข้อเสนอคือขึ้นตอน "ปิดงาน" ไม่ใช่ตอนออกใบ
   เพราะใบที่ออกแล้วแต่ยังไม่ได้ไป ถ้าขึ้นในประวัติทันทีจะกลายเป็นบันทึกว่า
   เข้าไปแล้วทั้งที่ยังไม่ได้เข้า แลกกับการที่ต้องกดปิดงาน 1 ครั้งเมื่อกระดาษ
   กลับมา
2. **ช่องงานที่ทำ อยู่ตรงไหน** — ข้อเสนอคือมีทั้งคอลัมน์ต่อเครื่อง (จะได้รู้ว่า
   ทำอะไรกับเครื่องไหน) และช่องรวมด้านล่าง ถ้าเจ้าของอยากได้ช่องใหญ่ช่องเดียว
   แก้ได้ในชั้น layout ไม่กระทบฐานข้อมูล
